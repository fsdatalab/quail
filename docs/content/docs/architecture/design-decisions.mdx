---
title: Design decisions
---

This page explains why the engine is structured the way it is.

## No public KV interface

A model backend owns its scheduler, KV layout, allocation, retention,
eviction, and model calls. These parts depend on each other and
should change together. Quail does not expose a KV API.

## One model copy per GPU

Each GPU holds one complete model copy. Quail does not split a model
across GPUs. This keeps the per-GPU execution self-contained and
avoids cross-GPU communication during forward passes.

## Fixed join order

Join order and anchors are decided before inference, not adapted
during execution. The planner uses estimated selectivities and a
Selinger-style search. Actual selectivities may differ, but the
execution follows the planned order. This makes the execution
predictable and the plan readable.

## Operator-at-a-time with streaming inside operators

Quail finishes each physical operator before starting the next. But
within a `PackedFilter` or `AnchoredJoin`, documents stream through
their predicates without waiting for the rest of the batch. This
gives the planner a clear materialization boundary while still
allowing KV reuse across predicates within one operator.

## Built-in code uses the same interfaces as extensions

Every built-in component registers through the same
`ExtensionRegistry` that extension code uses. There is no
privileged internal API. This means the extension interfaces are
always tested by the engine itself.

## No Modal integration

Quail does not depend on Modal. The user writes the Modal function,
configures the image, and manages volumes. Quail runs inside the
function like any other Python library. This keeps Quail independent
of any particular compute provider.

## Scope

The current runtime supports true-or-false filters and joins.
`AI.CLASSIFY`, `AI.EXTRACT`, and `AI.MAP` are planned but not
implemented. Open-ended generation and request forking are outside
the current design.
