---
title: Execution
---

Quail executes the operators selected by the physical plan. The CPU
coordinates their inputs and outputs. The GPU performs model inference.

Quail can ask several questions about a document without processing the
whole document again for each question. See
[Physical plans](/docs/architecture/physical-plans) for an example plan.

## Operator scheduling

### The runner

The *runner* coordinates the operators in the plan. It runs an operator
when the operator's required inputs are available.

- Model operators, such as classification, use the GPU.
- Operations that test computed labels use Apache Arrow on the CPU.
- Rust builds the region's rows from the operators' outputs: the id
  column of each table and the answers.
- DataFusion runs the relational operators above the region, such as
  ORDER BY, LIMIT, DISTINCT, and GROUP BY, on the region's rows, and
  joins each table's other columns back on its id. The region hands
  DataFusion its rows while it runs; see
  [Streaming the region's rows](#streaming-the-regions-rows).
- Compatible operators can pass documents to one another before they
  finish processing the whole input table.

### Pipelines and batches

A *pipeline* is a group of operators that can pass documents to one
another before they finish processing the whole input table.
*KV* is the key and value vectors saved for tokens the model has already
processed. Quail can keep a document's KV available as it passes through
the pipeline.

For example, imagine a `reviews` table containing review text. A query
first keeps reviews that discuss the acting, then classifies their
sentiment, then keeps negative reviews. In a pipeline:

1. A review reaches classification as soon as it passes the first filter.
2. Classification reuses the review's KV and adds the sentiment question.
3. The CPU tests the returned label and keeps the review if it is negative.

A *model request* is the model computation needed for one document or
pair at one stage of execution. A *batch* combines model requests that
can be processed together. Requests from different pipeline stages can
share a batch.

A *forward pass* processes a batch's new tokens through the model,
using any saved KV. The CPU prepares the next batch while the GPU
processes the current batch.

Quail limits each batch by token count and available KV memory:

- The *token budget* limits how many new token positions a forward pass
  can process. Shorter requests allow more documents to fit in a batch.
- The *KV budget* limits the GPU memory used for saved KV. Long documents
  can fill that memory before the token budget is reached.

A document whose prefix and first request exceed the token budget is
written over several forward passes, as vLLM's chunked prefill does. It
reserves its KV pages when admitted, and each pass writes the next piece
of its prefix into those pages, reading the pieces before it. Its first
request runs in the pass after the last piece. Documents that borrow its
prefix wait for that pass. On a hybrid model each piece starts from the
recurrent state the previous piece saved. Only a document whose KV does
not fit the whole KV budget fails, with an error that names it. A model
under set attention runs every request as one unpaged sequence, so a
document there must fit one forward pass.

An operator that requires all its input rows ends a pipeline. Later
operators wait until those rows are available.

On one GPU, a `RegionExecution` runs each pipeline, and each model
operator alone, through the same loop. Each physical node, or group of
consecutive nodes of one kind, is a `ModelOperator`. The region pushes
documents into the first operator. When a document leaves an
operator's stages, the region settles it there; a kept document goes
on to the next operator. After each forward pass the region takes the
rows each operator finished. Once the loop ends, it closes each
operator, which returns its nodes' results. A score of pairs and
extractions alone use their own prompt layout. Every other chain reads
one document table: the first node's prompt head with each document,
keyed by alias and document id, under one prefix tree.

Under set attention a pipeline also runs in one loop, but each request
there is a *pass*: one unpaged sequence of a state, a document and the
text after it, then the questions asked of it. A `SetChain` gives each
pass of each pass group, each join, and each classification of a
join's pairs a stage of one `StageExecutor`, which asks each pass at
its own stage only. A step's passes enter the loop once every pass of
the step before has answered, because a step asks only the rows the
steps before it kept.

### Reading the region's input

`ModelRegionExec` reads every row of each input the region reads, then
plans the region once over all of them and runs that plan once. The
planner sees every document's length, and KV and prefix sharing span
the whole input. For example, a score over 200,000 reviews is one plan
and one run over 200,000 rows, not four runs of 65,536 rows or fewer.

A region starts once each of its inputs has ended, so a region whose
input is another region's rows runs after that region has finished, on
the same thread.

### Streaming the region's rows

A row of the region is final once the region's last step, one operator
or one pipeline, has produced it. Every earlier step has finished by
then. So the runner sends rows on as the last step reports them:

- A filter, score, or classification that is the last step reports
  each forward pass's finished documents. Rust builds those documents'
  rows from the last step's outputs for them and the earlier steps'
  whole outputs, and `ModelRegionExec` hands them to DataFusion at once.
- A join reports each anchor's true pairs once they are answered. A
  lone anti-join reports each anchor that matched nothing once it
  settles, and a classification of a join's pairs reports each
  anchor's pairs once it settles.
- Under set attention each step of a pipeline reports its rows when
  the step finishes, while later steps run.
- Any other last step, such as an extraction, a map, or an operator
  with a guard, sends its rows when it finishes.
- A region with a fetch sends its rows once every row is in, so Rust
  can keep its first rows.
- A row is sent once: when the step finishes, the runner sends only
  the rows it has not sent.

For example, imagine `SELECT r.id, AI.SCORE(...) AS score FROM reviews
r ORDER BY score DESC LIMIT 25`. DataFusion's top-k sort reads each
forward pass's scored reviews while the GPU scores the next ones.

The thread that called DataFusion runs each region, as before, and
DataFusion's workers run the operators above it, so they read the
region's rows while the region runs. Rows come in the order they
finish. Only an ORDER BY sets the order of the result.

## Query operations

### Filters

A model filter can ask several TRUE or FALSE questions about each document.
Quail processes the document and the first question together. A document
that fails a question stops there. A document that passes continues to the
next question.

After each answer, Quail removes the question's KV and keeps the document's
KV. Removing the added KV while keeping the document's KV is called
*KV rewind*. The next question reuses the document's KV.

A passing document can reach a later operator in the same pipeline without
waiting for the filter to finish over the rest of the table.
See [KV](/docs/architecture/kv) for how Quail stores and reuses KV.

### Joins

A model join evaluates a question about a pair of documents. The planner
chooses one side as the *anchor*, whose document KV remains available
while Quail evaluates documents from the other side. A document from the
other side is a *partner*.

For example, imagine joining a `reviews` table with an `aspects` table.
Each aspect describes a subject such as acting or plot. The join asks
whether each review discusses each aspect. If reviews are the anchors,
Quail processes a review and the fixed join instructions once, then reuses
that KV when evaluating its aspects. The result contains review and
aspect pairs for which the model answers TRUE.

Several partners can be evaluated in the same batch. Each partner uses
the anchor's KV and its own tokens. Partners do not use one another's tokens.

An anchor that passes a filter in the same pipeline can enter the join
with its document KV already available. A later join can also reuse that
KV if the plan keeps it. See [KV retention](/docs/architecture/kv#kv-retention).

### Evaluation on partial answers

A map or an extraction writes its answer one token at a time. When the
region tests that answer, Quail decides the test on the tokens decoded
so far and stops the answer once the test is settled.

- `w` is the answer's text so far.
- `C(w)` is the set of complete answers still possible. A map's answer
  goes on with any text within its answer limit. An extraction copies a
  span of its document, so its answer goes on only with the text that
  follows a place where the document holds `w`. Before its first token,
  an extraction may still answer NULL, which means it found nothing.
- A test is *decided TRUE* at `w` when it is TRUE for every answer in
  `C(w)`, and *decided not TRUE* when it is FALSE or NULL for every one.
  Otherwise it is *undecided*. Undecided is a state of the executor, not
  a NULL.

The physical rule `should_stop_answers_early` gives each map and
extraction the region's exact tests that read its answer alone. The
executor stops an answer, and frees its KV, once one of them, or one of
the node's hint tests (R3), is decided not TRUE: the region would drop
the row. When nothing else reads the answer, it also stops once every
exact test is decided TRUE: the region keeps the row whatever the rest
of the answer says. The answer keeps its text so far, which is itself
in `C(w)`, so the region's filter gives it the value it was decided to
have.

For example, imagine `SELECT r.id FROM reviews r WHERE
LEFT(AI.MAP(r.body, 'Is it kind?'), 3) = 'yes'`. An answer that starts
with `n` is decided not TRUE after one token. An answer that starts
with `yes` is decided TRUE after it, and the map stops there, since the
SELECT list does not read the answer.

The decision runs in Rust, on DataFusion's expression of the test
(`crates/quail-datafusion/src/partial.rs`). It reads these shapes of
the answer `a` with literals, and AND, OR, NOT, and `IS [NOT] TRUE` or
`FALSE` of them:

- `a LIKE 'x%'`, `a LIKE 'x'`, `STARTS_WITH(a, 'x')`,
  `LEFT(a, k) = 'x'`, and `SUBSTR(a, 1, k) = 'x'`;
- `a = 'x'`, `a <> 'x'`, and `a IN ('x', ...)`;
- `a IS NULL` and `a IS NOT NULL`;
- `LENGTH(a)` or `CHARACTER_LENGTH(a)` compared with an integer.

The executor does not bound how many characters a map's remaining
tokens may add, so a length test of a map's answer is decided only once
the text so far passes the bound, or once the answer ends. Any other part stays
undecided until the answer is complete, and the
region's filter then tests the answer as usual. Parts are decided one at
a time, so a test that reads the answer twice may be decided later than
it could be, never wrongly. A classification needs none of this: it
scores its labels. A test of an AI.SCORE needs an upper bound on the
score, which Quail does not compute yet.

### Classification

Classification assigns one of the supplied labels to each input row.
It can run in a pipeline and reuse document KV from preceding operators.
The selected scoring method determines whether classification needs one
or several forward passes.

#### Label scoring

*Label scoring* determines how the model selects one of the supplied
classification labels. For Qwen3 generative models, the
[optimizer selects a method](/docs/architecture/optimizer#label-scoring)
using estimated GPU time. The methods can return different labels because
they score the choices differently.

For example, imagine classifying customer messages as `refund` or `praise`.
The generative models can select between these labels in three ways:

| Method | How it selects a label | Requirement |
| --- | --- | --- |
| `letters` | Give each label a distinct letter in the prompt, then compare the model's scores for those letters. | Each letter must be one token. |
| `trie_tree` | Score each label's token sequence and choose the highest sequence probability. Labels with common starting tokens share computation. | [Tree attention](#attention-paths) must be available. |
| `trie_decode` | Choose the allowed token with the highest score at each step until a label is complete. Only tokens that continue a supplied label are allowed. | No label's token sequence can be the start of another label's token sequence. |

A *trie* is a tree of token sequences in which common starting tokens are
stored together. `trie_tree` evaluates every label sequence.
`trie_decode` follows one sequence, so it can choose a different label
from the one with the highest probability for its complete sequence.

For example, suppose `refund` has two tokens. The first has probability
0.8, and the second has probability 0.6 after the first. The sequence
probability is 0.48. If the single token label `praise` has probability
0.3, `trie_tree` selects `refund`.

Additional requirements apply:

- `trie_decode` requires a model without extra answer positions and a
  classification that does not reuse document KV from an earlier operator.
- Requesting probabilities excludes `trie_decode`, because it does not
  score every label.
- Classifications of joined pairs use `letters` for generative models.
- DiffusionGemma uses `letters` with its extra answer positions. See
  [DiffusionGemma](/docs/user-guide/models#diffusiongemma) for configuration.

Decision 2.0 Kai uses `decision_choice`. It scores each supplied label
as an option and selects the option with the highest score. The model
processes all options in one request. It can also return label
probabilities for classifications of individual documents.

#### Classifying joined rows

Classification can also read both documents of a joined pair. It runs
in the join's pipeline, on one GPU, and classifies only pairs that the
join kept. It reuses the anchor's KV when processing each pair.

## GPU execution

### Attention paths

During *attention*, the model combines information from the current token
and earlier tokens. A *prefix* is the token sequence at the start of a
request. Quail supports two attention paths for filters and joins:

- *Unified attention* processes a request's saved prefix and new tokens
  in one attention call.
- *Tree attention* processes shared prefixes in one call and each
  request's own tokens in another. Quail combines the two results.

Tree attention groups requests that use the same saved KV. Grouping can
reduce memory reads, but the additional call and combination take time.
The [planner compares those costs](/docs/architecture/optimizer#attention-path)
when choosing a path.

Tree attention supports BF16 and FP8 weights. Quail enables it for models
with at least two billion parameters, excluding embeddings and output
layers. Smaller models use unified attention. DiffusionGemma also uses
unified attention because it requires extra answer positions. See
[Supported models](/docs/user-guide/models).

### Multiple GPUs

Each GPU holds a complete model copy and its own KV. A *coordinator* is
the process that divides the work among GPU workers and collects their
results.

- For filters, it assigns documents using their token lengths to balance
  work across GPUs.
- For joins, anchors stay on the GPU that filtered them so their KV can
  be reused. Each GPU receives the partner documents needed for its anchors.
- Between groups of joins, it combines the results and distributes the
  next group's anchors.

Quail supports up to eight GPUs on one host. Each GPU holds all model
weights; the weights are not divided between GPUs.
