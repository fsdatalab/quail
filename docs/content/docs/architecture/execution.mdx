This page describes how the physical plan is executed on the GPU.

## The runner

`GenericRunner.run(graph, context)` walks nodes in topological
order. For each node it calls the registered runtime, checks the
output ports, records node metrics, and notifies observers.

Relational nodes (`Recombine`, `Project`, `Limit`) run with Arrow
on the CPU. Model nodes run on the GPU.

## Planning

The planner builds the physical plan from the model spec, device
spec, and per-document token counts. It decides the filter order,
the anchor of each join, the forward pass token budget and KV arena
budget (based on GPU memory after the model weights), which document
KV to retain across operator boundaries, and document shards per
GPU.

## Filters

The filter loop fills each forward pass by two budgets: tokens and
KV pages.

### Pipelining

A document that passes one predicate enters the next forward pass
with its next predicate immediately. It does not wait for the rest
of the batch.

### Token-based admission

A forward pass is full when its token budget or the arena's free
pages are exhausted, not when a fixed request count is reached.

### KV rewind

The document's KV from the first predicate stays in the arena. Later
predicates add only the question suffix tokens. KV pages are freed
when a document fails a predicate or finishes its last one.

## Joins

A join packs one anchor document's prefix per forward pass and
evaluates multiple partner documents against it. All partners in one
forward pass share the anchor's KV through paged cross-attention.

### Gating

Between join stages, anchors with no passing pair are dropped and
their pages freed.

### Streaming

The first join group's anchor filter does not finish before the join
starts. Each document that passes its last filter keeps its KV and
enters the join immediately.

### Retention

Later join groups reuse retained KV for their anchors. If KV was
evicted, the document is reprocessed.

The planner uses dynamic programming (Selinger-style) to choose the
join order and anchors before inference.

## Multiple GPUs

With multiple GPUs, each GPU has its own CUDA context and KV arena.
A coordinator process sends work over pipes.

- **Filters**: each GPU filters its own shard of documents.
- **Joins**: anchors stay on the GPU that filtered them. Every GPU
  receives every surviving partner document.
- **Between join groups**: the coordinator prunes survivors and
  re-partitions the next anchor's documents.

## GPU code

| File | What it does |
| --- | --- |
| `quail/executor/pack.py` | Admission logic for filters and joins. |
| `quail/executor/arena.py` | The paged KV arena and page accounting. |
| `quail/executor/attention.py` | Forward pass with two-call attention and log-sum-exp merge. |
| `quail/executor/loop.py` | The overlapped filter and join execution loops. |
| `quail/executor/model.py` | Weight loading through vLLM's loader. |

The fused kernels assume the Qwen3 architecture: QK-norm before
RoPE, gated SiLU MLP, FP8 block-quantized weights.
