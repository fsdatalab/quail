---
title: Execution
---

Quail's executor runs a physical plan for one model region. The GPU
computes AI answers; the CPU coordinates operators and tests answer
columns. DataFusion runs SQL outside the model region.

## Operator scheduling

### The runner

`GenericRunner` runs an operator when its inputs are available. It can
combine compatible operators into a pipeline. Each operator returns a
`NodeResult` with its output values and measurements.

### Pipelines and batches

**Pipelining** passes a document to the next operator without waiting
for every document to finish. Compatible operators reuse its KV.

E.g., a review that passes an `AI.IF` filter can immediately enter a
classification in the same pipeline. Classification adds its question
tokens to the saved document KV. A CPU filter then tests the label.

A batch can contain requests from different pipeline stages. Each
forward pass processes the batch's new tokens. **Token-based admission**
limits new work by:

- The token budget: the maximum new token positions in a forward pass.
- Available KV memory: the space for active documents and their requests.

For paged execution, a document prefix that exceeds the token budget
can span several forward passes. Quail reserves its KV pages before
starting. Other documents wait until the shared prefix is complete
before reading it. A document that cannot fit the KV capacity fails.

A set-attention model processes each request as one unpaged sequence;
the request must fit one forward pass. See
[supported models](/docs/user-guide/models) for model-specific behavior.

An operator that requires all its input rows ends a pipeline.

### Reading the region's input

Quail reads each input to its end before planning the model region.
The planner measures all document lengths and shared prefixes, rather
than planning each Arrow batch separately. A model region that reads
another region's rows waits for that input to finish.

### Streaming the region's rows

Operators report completed rows to `FinishedRows`. Quail constructs a
model-region row once every operator that contributes to it has
reported its part. Quail sends each completed row to DataFusion once.

Reporting frequency depends on the operator. Some report after each
forward pass; others report when they finish. Guards and document
deduplication delay reports until Quail restores the original row IDs.
DataFusion can process completed rows while the GPU continues.

Only `ORDER BY` sets the result order. A region's fetch keeps the first
rows Quail constructs. See
[FinishedRows](https://github.com/fsdatalab/quail/blob/main/crates/quail-python/src/finished.rs).

## Query operations

### Filters

An `AI.IF` filter asks TRUE or FALSE questions. A document that fails
stops; a document that passes can continue to the next question.
**KV rewind** removes the question's KV while preserving the document's
KV for reuse. See [KV](/docs/architecture/kv).

### Joins

A join asks about a pair of documents. The planner chooses an **anchor**
whose KV stays available while Quail evaluates **partners** from the
other table.

E.g., when joining reviews to aspects, a review can be the anchor.
Quail processes the review once, then adds each aspect's tokens to ask
whether the review discusses it. The join keeps pairs that answer TRUE.

Several partners can share a batch. They read the anchor's KV, not one
another's tokens. A compatible filter before the join can supply anchor
KV. [KV retention](/docs/architecture/kv#kv-retention) can preserve it
for later joins.

### Evaluation on partial answers

Quail can stop a map or extraction before it completes an answer when
a filter's outcome cannot change:

- Reject the row when every possible completion makes a test FALSE or NULL.
- Keep the row when every exact test must be TRUE, but stop the answer
  only if nothing else reads it.
- Otherwise, continue the answer. An undecided test is not SQL NULL.

E.g., for a registered `reviews` table with `id` and `body` columns:

```sql
SELECT r.id
FROM reviews r
WHERE LEFT(AI.MAP(r.body, 'Is the review kind? Answer yes or no.'), 3) = 'yes';
```

An answer starting with `n` cannot pass. An answer starting with `yes`
already passes, and this query does not need the remaining text.

Quail recognizes literal prefix tests and comparisons with answer text.
It also handles null tests and integer comparisons with answer length.
It combines these through SQL boolean operators. An extraction's
possible completions must continue a span of its document.

When those forms leave a test undecided and few complete answers are
still possible, DataFusion evaluates the test on each one. This decides
any expression of the answer, such as `answer LIKE '%2027%'`, for an
extraction with few places left to copy from.

For a map's open-ended text, DataFusion's `PruningPredicate` reads the
test against the range of strings that start with the text so far, as
it reads a Parquet column's least and greatest values. That decides
comparisons such as `answer < 'M'`. Any other expression waits for the
complete answer.

See [partial.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/partial.rs)
for supported expression forms.

### Classification

Classification can reuse document KV from earlier operators in a
compatible pipeline. Its scoring method determines how it evaluates labels.

#### Label scoring

The planner compares supported methods using estimated GPU time.
Methods can return different labels because they score choices differently.

| Method | Label selection | Requirement |
| --- | --- | --- |
| `letters` | Score one letter per label. | Each letter is one token. |
| `trie_tree` | Score all label token sequences and choose the highest sequence probability. | Tree attention is available. |
| `trie_decode` | Choose the highest-scoring allowed token at each step. | No label token sequence starts another; no extra answer positions or requested probabilities. |

A trie stores common starting tokens together. `trie_decode` follows
one sequence, so it need not select the most probable complete label.
Model-specific methods include `decision_choice` and `set_choice`;
see [models](/docs/user-guide/models).

#### Classifying joined rows

A classification can read both documents of a joined pair. It evaluates
only pairs the join keeps and can reuse the anchor's KV. Generative
pair classification uses `letters`.

## GPU execution

### Attention paths

A prefix is the token sequence at the start of a request. Quail supports
two attention paths:

- **Unified attention** processes saved prefix KV and new tokens in one call.
- **Tree attention** processes shared prefixes separately from each request's
  own tokens, then combines the partial values.

Tree attention can reduce repeated KV reads, but its extra call and
combination take time. The planner [compares these costs](/docs/architecture/optimizer#attention-path).
It permits tree attention for models with at least two billion dense
parameters, no recurrent state layers, and no extra answer positions.

### Multiple GPUs

Quail supports up to eight GPUs on one host. Each GPU holds a complete
model copy; Quail does not divide weights between GPUs.

The planner divides a model region into **stages**, with one DataFusion
partition per GPU. Each stage uses one table's document IDs as its key.
DataFusion hashes those IDs to assign rows to GPUs.

- Filters run with the join anchored on their table, so surviving
  anchors keep their KV on the same GPU.
- Partner filters run in separate stages. Their surviving rows go to
  every partition that needs them.
- A `Barrier` starts a stage keyed by the next anchor. DataFusion moves
  rows between stages; a stage starts after its inputs finish.
- Documents with identical text or the same per-key stop group stay
  together when partitioning requires it.

Hashing balances document counts, not token counts. Ready stages on
one GPU run sequentially. With a limit, each GPU can admit documents
before other GPUs reach that limit, so multiple GPUs can ask more
questions than one GPU. Without `ORDER BY`, they can return different
qualifying rows.
