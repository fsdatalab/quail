This section describes how Quail works internally.

## How a query runs

1. The [SQL front end](https://github.com/fsdatalab/quail/blob/main/quail/sqlfront/compile.py)
   or the [Python builder](https://github.com/fsdatalab/quail/blob/main/quail/builder.py)
   produces a logical plan.
2. The session reads Arrow batches from each registered table and
   tokenizes the document columns.
3. The [planner](https://github.com/fsdatalab/quail/blob/main/quail/planner/decide.py)
   proposes one or more physical plans with cost estimates. The
   cheapest one is selected.
4. The [runner](https://github.com/fsdatalab/quail/blob/main/quail/runtime/runner.py)
   executes the physical graph. Model nodes run on the GPU.
   Relational nodes run with Arrow on the CPU.
5. The query returns the matching rows as a `pyarrow.Table` and an
   execution report with timing and token counts.

## Packages

| Package | What it does | Source |
| --- | --- | --- |
| `quail.sqlfront` | Parses SQL into a logical plan. | [compile.py](https://github.com/fsdatalab/quail/blob/main/quail/sqlfront/compile.py) |
| `quail.builder` | Builds logical plans from Python. | [builder.py](https://github.com/fsdatalab/quail/blob/main/quail/builder.py) |
| `quail.logical` | Logical node types and prompt binding. | [logical.py](https://github.com/fsdatalab/quail/blob/main/quail/logical.py) |
| `quail.physical` | Typed physical nodes with ports. | [physical/](https://github.com/fsdatalab/quail/tree/main/quail/physical) |
| `quail.planner` | Cost model, join ordering, KV retention. | [planner/](https://github.com/fsdatalab/quail/tree/main/quail/planner) |
| `quail.runtime` | Session, runner, token store, results. | [runtime/](https://github.com/fsdatalab/quail/tree/main/quail/runtime) |
| `quail.executor` | GPU code: packing, KV arena, attention. | [executor/](https://github.com/fsdatalab/quail/tree/main/quail/executor) |
| `quail.specs` | Model and device constants. | [specs/](https://github.com/fsdatalab/quail/tree/main/quail/specs) |
