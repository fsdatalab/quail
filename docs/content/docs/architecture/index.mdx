This section describes how Quail works internally. You do not need
to read it to use Quail. It is here for contributors and for users
who want to understand what happens between `session.sql(...)` and
`result.collect()`.

## How a query runs

1. The SQL front end or the Python builder produces a **logical plan**
   of `Scan`, `SemanticFilter`, `SemanticJoin`, and `Project` nodes.
2. Registered logical rules rewrite the plan (for example, pushing
   filters below joins).
3. The session reads Arrow batches from each registered table and
   tokenizes the document columns into memory-mapped files.
4. The model backend proposes one or more physical plans with time
   estimates. The cheapest one is selected.
5. The runner walks the physical graph in topological order. Model
   nodes run on the GPU. Relational nodes (Project, Limit,
   Recombine) run with Arrow.
6. The result is a `QueryResult` with an Arrow table and an execution
   report.

## Packages

| Package | What it does |
| --- | --- |
| `quail.sqlfront` | Parses SQL into a logical plan. |
| `quail.builder` | Builds logical plans from Python method calls. |
| `quail.logical` | Logical node types, prompt binding, and rewrite rules. |
| `quail.physical` | Typed physical nodes with ports and graph validation. |
| `quail.planner` | Cost model, join ordering, filter ordering, KV retention. |
| `quail.backends` | The `ModelBackend` protocol and the Quail, vLLM, and SGLang implementations. |
| `quail.runtime` | Session, query execution, the generic runner, token store, and results. |
| `quail.executor` | GPU code: token packing, paged KV, attention, the overlapped execution loop. |
| `quail.specs` | Model and device constants used by the planner. |
| `quail.extensions` | The per-session extension registry. |
