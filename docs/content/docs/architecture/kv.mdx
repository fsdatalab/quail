---
title: KV
---

**KV** is the attention key-value state Quail saves in GPU memory.
Reusing it avoids processing the same prefix tokens again.

## Paged KV

Quail stores KV in pages. The default page size is 16 tokens;
`DeviceSpec.page_tokens` can require a different size.

Each document references its pages. Documents that share a prefix can
reference the same pages without copying KV. A page becomes free when
no document references it.

Available pages depend on the memory left after model weights and
execution reservations. See [execution limits](/docs/architecture/optimizer#execution-limits)
and [PageArena](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/pages.py).

## KV rewind

Quail puts the document before the question. After reading an answer,
KV rewind removes the question's KV and keeps the document's KV.
The next question processes only its new tokens.

E.g., suppose a first filter keeps 1,000 reviews of 300 tokens each.
A second question of 50 tokens processes 50,000 new tokens with KV
rewind, compared with 350,000 if it processes every review again.

A join similarly reuses its anchor's KV across partners. Quail releases
document KV when no active or planned work needs it.

## Prefix sharing

Prefix sharing lets documents with identical starting tokens reuse KV.
E.g., traces saved after successive turns share the tokens of earlier turns.
The [prefix sharing rule](/docs/architecture/optimizer#prefix-sharing)
compares estimated compute savings with additional KV write costs.

### The sharing plan

Quail sorts documents by token sequence and compares adjacent documents.
It shares only complete pages and leaves each document's final token
to compute. `PrefixTree` records each document's parent and shared-token
count.

E.g., for documents containing the first 1,000, 1,400, and 1,900 tokens
of one trace, with 16-token pages:

| Document tokens | Shared tokens | New tokens |
| --- | --- | --- |
| 1,000 | 0 | 1,000 |
| 1,400 | 992 | 408 |
| 1,900 | 1,392 | 508 |

If the shared KV remains available, Quail processes 1,916 document
tokens rather than 4,300. Question tokens add work in both cases.
See [PrefixTree](https://github.com/fsdatalab/quail/blob/main/crates/quail-planner/src/inputs/prefix.rs).

### Execution

The executor admits documents in the sharing plan's order. A document
waits until its parent's shared pages are ready, then references them.

- If the parent is skipped or its KV is unavailable, the document
  computes the prefix again.
- Sharing works only within one GPU.
- With a row limit and no `ORDER BY`, sharing can change which qualifying
  rows the query returns because it changes admission order.

See [Borrowing](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/admission.py).

## KV retention

KV retention keeps document KV across separate operators. E.g., two
joins with the same anchors can reuse the anchors' KV.

`should_retain_kv` records planned reuse. The executor reserves space
for two forward passes and uses the remaining retention capacity to
keep prefixes with the highest estimated future savings per page.
When space runs out, it removes the lowest-priority retained KV.
A later operator recomputes a prefix if its KV is no longer available.

The priority includes the probability of reuse and the estimated cost
of recomputation. For hybrid models, it also accounts for saved recurrent
state. See [RetentionPolicy](https://github.com/fsdatalab/quail/blob/main/quail/common/retention.py)
and the [retention schedule](https://github.com/fsdatalab/quail/blob/main/crates/quail-planner/src/retention.rs).
