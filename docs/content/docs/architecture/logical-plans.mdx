---
title: Logical plans
---

A logical plan describes the operations a query requests and the data they
read. It does not specify GPU batches or attention settings. Quail's
logical plan is DataFusion's `LogicalPlan`: DataFusion binds a query, and
its optimizer rules place Quail's AI operators in it as `AiNode`s (see
[From SQL to a plan](#from-sql-to-a-plan)). Quail then reads each model
region's operators from that plan, and the
[optimizer](/docs/architecture/optimizer) prices the physical choices
and builds a physical plan.

This page describes the plan for contributors working on query syntax,
validation, or optimizer rules.

## Plan structure

The plan is a tree of DataFusion's operators. Each node represents an
operation, and its children are the operations that supply its inputs.
Data flows from the scans toward the root.

For example, imagine a query that classifies reviews by sentiment and
returns only negative reviews:

```sql
SELECT r.id, AI.CLASSIFY(r.body, ARRAY['positive', 'negative']) AS sentiment
FROM reviews r
WHERE sentiment = 'negative'
```

Its logical plan, as the first half of `explain()` prints it, is:

```text
Projection: r.id, sentiment
  AiNode: sentiment = ai_classify(r.body, make_array(Utf8("positive"), Utf8("negative"))), filter: sentiment = Utf8("negative")
    SubqueryAlias: r
      TableScan: reviews projection=[id, body]
```

The `AiNode` calls the model and adds the label column `sentiment`,
then keeps the rows whose label passes its filter. The filter tests the
column without calling the model again. `Projection`, `SubqueryAlias`,
and `TableScan` are DataFusion's own operators.

### AiNode

An `AiNode` (`crates/quail-datafusion/src/ai.rs`) asks the model one
AI call `f` about each row of its input `R`, and adds the call's answer
as the column `a`:

```text
AI(R; g, p, h, P, n) = π_P(Limit_n(σ_p(π_{*, f_g → a}(R))))
f_g = CASE WHEN g THEN f END
```

- `g`, the guard, says which rows the model is asked about.
- `p`, the filter, is an exact test of the input's columns and `a`.
- `h`, the hint, is the query's inexact `HINT` options, such as
  `{'selectivity': 0.4}`.
- `P`, the projection, names the added columns the node returns.
- `n`, the fetch, keeps the first rows: of all rows, or of each key.

The call's function names the node's kind: `ai_filter` (`AI.IF`),
`ai_score`, `ai_classify`, `ai_extract`, `ai_map`, or
`ai_sae_features`.

## From SQL to a plan

DataFusion parses and binds the SQL. Its analyzer then claims each
model region: the operators that call the model, with the filters and
joins below them and a LIMIT or DISTINCT that can stop the model early
(`crates/quail-datafusion/src/claim.rs`). DataFusion keeps the
operators above the region, such as GROUP BY, windows, and an ORDER BY
without a LIMIT, and moves their AI calls into the region's SELECT
list. The analyzer then lowers each AI call into one `AiNode`
(`crates/quail-datafusion/src/lower.rs`):

- An AI.IF filter is an `AiNode` whose filter is `a` and which returns
  only its input's columns. A comparison of an AI.SCORE is the same,
  with the comparison as the filter.
- An AI.IF over two tables is an `AiNode` over their join. An EXISTS
  or NOT EXISTS over a model call is an `AiNode` over the join with
  semi or anti semantics: it returns the outer rows.
- A classification, extraction, SAE feature list, or map is an
  `AiNode` that returns its answer column. A test of that column is
  first a plain DataFusion `Filter` above it.

For example, imagine a query that joins reviews to products on an
AI.IF, keeps negative reviews with another AI.IF, and keeps reviews
with more than 3 stars. DataFusion binds it with every test in one
`Filter` above the join. Lowering turns the two model tests into
`AiNode`s, still where the query wrote them:

```text
Filter: r.stars > 3
  AiNode: AI.IF('This review is negative', r.body)
    AiNode: AI.IF('Review {0} discusses product {1}', r.body, p.text)
      Inner Join: r.asin = p.asin
        TableScan: reviews as r
        TableScan: products as p
```

DataFusion's optimizer then runs the model region's rules
(`crates/quail-datafusion/src/optimize.rs`). `PlaceAiNodes` moves
each node to the tables it reads, as `PushDownFilter` does for plain
filters, and orders each table's operators the way the executor reads
them. `AbsorbIntoAiNodes` makes each test of an answer column the
filter of the `AiNode` that adds the column. `PushDownFilter` and
`OptimizeProjections` place the plain filters and prune unread
columns:

```text
AiNode: AI.IF('Review {0} discusses product {1}', r.body, p.text)
  Inner Join: r.asin = p.asin
    AiNode: AI.IF('This review is negative', r.body)
      TableScan: reviews as r, filter r.stars > 3
    TableScan: products as p
```

The DISTINCT rules run in the same place: `EliminateDistinct` removes
a DISTINCT when the SELECT list returns each table's id column, and
`PushDownDistinct` gives a one-table query's last AI.IF `AiNode` a
fetch of one row per selected key.

Finally, `derive` (`crates/quail-datafusion/src/derive.rs`) reads the
region's operators from the optimized plan. It walks the plan once,
children first and the left input before the right, and binds each AI
call's prompt and each condition in the order the query wrote them
(`binding.rs`). It places each table's terms (`terms.rs`) and writes
the region's `Operators`, with each operator where the rules left it.
The physical planner reads only these operators. A region whose shape
the operators cannot hold is refused when DataFusion claims it, and
DataFusion runs that part of the query itself.

Which implementation runs an operator, such as a classification's label
scoring method or whether a classification runs before or after a
join, is a physical choice. The [optimizer](/docs/architecture/optimizer)
prices those choices.

## Operators

`Operators` (`crates/quail-planner/src/operators.rs`) holds a region's
operators, grouped by kind, in the order the query wrote them. They
cross into Python as JSON (`Query.operators`).

| Field | Meaning |
| --- | --- |
| `scans` | Each table the region reads: its provider, alias, document column, the columns its operators read, and its regular predicates. |
| `filters` | Each table's AI.IF and AI.SCORE predicates, with their selectivity hints. |
| `joins` | Each AI join or EXISTS gate: its predicate, semantics (`full`, `exists`, or `anti`), selectivity, anchor, and the ON equalities below it. |
| `classifies`, `extracts`, `sae_features`, `maps` | Each column operator: its model call, its answer column, and whether it runs above a join. |
| `column_filters` | Each table's tests of answer columns, such as `sentiment IN ('negative')`. |
| `projection` | The SELECT list, with each extraction's struct columns. |
| `result` | ORDER BY, DISTINCT, OFFSET, and LIMIT. |
| `after_projection` | The operators on result rows above the SELECT list: each `UNNEST`, each test of more than one table's columns, and the outer SELECT list. |

A query joining three or more tables has one join for each binary
join. A classification may read one document or both documents of a
joined pair. Conditions on labels of joined pairs are unsupported.

GROUP BY, HAVING, and windows have no operator here: DataFusion runs
them on the rows a model region returns, or computes them as a region's
input. For example, a CTE that numbers a filter's survivors with
`ROW_NUMBER()`, read by a second AI filter, becomes two regions: the
first filter, then DataFusion's window, then the second filter, which
reads the window's rows as a table named by the CTE.

## Expressions

Expressions describe the values an operator reads, computes, or tests.
A value expression reads a column, accesses a struct field, or applies
a function without calling the model. A `ModelCall` describes an AI
operation.

| Expression | Value |
| --- | --- |
| `ColumnRef(alias, provider, column)` | A reference to a table column. |
| `GetField(input, field)` | A field read from a struct. |
| `ScalarFunction(function, args)` | A value computed for each row, such as text length. |
| `RegularPredicate(expression, comparison, value)` | A condition on a value, such as `length(r.body) < 40`. |
| `ModelCall(prompt, kind, labels, descriptions)` | An AI operation. The kind is `boolean`, `score`, `label`, `extract`, `features`, or `map`. |
| `Alias(expression, name)` | An expression returned under a specified column name. |

For example, `LENGTH(r.details.body)` reads the `details` column,
selects its `body` field, and computes the text length. Its expression is:

```python
ScalarFunction("length", (
    GetField(ColumnRef("r", "reviews", "details"), "body"),
))
```

The operators use these expressions as follows:

- A scan's `column` specifies the text to tokenize. It can read a
  source column directly or use a value expression, such as a struct
  field.
- A filter or join tests a boolean `ModelCall`, or a `RegularPredicate`
  that compares an `AI.SCORE` call with a threshold.
- A column filter tests a label, extracted answer, or answer position
  with a `RegularPredicate`. The condition does not call the model
  again.
- The projection's columns specify the returned values and their names.

## Prompt binding

Prompt binding converts a user's template and column references into the
layout the model receives. Quail places document text before the question
so questions about the same document can reuse its KV. KV is the key and
value vectors saved for previously processed tokens.

A template is therefore not treated as a plain string substitution.
For example, `PROMPT('Does {0} praise the acting?', r.body)` identifies
`r.body` as the document, but Quail sends that document before the question.

### Filters

A bound filter prompt contains, in order:

1. A document heading.
2. The document text.
3. The task instruction and question.
4. The answer cue.

For example, for a review with body "The acting was excellent.", this
call:

```sql
PROMPT('Does this review praise the acting? {0}', r.body)
```

uses this layout:

```text
DOCUMENT:
The acting was excellent.
You are performing a data processing task.
Evaluate TRUE or FALSE for the following question:
Does this review praise the acting?
ANSWER:
```

### Joins

The join layout places the anchor document first. The anchor is the side
whose KV remains available while Quail evaluates its partners.

The prompt contains, in order:

1. A heading and the anchor document.
2. The anchor frame, which identifies the anchor and states the question.
3. A heading and the partner document.
4. The answer cue.

The frame is fixed for all partners of an anchor. In the Quail executor,
the first partner heading is also stored with that frame, once per anchor.
Each pair then adds its partner document and answer cue. See
[Join execution](/docs/architecture/execution#joins).

### Classification

A classification prompt includes the document, question, and allowed
categories. Quail prepares both category text and letter choices when
one distinct token is available for each letter. The
[label scoring rule](/docs/architecture/optimizer#label-scoring) chooses
which version to use.

For example, suppose `reviews.body` contains "The acting was excellent."
This call supplies two sentiment categories:

```sql
AI.CLASSIFY(
    PROMPT('What sentiment does this review express? {0}', r.body),
    ARRAY['positive', 'negative'])
```

The version with letter choices has this layout before model chat
formatting is added:

```text
DOCUMENT:
The acting was excellent.

Answer with the letter of exactly one of the categories below for the following question: What sentiment does this review express?

Categories:
- A: positive
- B: negative
ANSWER:
```

The document precedes the question and category list, so another question
can reuse the same document KV. When the model selects A, Quail returns
the category text `positive` in the result column.

### Tokenization

Quail tokenizes documents separately from fixed prompt text. The executor
joins the token sequences without tokenizing the complete text again.
This lets it reuse document tokens across queries. A bound prompt is
text. The planner lowers it once per query with the session's
tokenizer (`quail.physical.lowering.lower_prompt`, which calls the Rust planner), and the
lowered prompt holds the fixed token IDs and counts the cost model and
the executor read.

For a score over one document, the input is:

```python
tokenize(before_document) + tokenize(document) + tokenize(after_document)
```

Separate tokenization can produce different tokens from tokenizing the
complete string. A token can span the boundary between fixed text and
the document, such as a space and the first word. Splitting at that
boundary prevents the combination and can change model scores.

When comparing implementations, use identical token IDs to compare model
execution. A comparison against an implementation that tokenizes the
complete string also measures the effect of tokenization.

## Logical rules

Logical rules rewrite the plan before physical planning. See the
[optimizer](/docs/architecture/optimizer#built-in-rules) for the built-in rules
