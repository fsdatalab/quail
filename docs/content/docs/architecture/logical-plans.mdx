title: Logical plans
---

A logical plan describes what a query does. Both front ends (SQL and
the Python builder) produce one through `LogicalPlanBuilder`, so
they always generate the same plan for the same query.

## The node protocol

All logical nodes implement this protocol:

```python
class LogicalNode(Protocol):
    type_name: ClassVar[str]

    def children(self) -> tuple[LogicalNode, ...]: ...
    def expressions(self) -> tuple[Any, ...]: ...
    def output_schema(self) -> tuple[ColumnRef, ...]: ...
    def validate(self) -> None: ...
    def with_children(self, children) -> LogicalNode: ...
    def with_expressions(self, expressions) -> LogicalNode: ...
    def explain_fields(self) -> dict[str, Any]: ...
```

`children()` returns the node's inputs in the plan tree. For
example, a `SemanticFilter`'s child is its `Scan`, and a `Project`'s
child is the filter or join below it. `expressions()` returns the data attached to the node, e.g., for a
`SemanticFilter` these are the `FilterPredicate` objects (each
containing a bound prompt and selectivity), and for a `Project`
these are the output column references.

Nodes are frozen dataclasses. Since they are immutable,
`with_children` and `with_expressions` return a new node with the
specified fields replaced. Logical rules (see below) use these
methods to transform the plan. `LogicalPlan.walk()` visits children
before parents.

## Node types

| Node | What it represents |
| --- | --- |
| `Scan(provider, alias, column)` | Read one document column from a registered table. |
| `SemanticFilter(input, predicates)` | One or more AI predicates over one table. |
| `SemanticJoin(inputs, predicate, semantics, selectivity, anchor)` | An AI join between two tables. `semantics` is `full`, `exists`, or `anti`. A query joining three or more tables has one `SemanticJoin` per pair. |
| `Project(input, columns, limit)` | Column projection and optional limit. Always the root. |


## Prompt binding

When the parser sees a `PROMPT(...)`, it creates a `Prompt` object
that rearranges the template into a fixed layout.

**For a filter**, `bind_prompt` produces:

1. **Preamble**: `DOCUMENT:\n`
2. **Document text**: the value of the column for this row.
3. **Question**: the instruction from the template, wrapped in an
   evaluation prompt.
4. **Answer cue**: `\nANSWER:`

<details>
<summary>Example: filter prompt layout</summary>

```text
PROMPT('Does this review mention a positive aspect?\n\n{0}', r.body)

Sent to the model as:

DOCUMENT:
A beautiful film with outstanding performances...
Evaluate TRUE or FALSE for the following question:
Does this review mention a positive aspect?
ANSWER:
```

</details>

**For a join**, `bind_join_prompt` produces:

1. **Preamble**: `DOCUMENT {0}:\n`
2. **Anchor document text** (e.g., `r.body`).
3. **Anchor frame**: a label identifying the document, followed by
   the full question. This stays in the anchor's KV.
4. **Partner label and document** (`DOCUMENT {1}:\n` + e.g.,
   `a.aspect`).
5. **Answer cue**: `\nANSWER:`

The anchor's preamble, document, and frame are computed once. For
each partner, only the partner label, partner document, and answer
cue are new.

<details>
<summary>Example: join prompt layout</summary>

```text
PROMPT('Does the review discuss this aspect?\n\n{0}\n\n{1}', r.body, a.aspect)
anchor: r

Sent to the model as:

DOCUMENT {0}:                                      ← anchor (r.body)
A beautiful film with outstanding performances...
                                                    ← anchor frame (computed once)
(The document above is DOCUMENT {0}.)
Evaluate TRUE or FALSE for the following question:
Does the review discuss this aspect?
Review: {0}
Aspect: {1}

DOCUMENT {1}:                                      ← partner (a.aspect)
the acting
ANSWER:
```

Everything above `DOCUMENT {1}:` is the anchor's KV, computed once.
Each partner adds only `DOCUMENT {1}:` onward.

</details>

In both cases, the document is placed before the question. This way,
the document's KV is the same regardless of which question follows,
which is what makes KV rewind possible.

<Callout type="info">
`PROMPT('Does {0} mention...', r.body)` is not a simple format
string where the document is inserted at `{0}`. Quail rearranges
the template so the document always comes first, even if the user
wrote the question before the placeholder.
</Callout>

Token counts and ids are stored on the `Prompt` so the planner and
executor do not re-tokenize.

## Logical rules

```python
class LogicalOptimizerRule(Protocol):
    name: str
    def rewrite(self, node, context) -> LogicalNode | None: ...
```

`apply_logical_rules` rewrites the plan recursively: it rewrites
all children first, then offers the current node to every registered
rule. All rules are applied to every node. A rule returns a
replacement node or `None` to leave it unchanged.

Quail includes one built-in logical rule:

- **[Projection pushdown](https://github.com/fsdatalab/quail/blob/main/quail/logical/rules.py)**
  (`ProjectionPushdown`): rewrites each `Scan` to load only the
  columns the query actually uses.

Other optimizations like filter ordering and join ordering currently
happen in the [planner](/docs/architecture/planning), because they
depend on cost estimates from the model and device specs. They could
also be expressed as logical rules.

Filter placement (filters above their scans, before joins) is
handled during plan construction in
[`LogicalPlanBuilder`](https://github.com/fsdatalab/quail/blob/main/quail/logical.py).

Extensions can register additional rules through
`registry.register_logical_rule(...)`.
