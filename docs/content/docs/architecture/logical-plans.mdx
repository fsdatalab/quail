---
title: Logical plans
---

Quail uses DataFusion's `LogicalPlan`, with an `AiNode` for each AI call.
DataFusion and Quail apply optimizer rules to this plan before Quail
claims model regions. GPU settings belong to each region's
[physical plan](/docs/architecture/physical-plans).

## Plan structure

The logical plan is a tree. A node reads the rows its children produce.

E.g., for a registered `reviews` table with `id` and `body` columns,
this query returns negative reviews:

```sql
SELECT r.id,
       AI.CLASSIFY(r.body, ARRAY['positive', 'negative']) AS sentiment
FROM reviews r
WHERE AI.CLASSIFY(r.body, ARRAY['positive', 'negative']) = 'negative';
```

`WHERE` cannot read the `SELECT` alias. Quail reuses the identical AI
call, so the model classifies each review once.

The optimized plan has this structure, before Quail claims the model region:

```text
Projection: id, sentiment
  AiNode: classify body; keep sentiment = 'negative'
    TableScan: reviews
```

### AiNode

An [AiNode](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/ai.rs)
stores one AI call and the operations that apply to its answer:

| Field | Meaning |
| --- | --- |
| `call` | The AI call. |
| `guard` | Ask the model only for rows where this condition is TRUE. |
| `filter` | Keep rows where this exact condition on input columns and answers is TRUE. |
| `hint` | Planning options, such as a selectivity. |
| `projection` | The added columns the node returns. |
| `fetch` | Keep the first rows globally, or the first rows for each key. |
| `semantics` | Return passing rows, or the outer rows that have a match (`Semi`) or no match (`Anti`). |

An `AI.IF` filter tests its own answer and need not return that answer
column. A classification adds a label column. An `AI.IF` join reads two
tables below the node.

## From SQL to a plan

1. **Parse and bind.** DataFusion resolves the SQL against the session's
   tables and functions.
2. **Lower AI calls.** Quail's `lower_ai_calls` analyzer rule makes one
   pass: each AI call becomes an `AiNode` below the operator that held
   it. Tests of answer columns initially remain DataFusion filters.
3. **Rewrite the plan.** DataFusion moves ordinary filters toward scans
   and removes unused columns. Quail places AI calls at the tables they
   read, absorbs tests of answers, and merges repeated AI calls.
4. **Claim model regions.** After the optimizer, the query planner
   calls `claim_model_regions`. It replaces each run of `AiNode`s with
   a `ModelRegion` node, then runs the optimizer once more over the
   operators around them. A run over one table reads the table, with
   its key. A run over anything else reads rows DataFusion computes. `EXPLAIN` shows `AiNode`s in the logical plan
   and `ModelRegionExec` in the physical plan.
5. **Read region operators.** `derive` converts each model region into
   `Operators`, which Quail's planner uses to choose a physical plan.

An `AiNode` tells DataFusion which rewrites preserve its behavior:

- Input-only filters can move below a node without a fetch.
- A fetch prevents later filters from moving below it. A filter of a
  per-key fetch's key columns can still move because it keeps or drops
  each key's rows together.
- A `LIMIT` does not move below an `AiNode`. Eligible limits become its fetch.
- Projection pruning retains every column the call or its conditions read.

DataFusion can compute a model region's input, including an aggregate
or a window in a CTE. A query with AI calls on both sides of that operation
has separate model regions.

A model region returns table IDs and AI answers. DataFusion joins other
requested table columns back on their IDs. For inputs without a primary
key, Quail adds `__quail_row`. A `SharedInput` lets the region and this
join read the same computed input without recomputing it.

DataFusion runs the remaining SQL above the region. Only `ORDER BY`
sets the result order. An eligible `LIMIT` becomes a fetch and can stop
model work early; `ORDER BY ... LIMIT` must consider the region's rows
for its top-k sort.

See [optimizer rules](/docs/architecture/optimizer#built-in-rules) for
individual rewrites and their conditions.

## Operators

[Operators](https://github.com/fsdatalab/quail/blob/main/crates/quail-planner/src/operators.rs)
describes the work inside one model region:

| Fields | Contents |
| --- | --- |
| `scans` | Tables, document columns, and input conditions. |
| `filters`, `joins` | AI filters and joins, with selectivity and join settings. |
| `classifies`, `extracts`, `sae_features`, `maps` | AI calls that add answer columns. |
| `column_filters` | Tests of those answers. |
| `projection` | Table IDs and answers the region returns. |
| `fetch`, `stop_keys` | Global or per-key row limits. |

DataFusion runs aggregates and windows outside model regions; they have
no operator in this structure.

## Expressions

Quail identifies model calls and their column references. DataFusion
computes other expressions, including tests of answers on the CPU.

An `Expression` stores an encoded DataFusion expression with its column
references and Arrow types. Each process builds its physical expression
once when it reads the plan. `expression.evaluate(rows)` then evaluates
it over Arrow columns. A column with the wrong type raises `CompileError`.

See [expressions.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/expressions.rs).

## Prompt binding

Quail converts a prompt and its document references into the model's
prompt layout. It places the document before the question so later
questions can reuse the document's KV. `PROMPT(...)` is not plain string
substitution.

### Filters

A filter prompt places the document after its heading, followed by the
question and answer cue.

E.g., for the question "Does this review praise the acting?", Quail
places the review text before the TRUE/FALSE instruction and question.

### Joins

A join puts the anchor document first. The anchor is the document whose
KV stays available while Quail evaluates its partners. A fixed question
follows the anchor; each pair then adds the partner document and answer
cue. See [Joins](/docs/architecture/execution#joins).

### Classification

A classification prompt includes the allowed labels after the document.
The [label scoring method](/docs/architecture/execution#label-scoring)
determines whether Quail scores label tokens or letters that represent
the labels. Quail returns the label text, not its letter.

### Tokenization

Quail tokenizes documents separately from fixed prompt text and joins
the token sequences. This permits reuse of document tokens across queries.

Separate tokenization prevents a token from crossing the boundary
between fixed text and a document. For set attention, `join_document_ends`
retokenizes document endings with the following prompt text. Use identical
token IDs when comparing model implementations.
