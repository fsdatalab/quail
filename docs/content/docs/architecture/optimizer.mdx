---
title: Optimizer
---

Optimizer rules rewrite DataFusion's logical plan. Quail's planner then
chooses a physical plan for each model region using estimated GPU time.
Use `explain(verbose=True)` to inspect the choices and candidate costs.

## Planning process

1. DataFusion and Quail apply logical optimizer rules, then Quail claims
   model regions.
2. Quail tokenizes each region's input documents and measures their
   lengths and shared prefixes.
3. The planner considers the operators' current placement and an
   alternative that moves eligible answer-producing operators after joins.
4. It builds a physical plan for each candidate and applies physical rules.
5. It selects the lowest estimated GPU time. Ties keep the first candidate.

See [planning.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail/src/planning.rs)
and [optimize.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-planner/src/optimize.rs).

## Cost estimates

The cost model estimates GPU computation and memory traffic. It counts:

| Count | Meaning |
| --- | --- |
| Tokens | Token positions the model processes, including repeated computation. |
| Attention pairs | Token-position pairs attention compares. |
| KV writes | Token positions whose new KV goes to GPU memory. |
| KV reads | Token positions whose saved KV the model reads. |

E.g., a second question that reuses document KV adds question tokens
and KV reads, but does not process the document tokens again.

### The roofline model

Quail converts work into floating-point operations and bytes transferred.
For each model component, it takes the larger of compute time and memory
time, then sums those component times:

```text
time_seconds = max(FLOPs / operations_per_second,
                   bytes_transferred / bytes_per_second)
```

Compute rates depend on the operation's precision and the device
specification. These estimates do not include CPU work or kernel launch
time. Compare them with measurements from `explain(analyze=True)`.

See [roofline.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-cost/src/roofline.rs)
and the [filter cost explanation](https://fsdatalab.github.io/blog/ai-filter-cost-estimates/).

### Speed of light estimate

`quail.speed_of_light_estimate` estimates ideal query time separately
from the planner's chosen schedule. It assumes one GPU at peak compute
rates and memory bandwidth, with unlimited KV capacity. By default,
each distinct document prefix needs computation once.

- Caller-supplied answers determine which rows pass filters and joins.
- The estimate counts the work to confirm those answers, not to search
  for them. Classification uses one answer readout; extraction verifies
  the reference answer in one forward pass.
- It excludes CPU work, scheduling, and kernel launch time.

Report the supplied answers and KV assumptions with the estimate.
Different model answers can change which rows a measured run evaluates.
See [sol.py](https://github.com/fsdatalab/quail/blob/main/quail/api/sol.py)
for supported operations and arguments.

## Built-in rules

DataFusion's logical rules run over the whole plan, including `AiNode`s.
Quail inserts its rules before `replace_distinct_aggregate` and runs
`claim_model_regions` last. The table lists Quail's logical rules in order;
[Rewrites by number](/docs/extending/rules#rewrites-by-number) gives their
conditions.

| Rule | Change |
| --- | --- |
| `eliminate_distinct` | Remove a redundant `DISTINCT` when selected primary keys make rows unique. |
| `place_ai_nodes` | Place AI calls at the tables they read. |
| `absorb_into_ai_nodes` | Make tests of answers the node's exact filter (R2). |
| `merge_repeated_ai_calls` | Reuse an identical earlier call's answer (R17). |
| `push_down_distinct` | Stop after one passing row per selected key (R12). |
| `push_down_limit_into_ai_nodes` | Give an eligible node a fetch, including `OFFSET` (R9–R10). |
| `push_down_projection_into_ai_nodes` | Drop unused added columns and extraction fields (R5). |
| `push_down_case_guards` | Ask only rows that need an answer in `CASE` (R6). |
| `push_down_or_guards` | Skip `AI.IF` when earlier `OR` terms already pass (R7). |
| `push_down_hint_tests` | Add an answer test as an early-rejection hint (R3). |
| `push_down_substring_prechecks` | Test documents for text an extracted answer must contain (R4). |
| `push_down_semi_join_fetch` | Stop after one passing row per semi-join key (R13). |
| `push_down_count_threshold` | Stop after enough rows pass a count threshold per key (R14). |

DataFusion supplies ordinary filter pushdown and projection pruning.
See the complete [logical rule order](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/rules.rs).

## Plan choices

### Classification placement

The planner compares the current placement with a candidate that moves
eligible classifications, extractions, and maps after joins.

- Before a join, a test of an answer can reduce join work.
- After a join, the AI call processes only surviving documents.

E.g., classifying reviews first saves join work when few labels pass.
Joining first saves classification work when few reviews match.
The planner compares candidates after applying physical rules.

### Filter order

Selectivity is the fraction of documents or pairs expected to pass a
filter. The planner uses selectivity and model costs to order filters.

The first `AI.IF` question processes the document. Later questions can
reuse its KV. The planner tries eligible first steps, orders subsequent
steps by cost per rejected document, and compares total estimated time.
Tests of a score that is already available need no model work.

Set `order="as_written"` on `session.sql()` to preserve filter order.

### Join order

The planner compares join sequences and anchor choices. An anchor's
KV can serve several partners; each partner adds its tokens to the
anchor's saved KV.

The search uses dynamic programming over plans in which each join adds
one table. It tracks joined tables and retained KV, and removes
alternatives that require no less work than another candidate.
It ranks complete plans by estimated query time, including filters.

An explicit anchor stays fixed. With `order="as_written"`, the planner
preserves join order but can choose unspecified anchors.

## Physical rules

Physical rules run on each candidate in registration order. The built-in
order is:

| Rule | Change |
| --- | --- |
| `should_push_down_limit` | Set an early stop for eligible filters. |
| `choose_classify_implementation` | Choose a label scoring method. |
| `pack_set_passes` | Group questions for set-attention execution. |
| `join_document_ends` | Retokenize document endings with the following prompt text for set attention. |
| `should_retain_kv` | Schedule KV reuse across operators. |
| `should_share_prefixes` | Enable prefix sharing when estimated savings exceed its costs. |
| `choose_attention_path` | Choose unified or tree attention. |
| `should_deduplicate` | Reuse answers for duplicate documents and restore their rows. |
| `should_stop_answers_early` | Stop maps and extractions when answer tests are decided. |

See [physical_rules.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-planner/src/physical_rules.rs)
and [Custom Rules](/docs/extending/rules).

### Stop filters after enough rows pass

`should_push_down_limit` sets a filter limit when the physical plan has
an eligible `Limit`, no join, and at most one pipeline. The executor
can stop admitting documents once enough pass.

### Execution limits

The model and GPU specifications determine:

- The **token budget**, which limits new tokens per forward pass.
  Memory reservations and kernel index limits constrain it.
- **KV capacity**, the pages available after weights and execution
  memory reservations.

See [batching](/docs/architecture/execution#pipelines-and-batches).

### KV retention

`should_retain_kv` identifies prefixes that later operators can reuse.
The executor decides which to keep within the retention capacity.
When space runs out, it removes KV with the lowest estimated future
savings per page. See [KV retention](/docs/architecture/kv#kv-retention).

### Label scoring

`choose_classify_implementation` compares supported methods using the
model and label tokens. It accounts for requested probabilities and
available document KV. See [label scoring](/docs/architecture/execution#label-scoring)
for how methods differ.

### Prefix sharing

`should_share_prefixes` compares the estimated compute savings from
shared tokens with additional KV write time. An operator that already
writes KV has no additional write cost. The rule counts complete pages
and requires exact token sequences.

The comparison excludes sorting and scheduling costs. It also excludes
recomputation when shared KV is unavailable. See [prefix sharing](/docs/architecture/kv#prefix-sharing).

### Attention path

`choose_attention_path` compares unified and tree attention for requests
that read a shared prefix. Tree attention groups those reads but adds
work to combine partial attention values. Ties choose unified attention.

The comparison uses the model's attention precision and device bandwidth.
It excludes kernel launch time. Models that do not support tree attention
use unified attention. See [attention paths](/docs/architecture/execution#attention-paths)
and [cheaper_attention_path](https://github.com/fsdatalab/quail/blob/main/crates/quail-cost/src/budgets.rs).
