---
title: Optimizer
---

The optimizer chooses how to execute a query. It converts a logical plan
(the requested operations) into a physical plan (executable operators and
settings).

- **Logical rules** change the query tree.
- **Physical rules** change the executable graph and its settings.

Logical rules run before physical rules. Either kind can involve a cost
comparison. A logical alternative is priced after its physical rules run.

See [Custom rules](/docs/extending/rules) to add a rule.

## Planning process

1. **Prepare statistics.** Read token counts, or estimate document lengths
   while tokenization runs in the background.
2. **Rewrite candidates.** Each logical rule returns a list of viable query
   trees. Projection pushdown replaces a tree; map placement keeps both
   placements. Apply later rules to every candidate and remove duplicates.
3. **Compare plans.** Build each candidate and apply its execution settings,
   including KV retention and prefix sharing. Choose the candidate with
   the lowest estimated time. Keep the first candidate on a tie.
4. **Update with exact tokens.** If the first search used estimated lengths,
   repeat it after tokenization. Exact prefixes can change the chosen plan.
5. **Execute.** Run the selected plan with its tokenized inputs.

Use `explain(verbose=True)` to see rules, settings, and candidate costs.
Use `explain(analyze=True)` to compare estimates with measured execution.

## Built-in rules

| Rule | Category | Action |
| --- | --- | --- |
| `should_eliminate_distinct` | Logical | Remove DISTINCT when returned keys are unique. |
| `should_push_down_distinct` | Logical | Stop eligible AI.IF filters after one document per key passes. |
| `should_push_down_projection` | Logical | Load only columns the query uses. |
| `should_push_down_filters` | Logical | Move eligible CPU filters before joins. |
| `should_lift_maps` | Logical | Compare classification and extraction before and after joins. |
| `should_push_down_limit` | Physical | Stop an eligible filter sequence after enough documents pass. |
| `choose_classify_implementation` | Physical | Choose a classification implementation. |
| `should_retain_kv` | Physical | Set up KV retention for compatible later operators. |
| `should_share_prefixes` | Physical | Reuse shared prefixes when estimated savings exceed extra KV writes. |
| `choose_attention_algorithm` | Physical | Choose unified or tree attention. |

Physical rules run in registration order on every candidate. Classification
selection comes before KV retention, then prefix sharing, then attention
selection. Each uses settings from the preceding rules.

## Cost estimates

The cost model estimates GPU time from computation and memory transfers.
It uses peak hardware rates and excludes CPU work and kernel launch time.
It counts:

| Count | Meaning |
| --- | --- |
| Tokens | Token positions processed, including repeated computation. |
| Attention pairs | Token pairs compared by attention. |
| KV writes | Token positions whose KV is written to GPU memory. |
| KV reads | Token positions whose saved KV is read. |

### The roofline model

Model dimensions convert these counts into floating point operations
(FLOPs) and bytes. For each part of the computation, the estimate is:

```text
time_seconds = max(FLOPs / peak_FLOPs_per_second,
                   bytes_transferred / bytes_per_second)
```

Quail adds these times across the model. See the
[filter cost model](https://fsdatalab.github.io/blog/ai-filter-cost-estimates/)
for the equations and filter-order derivation.

### Speed of light estimate

`quail.speed_of_light_estimate` estimates query time with:

- One GPU at peak compute rates and memory bandwidth.
- Unlimited KV, with each distinct document prefix computed once by default.
- No CPU, scheduling, or kernel launch time.
- Surviving rows supplied by the caller, such as saved reference answers.

For classification, it counts the question and category text but excludes
label selection overhead. The optimizer includes that overhead in its
plan costs. Report the supplied answers and KV assumptions with the
estimate. Different answers can require different work.

## Plan choices

### Classification placement

The `should_lift_maps` rule lets the planner compare classification and extraction
before and after joins. It applies to Quail's one-table operations:

- Before joins, evaluate documents that pass the table's filters. A
  condition on a classification label can reduce join work.
- After joins, evaluate only documents that survive the joins.

The planner compares both placements after applying execution settings.

### Filter order

The planner uses predicate cost and *selectivity*, the estimated fraction
of rows that pass.

For `AI.IF`, the first predicate processes the document. With KV rewind,
later predicates process only their question tokens for surviving
documents. The planner tries each predicate first, orders the rest by
cost per rejected document, and chooses the lowest estimated time.

For `AI.SCORE`, it prices each prompt at the expected survivor count and
accounts for prefix reuse. Repeated comparisons of a computed score reuse
that score column.

Set `order="as_written"` to preserve predicate order.

### Join order

The planner chooses join order and anchors. An *anchor* keeps its document
KV in GPU memory while each partner document is processed after it.

It compares estimated query time, including filters and KV reuse. Each
join adds one table to the preceding result. The search uses dynamic
programming to retain useful partial plans.

An explicit anchor is preserved. With `order="as_written"`, the planner
preserves join order and chooses only unspecified anchors.

## Execution settings

### Execution limits

- The *token budget* limits new tokens in one forward pass.
- *KV capacity* limits pages after reserving memory for model weights and
  execution.

See [Execution](/docs/architecture/execution#pipelines-and-batches) for
how these limits affect batching.

### KV retention

The planner rule sets up retention when a later operator can reuse
compatible document KV. This physical rule does not compare retention
on versus off.

The executor uses a cost-based policy to decide which KV to keep:

```text
priority = probability_of_reuse * estimated_recomputation_seconds / pages
```

When space is needed, it removes KV with the lowest priority first. See
[KV retention](/docs/architecture/kv#kv-retention) for the calculation.

### Label scoring

`choose_classify_implementation` selects the supported classification
method with the lowest estimated time. It accounts for label tokens,
requested outputs, and available document KV.

Decision 2.0 Kai uses `decision_choice` without comparing methods.
See [Label scoring](/docs/architecture/execution#label-scoring) for the
implementations.

### Prefix sharing

`should_share_prefixes` enables reuse when estimated compute savings exceed
additional KV write time:

```text
saved_seconds = shared_tokens * 2 * model.params / device.peak_flops
write_seconds = total_tokens * model.kappa / device.hbm_bw
```

`shared_tokens` counts reusable prefix tokens in complete KV pages.
`total_tokens` counts document tokens. `model.params` is the parameter
count, and `model.kappa` is KV bytes per token. The device rates are FP8
operations per second and memory bytes per second.

If the operator already writes KV, additional write time is zero.
Prefix matching needs exact token sequences. The comparison excludes
sorting, scheduling, attention, and recomputation after KV eviction.

### Attention path

`choose_attention_algorithm` compares unified and tree attention for requests that
read the same prefix. For `r` requests with `q` new tokens each and a
shared prefix of `s` tokens:

```text
unified_seconds = r * attention_seconds(q, s)
tree_seconds = attention_seconds(r * q, s) + merge_seconds
```

The merge term estimates the memory time to combine attention outputs.
For joins, the inputs come from estimated partners per anchor and token
lengths. For filters, they come from groups sharing a prefix.

Tree attention requires a supported model with at least two billion
parameters, excluding embeddings and output layers, and no extra answer
positions. Other configurations use unified attention.

The path comparison uses the FP8 compute rate for BF16 attention and
excludes kernel launch time. It can underestimate attention time.
See [Attention paths](/docs/architecture/execution#attention-paths) for
execution details.
