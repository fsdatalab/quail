title: Physical plans
---

Quail's physical plan describes one model region: its operators,
their input and output ports, and GPU settings. DataFusion's plan
contains a `ModelRegionExec` for the region and runs the SQL around it.

## Execute a review query

E.g., for a registered `reviews` table with `id` and `body` columns:

```sql
SELECT r.id,
       AI.CLASSIFY(r.body, ARRAY['positive', 'negative']) AS sentiment
FROM reviews r
WHERE AI.CLASSIFY(r.body, ARRAY['positive', 'negative']) = 'negative';
```

Quail runs the identical classification once and uses its answer in
both `SELECT` and `WHERE`.

<Mermaid chart={`flowchart TD
    scan["Scan"]
    classify["AiClassify"]
    filter["Filter"]

    scan -->|Document IDs| classify
    classify -->|Document IDs and labels| filter
    filter -->|Passing rows| rows

- `Scan` supplies document IDs: zero-based positions in the region's input,
  not the values in `reviews.id`.
- `AiClassify` asks the model for a label for each document.
- `Filter` tests the labels on the CPU and keeps negative reviews.

Quail builds the model region's rows from the surviving document IDs
and answers. It returns the source `reviews.id` values with the labels.
If the query also requests `reviews.body`, DataFusion joins that column
back on `id` above the model region.

Compatible operators pass documents to the next operator before they
finish the entire input. See [pipelining](/docs/architecture/execution#pipelines-and-batches).

## Operators above the region

DataFusion runs operations outside the model region, including:

- `ORDER BY`, `LIMIT`, and `OFFSET`.
- `DISTINCT`, aggregates, and window functions.
- `UNNEST` in the `SELECT` list.
- Remaining expressions over the region's rows.

These operations read AI answers without asking the model again.
An eligible `LIMIT` becomes the region's fetch and can stop model work
early. A top-k sort cannot use a fixed fetch to take only the first rows;
it must consider every row that can enter the top k.

`ModelRegionExec` receives inputs from DataFusion and returns Arrow
batches as the model region completes rows. If DataFusion computes an
input that the join above also reads, `SharedInputExec` computes it once.
See [streaming](/docs/architecture/execution#streaming-the-regions-rows)
and [multiple GPUs](/docs/architecture/execution#multiple-gpus).

### Runtime filters

DataFusion's top-k sorts and hash joins can send **dynamic filters** to
`ModelRegionExec`. These filters tighten as DataFusion reads rows.
Quail can skip model work for rows that cannot pass them. The operator
above the region still applies the filter.

Quail disables these hints when the model region has a fetch or per-key
stop. For other regions:

- A filter on an input column can reject a row before model execution.
- A filter on an unknown AI answer rejects a row only if every possible
  answer fails. For `AI.SCORE`, Quail uses bounds of 0 and 1.
- The executor reads updated hints before admitting documents. A hint
  saves no work if the region finishes before DataFusion can tighten it.

E.g., a top-k sort by descending score cannot reject an unscored row
merely because the current threshold is 0.9. That row could score 1.
At a threshold of 1, a secondary sort key can rule out rows that would
lose even if they score 1.

See [RegionHint](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/region_hint.rs).
Without `ORDER BY`, rows can arrive in any order.

## Inspect the plan

Call `query.explain()` to inspect operators and estimated work without
running model inference. Use `verbose=True` to include execution settings
and candidate costs.

## Editing a plan

`query.plan()` returns a physical plan. Each edit returns a new plan;
run it with `query.run(plan=edited)`. An edited plan applies to a query
with one model region.

See [Editing physical plans](/docs/user-guide/editing-plans) for an example
or [Custom operators](/docs/extending/operators) to implement a node.
