---
title: Physical plans
---

A physical plan specifies which operators execute a query, what data each
operator receives, and what data it produces. An operator performs one
part of the query, such as classifying reviews or selecting result columns.
SQL functions describe what a query requests. Physical operators
specify how Quail executes that work.
The plan also records execution settings, such as the
[attention path](/docs/architecture/execution#attention-paths) used by a model operator.

The [optimizer](/docs/architecture/optimizer) builds the physical plan
from a logical plan. The logical plan describes the requested operations.
The physical plan specifies how Quail executes them.

## Execute a review query

For example, imagine a `reviews` table with an `id` column for review
identifiers and a `body` column for review text. This query classifies
each review as positive or negative and returns only negative reviews:

```sql
SELECT r.id,
       AI.CLASSIFY(
           PROMPT('What sentiment does this review express? {0}', r.body),
           ARRAY['positive', 'negative']) AS sentiment
FROM reviews r
WHERE AI.CLASSIFY(
    PROMPT('What sentiment does this review express? {0}', r.body),
    ARRAY['positive', 'negative']) IN ('negative');
```

Before execution, Quail tokenizes the review text. During execution,
it identifies each review by its row position in the input table,
starting at zero. Quail calls this position a document ID. It is separate
from the value in `reviews.id`.

Quail uses three operators to execute this query. Each box
represents an operator. Each arrow shows the data passed between operators.

<Mermaid chart={`flowchart TD
    scan["Scan"]
    classify["AiClassify"]
    filter["Filter"]
    rows["region rows"]
    scan -->|Document IDs| classify
    classify -->|Document IDs and labels| filter
    filter -->|Document IDs and labels of negative reviews| rows
`} />

1. **Scan** returns the document IDs for the `reviews` input.
2. **AiClassify** receives these IDs and uses the model to classify the
   corresponding reviews. It produces a table of document IDs and labels.
3. **Filter** reads that table and keeps the document IDs whose label is
   `negative`. This comparison runs on the CPU.

The region's rows are built from the operators' outputs, not by an
operator: one row per surviving document, or per surviving tuple of an
AI join, with the id column of each table, here `reviews.id`, and each
answer the SELECT list reads, here the label. Rust joins the surviving
documents, each full join's true pairs, and each answer table on
document IDs (`quail::results::region_rows`). A query that also reads
another column of `reviews`, such as `title`, gets it from DataFusion,
which joins `reviews` back on `id` above the region.

The `SELECT` and `WHERE` expressions use the same classification output.
Quail does not classify each review again for the `SELECT` expression.

The arrows show which inputs each operator needs. Compatible operators
can pass batches to each other before they finish processing all rows.
See [Execution](/docs/architecture/execution#pipelines-and-batches) for
how Quail groups and schedules these operators.

## Operators above the region

DataFusion runs the relational operators on the rows a model region
returns, so they are not in Quail's physical plan: ORDER BY, LIMIT and
OFFSET, DISTINCT, GROUP BY, [window functions](/docs/user-guide/sql/sql-functions#window-functions),
each `UNNEST`, each test of more than one table's columns, and the
SELECT list's expressions. They reuse the region's AI outputs and do not
call the model again.

A LIMIT stops the model early only when it becomes the region's fetch:
with no ORDER BY, DISTINCT, or other row filter between the LIMIT and
the AI operator it reads. An ORDER BY with a LIMIT is a top-k sort,
DataFusion's `SortExec` with a fetch, over every row the region returns.

For example, `explain()` of a query that scores filtered sales calls
and keeps the top 25 starts with DataFusion's physical plan, then the
region's:

```text
DataFusion:
SortExec: TopK(fetch=25), expr=[commit_score@1 DESC NULLS LAST, id@0 ASC NULLS LAST], preserve_partitioning=[false]
  ModelRegionExec
    FilterExec: deal_stage@1 = Negotiation, projection=[id@0, transcript@2]
      DataSourceExec: partitions=4, partition_sizes=[1, 1, 1, 0]
```

`ModelRegionExec` runs the region. Its inputs below it are the rows
DataFusion computes for it, here the calls in the Negotiation stage.
It returns one stream of the region's rows, which DataFusion reads
while the region runs: each forward pass's finished rows when the
region's last operator is a filter, score, or classification, and
otherwise its rows once that operator finishes. With several GPUs, the
coordinator merges each GPU's outputs first and sends the rows at the
end.

When the SELECT list reads a table's columns besides its id,
DataFusion joins the table back above the region. For example, a query
that returns each review's `stars` beside a classification:

```text
DataFusion:
HashJoinExec: mode=CollectLeft, join_type=Inner, on=[(__quail_key_r@0, id@0)], projection=[id@2, stars@1, kind@3]
  CoalescePartitionsExec
    ProjectionExec: expr=[id@0 as __quail_key_r, stars@1 as stars]
      DataSourceExec: partitions=4, partition_sizes=[1, 1, 1, 0]
  RepartitionExec: partitioning=RoundRobinBatch(4), input_partitions=1
    ModelRegionExec
```

DataFusion plans the join with its default settings: it splits the
region's rows across partitions and picks the join's build side from
the statistics it has. When DataFusion computes a table's rows for the
region, the join reads them through the same `SharedInputExec` as the
region, so they are computed once.

Only an ORDER BY sets the order of the result rows. Without one, the
rows can come back in any order, and a LIMIT returns any of the rows
that qualify.

## Inspect the plan

Call `query.explain()` to inspect the plan without running model inference.
The output shows the operators, their execution settings, and estimated work.

## Editing a plan

Call `query.plan()` to get a plan that you can edit before execution.
Each edit returns a new plan. You can execute it with
`query.run(plan=edited)`.

See [Editing physical plans](/docs/user-guide/editing-plans) for a complete
example that inspects a plan, inserts an operator, and removes it.

To implement an operator, see
[Custom operators](/docs/extending/operators). That guide explains how
operator classes declare their inputs, outputs, and execution code.
