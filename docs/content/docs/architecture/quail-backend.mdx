---
title: The Quail backend
---

`QuailBackend` is the default model backend. It owns the scheduler,
the paged KV arena, and the model calls.

## Planning

The planner builds a physical plan from the model spec, device spec,
and per-document token counts. It decides:

- The filter order per table.
- The anchor of each join.
- The forward pass token budget and KV arena budget, based on GPU
  memory remaining after the model weights.
- Which document KV to retain across operator boundaries.
- Document shards per GPU when using multiple GPUs.

A document that cannot fit in one forward pass is refused at plan
time.

## Filters

The filter loop fills each forward pass by two budgets: tokens and
KV pages.

- **Pipelining.** A document that passes one predicate enters the
  next forward pass with its next predicate immediately.
- **Token-based admission.** A forward pass is full when its token
  budget or the arena's free pages are exhausted.
- **KV rewind.** The document's KV from the first predicate stays
  in the arena. Later predicates add only the question suffix tokens.

KV pages are freed when a document fails a predicate or finishes its
last one.

## Joins

A join packs one anchor document's prefix per forward pass and
evaluates multiple partner documents against it. All partners in one
forward pass share the anchor's KV through paged cross-attention.

- **Gating.** Between join stages, anchors with no passing pair are
  dropped and their pages freed.
- **Streaming.** The first join group's anchor filter does not finish
  before the join starts. Each document that passes its last filter
  keeps its KV and enters the join immediately.
- **Retention.** Later join groups reuse retained KV for their
  anchors. If KV was evicted, the document is reprocessed.

The planner uses dynamic programming (Selinger-style) to choose the
join order and anchors before inference. Filter survival is estimated
from the selectivities you provide.

## The executor

`quail.executor` holds the GPU code:

| File | What it does |
| --- | --- |
| `pack.py` | Admission logic for filters and joins. |
| `arena.py` | The paged KV arena and page accounting. |
| `attention.py` | The forward pass with two-call attention and log-sum-exp merge. |
| `loop.py` | The overlapped filter and join execution loops. |
| `model.py` | Weight loading through vLLM's loader. |

The fused kernels assume the Qwen3 architecture: QK-norm before
RoPE, gated SiLU MLP, FP8 block-quantized weights.

## Multiple GPUs

With multiple GPUs, each GPU has its own CUDA context and KV arena.
A coordinator process sends work over pipes.

- **Filters**: each GPU filters its own shard of documents.
- **Joins**: anchors stay on the GPU that filtered them. Every GPU
  receives every surviving partner document.
- **Between join groups**: the coordinator prunes survivors and
  re-partitions the next anchor's documents.
