---
title: The request backends
---

Three comparison backends implement the same `ModelBackend` protocol
as the Quail backend. They exist for benchmarking. They accept the
same queries and return the same result format, so switching between
them is one line: `EngineConfig(backend="stock_vllm")`.

| Backend | How filters run | How joins run |
| --- | --- | --- |
| `stock_vllm` | One stage at a time. Stage 2 waits for all of stage 1. | One request per pair, anchor-major order. |
| `pipelined_vllm` | Next stage submitted as soon as a document passes. | Same as stock. |
| `pipelined_sglang` | Next stage submitted on each completion via SGLang's async API. | One request per pair, partner-major order. |

None of them use Quail's executor or KV arena.

## Planning

Each backend produces a single `RequestExecution` physical node
containing the tokenized prompt parts for every filter and join
stage. Filter ordering uses the same rule as the Quail backend.

## Execution

All three are instances of one `RequestBackend` class, configured
with an engine adapter (`VLLMEngine` or `SGLangEngine`) and
submission strategies. The engine boots once per container and
provides `generate`, `reset_prefix_cache`, and `run_filter_chain`.

Stock vLLM and pipelined vLLM share one loaded vLLM model when they
run in the same process. SGLang needs its own container because
vLLM and SGLang require incompatible versions of `apache-tvm-ffi`.
