---
title: In-process execution
description: How a query runs inside its session's process.
---

`Query.run()` calls `quail.runtime.execute.execute_query` with the
existing query. The same path runs on a GPU host or inside a Modal GPU function.
Tests can supply a fake physical executor to exercise the query without a GPU.

## The Modal wrapper

The calling application defines its image, GPU function, and optional volumes
using the Modal SDK. It creates a normal session, registers sources and
extensions, runs queries, and collects or saves results.
See [Running on Modal](/docs/user-guide/compute) for a complete example.
Modal controls GPU allocation, secrets, timeouts, and container lifetime.
The application chooses file paths and commits its volumes explicitly.
Quail has no Modal integration module or required mounts.

## One query

1. The executor checks that the process has a CUDA GPU. Library cache
   defaults and the caller's environment settings remain unchanged.
2. The query plans from the session's registered sources. Document tokenization
   runs in the background. Existing planning and token files are reused.
3. The selected backend can load its model from the plan before tokenization
   finishes. The executor waits for tokens before constructing physical inputs.
4. The executor validates the physical graph, backend, codecs, and runtimes.
   It calls `backend.execute_request(context)` with the session's registry
   and per-process model state.
5. The Quail backend loads weights and warms kernels on first use. Several GPUs
   use one model copy per GPU through the backend's existing child processes.
6. Model outputs return as Arrow tables keyed by port. The generic runner
   finishes `Recombine`, `Project`, and `Limit` with those outputs supplied.
7. The query returns a `QueryResult` with its executed plan and node metrics.
   The engine returns its report without writing it to storage.

## Lifetime

The backend keeps loaded models in process state for later queries.
A session keeps token files for reuse across its queries. Collect or save rows
before closing the session, because their projection may still read those files.

`Session.close()` waits for background tokenization and closes temporary
files. It does not unload the model or change Modal container settings.
Separate Modal invocations may use different containers.

## Limits

- Temporary token and value files must fit on the process's local disk.
  Very large sources need query partitioning or persistent token storage.
- Query execution supports at most eight GPUs in one host or container.
  Execution across several hosts or containers is not implemented.
