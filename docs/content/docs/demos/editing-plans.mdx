---
title: Editing physical plans
---

Inspect and edit a physical plan before running it. The example adds
a barrier and a Python function between operators. No GPU is needed
to plan or edit the query.

The full example is in
[`demos/plan_walkthrough.py`][demoscript].

## Run the example

```bash
uv run python demos/plan_walkthrough.py
```

## The query

The example uses three claims and three evidence passages from a
[FEVER](https://fever.ai/) query in
[QUAIL-B](/docs/contributing/benchmark). An AI filter selects claims
about a person. An AI join tests whether a passage supports a claim.
The page URL determines which claim and passage pairs are tested.

The query uses the [Python builder API](/docs/user-guide/python-api):

```python
from quail import col, prompt

PERSON = "Is the claim in DOCUMENT {0} about a person?"
SUPPORT = (
    "Does the passage in DOCUMENT {1} support the claim in "
    "DOCUMENT {0}?"
)

query = (
    session.docs("claims").alias("c")
    .ai_if(prompt(PERSON, col("c.claim")))
    .join(
        session.docs("evidence").alias("e"),
        on=col("c.evidence_wiki_url") == col("e.id"),
    )
    .ai_if(prompt(SUPPORT, col("c.claim"), col("e.text")))
    .select("c.id", "e.id")
)
```

The `.join(..., on=...)` restricts which combinations of claims and
evidence the model evaluates.

## Inspect the plan

`query.explain()` shows the physical plan:

<Callout type="info">
Time estimates assume peak GPU throughput and exclude host overhead.
Use `explain(analyze=True)` on a GPU to compare estimates with measured
execution time.
</Callout>

```text
physical: backend=quail, model=qwen3-4b-fp8, workers=1
  KV=bf16, chunk budget=110,376 tokens

                                                 est. rows  est. pass  est. time
  Project: c.id, e.id
    AiJoin: anchor=c                                                     4.29 ms
      KV: anchor=streamed from its filter, retain after join=no
      join 1 full (c, e) over hash_join:c-e            0.6       20%*
      AiFilter: c                                      0.6               2.39 ms
        survivors stream into the join with KV pinned
        predicate 1                                      3       20%*
        Scan claims as c
          tokens=306, mean_doc_tokens=102
      Scan evidence as e
        tokens=4,506, mean_doc_tokens=1,502
      HashJoin: c.evidence_wiki_url = e.id
```

"survivors stream into the join with KV pinned" means: when a claim
passes the filter, the engine keeps its KV in GPU memory and
immediately starts evaluating evidence passages against it. The filter
and the join overlap.

## Insert a barrier

A `Barrier` collects all filter survivors before starting the join:

```python
from quail.physical import Barrier

plan = query.plan()
edited = plan.insert(
    Barrier(node_id="barrier:c", next_anchor="c", aliases=("c",)),
    between=("ai_filter:c", "ai_join:c"),
)
```

The barrier separates the filter and join into two pipelines.
The filter sets `keep_kv=True` to retain surviving documents' KV
until the join starts:

```text
      Barrier: next_anchor=c
        AiFilter: c
          retain KV for later joins
```

Removing the barrier restores the original plan:

```python
assert edited.remove("barrier:c") == plan
```

Only `Barrier`, `Foreign`, and `Exchange` nodes can be removed.
Removing `Foreign` also removes its Python function and can change
the results. Removing a model node raises an error:

```text
PlanEditError: 'ai_filter:c' is a AiFilter; removing it would change
what the query means
```

## Insert a user function

`apply()` inserts a Python function between operators:

```python
query.apply(fn, columns=(), *, name=None, ids=None, kind="per_batch")
```

- `fn` receives a `dict[str, pa.Table]` keyed by alias. Each table
  has the alias's row indices plus the columns you listed in `columns`.
- `columns` is a list of `col(...)` references that your function
  needs to read.
- After a `.join()`, `fn` returns a table with both alias columns
  (e.g. `c` and `e`) selecting which combinations the next AI
  predicate evaluates.
- Without a preceding `.join()`, `fn` returns the ids to keep.
- `kind="per_batch"` can run as documents pass through a pipeline.
  Outside a pipeline, it receives all input rows. `kind="barrier"`
  runs once after all surviving rows are available.

An Arrow join in the function can select candidate pairs by URL:

```python
def match_by_url(tables):
    """Match each claim to the evidence page its URL names."""
    return tables["c"].join(
        tables["e"],
        keys=["evidence_wiki_url"],
        right_keys=["id"],
        join_type="inner",
    ).select(["c", "e"])

query = (
    session.docs("claims").alias("c")
    .ai_if(prompt(PERSON, col("c.claim")))
    .join(session.docs("evidence").alias("e"))
    .apply(match_by_url, columns=[col("c.evidence_wiki_url"),
                                  col("e.id")])
    .ai_if(prompt(SUPPORT, col("c.claim"), col("e.text")))
    .select("c.id", "e.id")
)
```

In the physical plan, `match_by_url` appears as a `Foreign` node:

```text
      Foreign: match_by_url (per_batch, pairs) on c, e
        columns: c.evidence_wiki_url, e.id
```
