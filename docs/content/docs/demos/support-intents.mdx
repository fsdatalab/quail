---
title: Explore topics in support conversations
description: Inspect sparse features in customer requests.
---

Inspect support requests from
[τ-bench](https://github.com/sierra-research/tau-bench) for possible topics
without a predefined list of labels.

<Callout type="info">
This analysis is experimental. A feature can combine unrelated topics;
inspect the requests before assigning a meaning to it.
</Callout>

## Sparse feature vectors

`AI.SAE_FEATURES` returns a sparse feature vector for each request.
Each entry has a feature ID and an activation strength. Requests use
the same feature IDs, but the model does not give them topic labels.

## Get features for each request

Run the examples from the repository root after
[development setup](/docs/contributing). The QUAIL-B `support_traces`
table contains each conversation's opening `request` and its `task_id`.
Several conversations can share a customer task.

E.g., get features on one H100 SXM:

```python
import quail
from quail_b import load_table

conversations = load_table("support_traces", scale_factor=1.0)
config = quail.EngineConfig(model="qwen3.5-2b-sae-bf16", device="h100-sxm")

with quail.Session(config) as session:
    session.register("conversations", quail.DocumentProvider.from_table(
        conversations, id_col="id"))
    features = session.sql(r"""
        SELECT x.id AS id, x.intent['feature'] AS feature,
               x.intent['strength'] AS strength
        FROM (SELECT t.id,
                     UNNEST(AI.SAE_FEATURES(
                         PROMPT('{0}\n\nWhat is the customer asking for?', t.request),
                         {'pooling': 'last'})) AS intent
              FROM conversations t) x
    """).collect()
```

This model returns up to 100 positive feature values per request.
`UNNEST` expands the list into rows:

| Column | Meaning |
| --- | --- |
| `id` | Conversation ID |
| `feature` | Feature ID |
| `strength` | Activation strength |

## Find common features and inspect their requests

The demo weights features by frequency and keeps three per request.
For each common feature, it selects up to three requests from different
customer tasks.

E.g., continue with the tables above:

```python
from demos.support_intents import analyze

report = analyze(conversations, features)
for feature in report["intents"]:
    print(feature["feature"], feature["requests"], feature["examples"])
```

## Retrieve more requests for a topic

Use the feature table to retrieve requests without another model run.
E.g., inspect the strongest activations for a feature from the report:

```python
import pyarrow.compute as pc

feature_id = report["intents"][0]["feature"]
matches = features.filter(pc.equal(features["feature"], feature_id))
matches = matches.sort_by([("strength", "descending")])
positions = pc.index_in(matches["id"], value_set=conversations["id"])
requests = conversations.take(positions).select(["id", "request"])
print(requests.slice(0, 10).to_pylist())
```

## Run the demo

The complete script is
[`demos/support_intents.py`](https://github.com/fsdatalab/quail/blob/main/demos/support_intents.py).
E.g., run its Modal wrapper on one H100:

```bash
uv run modal run --detach demos/support_intents_modal.py \
    2>&1 | tee /tmp/quail-support-intents.log
```

The wrapper prints the Modal function call ID and saves these files under
`demos/support-intents/<run-id>/` on the `quail-results` volume:

- `features.parquet`: the feature table.
- `report.json`: feature counts and example requests.
