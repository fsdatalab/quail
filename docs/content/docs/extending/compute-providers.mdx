---
title: Compute providers
description: Running the same logical query somewhere other than Modal.
---

A compute provider decides where a query runs. It receives the
logical request and returns the result. The in-process provider is the
default, but the interface is two methods:

```python
class ComputeProvider(Protocol):
    def execute(self, request: QueryRequest) -> QueryResult: ...
    def close(self) -> None: ...
```

```python
@dataclass(frozen=True)
class QueryRequest:
    logical_plan: LogicalPlan
    providers: Mapping[str, TableProvider]
    config: EngineConfig
    device: str
    order: str | None = None
    registry: ExtensionRegistry = field(default_factory=ExtensionRegistry.with_built_ins)
```

Pass yours to the session:

```python
session = quail.Session(compute_provider=MyProvider())
```

## What a provider has to do

1. Move the data. For each provider in `request.providers`, either
   send `remote_source()` if the worker can open it, or scan the
   needed columns and send them. `quail.runtime.compute._modal_request`
   shows the column selection: the id column, every scanned document
   column, and every projected column.
2. Run the query in the worker. `quail.runtime.local.execute_query_request`
   is the in-process entry point that tokenizes, plans, validates,
   dispatches to the backend, and finishes the graph. A custom
   provider can call it in whatever process it controls. Pass the request's
   registry through preparation and execution in that process.
3. Return a `QueryResult`. `QueryResult.from_table(table, report)`
   wraps a materialized Arrow table.

## The in-process provider

`quail.InProcessComputeProvider` runs the request in the current
process and is what `Session()` uses when no provider is passed. The
process needs a CUDA GPU and the backend's runtime package; vLLM is
installed with the package on Linux. Without a GPU, `execute` raises a
`RuntimeError` that names `ModalComputeProvider`. The benchmark runner
inside a Modal function uses this provider too, since it already runs
where the GPUs are.

It takes an optional `physical_executor` callable that replaces the
backend dispatch and skips the GPU check, which is how the CPU tests
run the whole path without a GPU. The QUAIL-B runner uses this provider, so the benchmark
and production build the same result objects.

## Modal specifics that are not part of the protocol

`ModalComputeProvider` also builds the worker image with the
extension packages, chooses the function for the GPU count, keeps one
container warm while the provider is open, prints the function call
id, and saves a run record on the results volume. None of that is
required of another provider.

Set `local_python_sources=(...)` and `pip_packages=(...)` on
`ModalComputeProvider` to copy extension code and install dependencies.
The registry contains no package configuration.

`initialize_worker=callback` runs `callback(registry)` once per query in
the Modal process, before sources are opened. Use it for registrations
that need to create objects inside that process.

Modal receives the registry as a Python object. It returns a materialized
`QueryResult` with its executed plan and node metrics attached. No extension
manifest is involved.
