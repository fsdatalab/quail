---
title: Compute providers
description: Running the same logical query somewhere other than Modal.
---

A compute provider decides where a query runs. It receives the
logical request and returns the result. Modal is the default, but the
interface is two methods:

```python
class ComputeProvider(Protocol):
    def execute(self, request: QueryRequest) -> QueryResult: ...
    def close(self) -> None: ...
```

```python
@dataclass(frozen=True)
class QueryRequest:
    logical_plan: LogicalPlan
    providers: Mapping[str, TableProvider]
    config: EngineConfig
    device: str
    order: str | None = None
    extensions: tuple[ExtensionPackage, ...] = ()
```

Pass yours to the session:

```python
session = quail.Session(compute_provider=MyProvider())
```

## What a provider has to do

1. Move the data. For each provider in `request.providers`, either
   send `remote_source()` if the worker can open it, or scan the
   needed columns and send them. `quail.runtime.compute._modal_request`
   shows the column selection: the id column, every scanned document
   column, and every projected column.
2. Run the query in the worker. `quail.runtime.worker.execute_worker_query`
   is the in-process entry point that tokenizes, plans, validates,
   dispatches to the backend, and finishes the graph. A custom
   provider can call it in whatever process it controls, as the CPU
   tests do.
3. Return a `QueryResult`. `QueryResult.from_table(table, report)`
   wraps a materialized Arrow table.

## A local provider for tests

The CPU test suite fakes the GPU and runs the whole path in process.
A provider that does the same is a few lines:

```python
from quail.runtime.worker import execute_worker_query


class InProcessProvider:
    def execute(self, request):
        return execute_worker_query(request)

    def close(self):
        pass
```

Without a GPU this only works when the selected backend does not need
one, for example the `LocalFilterBackend` from the physical node tests.

## Modal specifics that are not part of the protocol

`ModalComputeProvider` also builds the worker image with the
extension packages, chooses the function for the GPU count, keeps one
container warm while the provider is open, prints the function call
id, and saves a run record on the results volume. None of that is
required of another provider.
