title: Custom models and GPUs
---

Register a `ModelSpec` or `DeviceSpec` to add a model or GPU specification.
The specification supplies cost estimates and execution limits; it does
not add execution support. See [supported configurations](/docs/user-guide/models).

## Model specifications

### Register a Qwen3 checkpoint

`qwen3_spec` reads model dimensions and the weight format from `config.json`.
It accepts BF16 weights or FP8 weights in 128-by-128 blocks. It rejects
Qwen3 configurations with sliding window attention.

E.g., register a complete checkpoint at `/models/review-qwen3-4b`:

```python
import quail
from quail.specs import qwen3_spec

spec = qwen3_spec(
    name="review-qwen3-4b",
    hf_name="/models/review-qwen3-4b",
    config="/models/review-qwen3-4b/config.json",
)
registry = quail.ExtensionRegistry.with_built_ins()
registry.register_model(spec)
config = quail.EngineConfig(model=spec.name, device="h100-sxm")
with quail.Session(config=config, registry=registry) as session:
    pass
```

The checkpoint directory must include tokenizer files and be available
in the process that loads the model. This example creates a session
without running a query.

For a Hugging Face checkpoint, set `hf_name` to its repository ID and
`revision` to its commit ID. Omit `config` to download `config.json`.
Pass extra `ModelSpec` fields to override derived values, such as a
measured `w_mem_bytes`. See [qwen3_spec](https://github.com/fsdatalab/quail/blob/main/quail/specs/qwen3.py).

### Other architectures

Define a [ModelSpec](https://github.com/fsdatalab/quail/blob/main/quail/specs/base.py)
that matches the checkpoint and register it with `register_model(spec)`.
If Quail has no forward pass for its `arch`, implement one as described
[below](#implementing-a-model-architecture).

## GPU specifications

`DeviceSpec` describes one GPU. Use dense compute rates, without
structured sparsity.

| Field | Value and unit |
| --- | --- |
| `name` | The value of `EngineConfig.device`. |
| `mem_bytes` | GPU memory capacity in bytes. |
| `hbm_bw` | GPU memory bandwidth in bytes per second. |
| `fp8_flops` | Peak dense FP8 operations per second. |
| `bf16_flops` | Peak dense BF16 operations per second. |

Register the specification with `registry.register_device(spec)`.
The backend must also accept the device and provide compatible kernels.
See the [H100 specification](https://github.com/fsdatalab/quail/blob/main/quail/specs/data/devices/h100-sxm.toml)
and [backend support checks](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/backend.py).

## Implementing a model architecture

Quail's default loader uses vLLM. Quail selects a `ModelPipeline` by
`ModelSpec.arch`. To add an architecture:

1. Check that the [loader](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/model_loading.py)
   can load the checkpoint and access its `lm_head`.
2. Define the `ModelSpec`, including its KV shapes and prompt format.
3. Implement `ModelPipeline` in `quail/backends/quail/executor/models/`.
   Its constructor receives `(model, arena, *, spec)`.
   `forward_chunk()` returns hidden states for `chunk.final_indices`
   after final normalization. An SAE configuration instead returns
   the residual stream without final normalization.
4. Set the attention and memory requirements defined by
   [ModelPipeline](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/models/base.py).
   Implement its kernel preparation methods when required.
5. Add the class to `PIPELINES` in that directory's `__init__.py`.
   Use its key for `ModelSpec.arch`.

The executor owns KV allocation and release. The forward pass computes
with the supplied pages. Check reused kernels against the architecture's
operations and number formats.

Compare the forward pass with the model's reference implementation on a
GPU. Use identical token IDs and positions. Check fresh inputs and
inputs that reuse KV.
