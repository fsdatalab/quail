---
title: Custom models and GPUs
---

Every planning decision in Quail comes from a `ModelSpec` and a
`DeviceSpec`. Adding support for a new model or GPU means registering
a spec.

## ModelSpec

A `ModelSpec` describes the model architecture. Every field except
`params` and `w_mem_bytes` comes from the checkpoint's `config.json`.

```python
from quail.specs import ModelSpec

MY_MODEL = ModelSpec(
    name="qwen3-4b-fp8",
    params=4.0e9,
    layers=36,
    hidden=2560,
    n_q=32,
    n_kv=8,
    d_head=128,
    ffn_width=19456,
    w_bytes=1.0,
    hf_name="Qwen/Qwen3-4B-FP8",
    revision="96b30dc...",
    vocab=151936,
    tied_head=True,
)
```

Source:
[quail/specs/base.py](https://github.com/fsdatalab/quail/blob/main/quail/specs/base.py).

`revision` pins the Hugging Face hub commit so the worker resolves
weights from cache without network round trips.

The planner uses derived properties: `kappa` (KV bytes per token),
`W_resident` (weight bytes on GPU after discarding the full output
head), and `act_per_token` (activation memory per token).

### Qwen3 checkpoints

`qwen3_spec` builds the `ModelSpec` of any Qwen3 checkpoint from its
`config.json`. It reads the layer count, the hidden size, the head
counts and head dim, the MLP width, the vocabulary, whether the
output head is tied to the embedding, and the weight precision. For
example, imagine registering a Qwen3 fine-tune that Quail does not
ship a spec for:

```python
import quail
from quail.specs import qwen3_spec

spec = qwen3_spec(
    "my-qwen3-1.7b",                 # the model= value
    "Org/My-Qwen3-1.7B",             # the Hugging Face repo
    revision="<commit hash>",
)
registry = quail.ExtensionRegistry.with_built_ins()
registry.register_model(spec)
session = quail.Session(
    quail.EngineConfig(model="my-qwen3-1.7b", device="h100-sxm"),
    registry=registry,
)
```

Source:
[quail/specs/qwen3.py](https://github.com/fsdatalab/quail/blob/main/quail/specs/qwen3.py).

The checkpoint needs bf16 weights, or fp8 weights in 128 x 128
blocks (the layout DeepGEMM reads). `qwen3_spec` raises `ValueError`
for any other weight format, for a sliding attention window, and for
a model type other than `qwen3`. Keyword arguments set any other
`ModelSpec` field, such as a measured `w_mem_bytes`.

`params` counts the attention and MLP projections and the norms. It
leaves out the embedding table and the output head, because a query
reads only the output head's TRUE and FALSE rows.

### Which models work with a spec alone

The Quail executor's GPU kernels are written for the Qwen3
architecture (QK-norm, gated SiLU MLP). FP8 checkpoints run DeepGEMM
and both attention paths; bf16 checkpoints run cuBLAS and unified
attention.

A model with a different architecture (different attention layout,
different activation function, different weight format) would need
new GPU kernels in
[quail/backends/quail/executor/](https://github.com/fsdatalab/quail/tree/main/quail/backends/quail/executor),
or could run through a [custom inference engine](/docs/extending/backends)
like vLLM or SGLang, which handle model loading independently.

## DeviceSpec

A `DeviceSpec` describes the GPU hardware.

```python
from quail.specs import DeviceSpec

MY_DEVICE = DeviceSpec(
    name="h100-sxm",
    mem_bytes=80e9,
    hbm_bw=3.35e12,
    peak_flops=1.979e15,
    bf16_flops=0.989e15,
)
```

Source:
[quail/specs/base.py](https://github.com/fsdatalab/quail/blob/main/quail/specs/base.py).

All values are per GPU. `peak_flops` is the dense FP8 rate.
The [H100 datasheet](https://resources.nvidia.com/en-us-tensor-core)
quotes rates with 2:1 structured sparsity; divide by 2 for the dense
rate Quail uses. `bf16_flops` is the dense BF16 rate, used for
attention (FlashAttention runs in BF16).

## Registration

```python
registry = quail.ExtensionRegistry.with_built_ins()
registry.register_model(MY_MODEL)
registry.register_device(MY_DEVICE)
```

Then use the registered names in `EngineConfig`:

```python
config = quail.EngineConfig(
    model="my-model",
    device="my-device",
    gpus=1,
)
```
