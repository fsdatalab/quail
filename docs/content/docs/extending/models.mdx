---
title: Custom models and GPUs
---

Quail uses model and GPU specifications to estimate query time and set
execution limits. The inference backend must also support the model
architecture and GPU you select. See
[Supported models and GPUs](/docs/user-guide/models) for the included
configurations.

## Model specifications

A *model specification* records a checkpoint, model dimensions, and
numerical formats. Quail represents it with `ModelSpec`.

### Register a Qwen3 checkpoint

Use `qwen3_spec` to read the model dimensions and weight format from the
checkpoint's `config.json`.

For example, imagine that you have fine tuned Qwen3 4B and saved a complete
checkpoint in `/models/review-qwen3-4b`. The directory contains the weights,
model configuration, and tokenizer files.

```python
import quail
from quail.specs import qwen3_spec

spec = qwen3_spec(
    name="review-qwen3-4b",
    hf_name="/models/review-qwen3-4b",
    config="/models/review-qwen3-4b/config.json",
)
registry = quail.ExtensionRegistry.with_built_ins()
registry.register_model(spec)
config = quail.EngineConfig(model=spec.name, device="h100-sxm")
session = quail.Session(config=config, registry=registry)
session.close()
```

The example registers the checkpoint and creates a session. It does not
run a query. The checkpoint directory must be available in the process
that loads the model.

For a Hugging Face checkpoint, set `hf_name` to its repository ID and
`revision` to its commit ID. Omit `config` to download `config.json`.

The checkpoint must use BF16 weights or FP8 weights stored in blocks of
128 by 128 values. Models that use sliding window attention are not
supported. See [weight formats](/docs/user-guide/models#models).

You can pass additional `ModelSpec` fields to `qwen3_spec`. For example,
set `w_mem_bytes` to a value you have measured to replace the estimate.
See [`qwen3_spec`](https://github.com/fsdatalab/quail/blob/main/quail/specs/qwen3.py)
for its arguments.

### Other architectures

For another architecture, you can define a `ModelSpec` and register it
with `registry.register_model(spec)`. The specification must match the
checkpoint's dimensions, weight format, and prompt format. Registering a
specification does not add execution support for the architecture.

See [`ModelSpec`](https://github.com/fsdatalab/quail/blob/main/quail/specs/base.py)
for the fields and
[Implementing a model architecture](#implementing-a-model-architecture)
for the execution requirements.

## GPU specifications

A *GPU specification* records memory capacity, memory bandwidth, and
compute rates. Quail represents it with `DeviceSpec`.

| Field | Value and unit |
| --- | --- |
| `name` | The name used in `EngineConfig.device`. |
| `mem_bytes` | GPU memory capacity in bytes. |
| `hbm_bw` | GPU memory bandwidth in bytes per second. |
| `peak_flops` | Peak dense FP8 operations per second. |
| `bf16_flops` | Peak dense BF16 operations per second. |
| `sustained_fp8_flops` | Optional. The highest FP8 GEMM rate measured on the GPU (mamf-finder's MAMF). The cost model prices dense projections at this rate when it is set, and at `peak_flops` otherwise. |
| `sustained_hbm_bw` | Optional. The device-to-device copy bandwidth, measured, in bytes per second. The cost model prices memory traffic at this rate when it is set, and at `hbm_bw` otherwise. |
| `attention_rates` | Optional. Measured attention rates as `((query heads, KV heads, head dimension), AttentionRates)` entries. `AttentionRates` holds the causal rate by document length and the cached-read rate by query rows and context length, in operations per second. A model whose head layout has an entry prices attention from it; others use `bf16_flops`. |

All values describe one GPU. Use compute rates without structured
sparsity. The
[H100 specification](https://github.com/fsdatalab/quail/blob/main/quail/specs/h100_sxm.py)
is a complete example.

### Measuring a GPU

The [`calibrate/`](https://github.com/fsdatalab/quail/blob/main/calibrate/README.md)
package fills in the three measured fields. It times
vendor libraries, not Quail's kernels: fp8 matmuls with
[mamf-finder](https://github.com/stas00/ml-engineering/blob/master/compute/accelerator/benchmarks/mamf-finder.py)
(cuBLAS), attention with FlashAttention 3 and FlashInfer, and a 4 GB
copy. Each rate is the one the GPU holds for 2 s at full load.
Attention rates depend on the head layout: query heads, KV heads, and
head dimension. For example, for an H100 and the layout of Qwen3 4B,
on a machine with the GPU:

```bash
uv run python -m calibrate.gemm --device h100-sxm --root results/calibrate
uv run python -m calibrate.attention --device h100-sxm --heads 32,8,128 \
    --root results/calibrate
uv run python -m calibrate.to_spec results/calibrate/h100-sxm
```

The attention run needs FlashAttention 3 and FlashInfer installed. Its
calls have the size of Quail's chunk and KV arena for the models with
that head layout. To run on Modal instead, use `calibrate/modal_app.py`,
which writes to the `quail-results` volume. `--gpus` measures on that
many GPUs at once, and `to_spec` keeps the fastest GPU's rate so the
speed-of-light estimate stays a lower bound:

```bash
uv run modal run --detach calibrate/modal_app.py::gemm --device h100-sxm --gpus 5
uv run modal run --detach calibrate/modal_app.py::attention --device h100-sxm \
    --heads all --gpus 3
modal volume get quail-results calibrate/h100-sxm .
uv run python -m calibrate.to_spec h100-sxm
```

The last command prints `sustained_fp8_flops`, to paste into the
specification. With `--attention` it also prints the measured copy
bandwidth and one `AttentionRates` table per head layout, as comments;
the H100 specification does not use them yet. A new GPU needs an entry in `calibrate/targets.py` naming its
Modal GPU type and FlashInfer architecture.

Register a new specification with `registry.register_device(spec)`.
The backend must accept its device name and provide compatible execution
code. The Quail backend currently accepts `h100-sxm` and
`rtx-pro-6000-blackwell-server`. Its checks are in
[`backend.py`](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/backend.py).

## Implementing a model architecture

The Quail executor implements the Qwen3 and DiffusionGemma architectures.

Quail loads the checkpoint through vLLM, then selects its forward pass
using `ModelSpec.arch`. Supporting another architecture requires both a
compatible model loader and a forward pass that works with Quail's executor.

1. Confirm that vLLM can load the checkpoint. Quail's
   [loader](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/model.py)
   also expects the loaded model to expose an `lm_head` output layer.
2. Define a `ModelSpec` with the model dimensions, KV shapes, weight
   format, and prompt format. The executor uses these values to allocate
   memory and prepare model inputs.
3. Implement a subclass of `ModelPipeline` in
   `quail/backends/quail/executor/models/`. Its constructor receives
   `(model, arena, *, spec)`: the loaded model, KV memory allocator,
   and specification. Its `forward_chunk()` method returns hidden states
   after the model's final normalization, for `chunk.final_indices`.
4. Configure the pipeline's attention support and KV requirements with
   `tree_attention` and `needs_pages`. If `gemm_warmup` is enabled,
   implement `linears()` and provide an `engine` with the `quant()` and
   `gemm()` methods used to prepare kernels. Models with extra answer
   positions also need the canvas settings described in the interface.
5. Add the class to `PIPELINES` in that directory's `__init__.py` and
   set `ModelSpec.arch` to the corresponding key.

The executor allocates and releases KV pages. The forward pass computes
outputs using the supplied pages and the selected attention path.
Before reusing a kernel, check its operation, input shapes, and number
formats against the model. For example, Qwen3's activation kernel computes
`SiLU(gate) * up`. For a model that uses GELU, use that model's GELU
implementation in the forward pass.

Check the forward pass on a GPU against the model's reference
implementation using identical input tokens and positions. Check both
fresh inputs and inputs that reuse saved KV.

See the
[`ModelPipeline` interface](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/models/base.py)
and the
[Qwen3 implementation](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/models/qwen3.py)
for the execution requirements.
