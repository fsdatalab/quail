---
title: Custom models and GPUs
---

Quail uses model and GPU specifications to estimate query time and set
execution limits. The inference backend must also support the model
architecture and GPU you select. See
[Supported models and GPUs](/docs/user-guide/models) for the included
configurations.

## Model specifications

A *model specification* records a checkpoint, model dimensions, and
numerical formats. Quail represents it with `ModelSpec`.

For example, imagine that you have fine tuned Qwen3 4B and saved a complete
FP8 checkpoint in `/models/review-qwen3-4b-fp8`. The checkpoint contains the
weights, model configuration, and tokenizer files. Its model dimensions,
tokenizer, and weight format match the original checkpoint.

Create a `ModelSpec` for the checkpoint:

```python
from quail.specs import ModelSpec

MY_MODEL = ModelSpec(
    name="review-qwen3-4b-fp8",
    params=3.6e9,
    layers=36,
    hidden=2560,
    n_q=32,
    n_kv=8,
    d_head=128,
    ffn_width=19456,
    w_bytes=1.0,
    hf_name="/models/review-qwen3-4b-fp8",
    w_mem_bytes=4.5e9,
    vocab=151936,
    tied_head=True,
    arch="qwen3",
)
```

The checkpoint directory must be available in the process that loads the
model. For a Hugging Face checkpoint, use its repository ID in `hf_name`
and commit ID in `revision`.

If the dimensions, tokenizer, or weight format changed, update the
specification to match. Use the checkpoint's `config.json` and weight
files for the values. Measure loaded weight memory for `w_mem_bytes`;
its default estimate uses `params * w_bytes`.

See [`ModelSpec`](https://github.com/fsdatalab/quail/blob/main/quail/specs/base.py)
for the fields and
[the Qwen3 4B specification](https://github.com/fsdatalab/quail/blob/main/quail/specs/qwen3_4b.py)
for a complete configuration.

## GPU specifications

A *GPU specification* records memory capacity, memory bandwidth, and
compute rates. Quail represents it with `DeviceSpec`.

| Field | Value and unit |
| --- | --- |
| `name` | The name used in `EngineConfig.device`. |
| `mem_bytes` | GPU memory capacity in bytes. |
| `hbm_bw` | GPU memory bandwidth in bytes per second. |
| `peak_flops` | Peak dense FP8 operations per second. |
| `bf16_flops` | Peak dense BF16 operations per second. |

All values describe one GPU. Use compute rates without structured
sparsity. The
[H100 specification](https://github.com/fsdatalab/quail/blob/main/quail/specs/h100_sxm.py)
is a complete example.

Register a new specification with `registry.register_device(spec)`.
The backend must accept its device name and provide compatible execution
code. The Quail backend currently accepts `h100-sxm` and
`rtx-pro-6000-blackwell-server`. Its checks are in
[`backend.py`](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/backend.py).

## Registration

Register the checkpoint specification and select it in `EngineConfig`:

```python
import quail

registry = quail.ExtensionRegistry.with_built_ins()
registry.register_model(MY_MODEL)
config = quail.EngineConfig(model=MY_MODEL.name, device="h100-sxm")
session = quail.Session(config=config, registry=registry)
session.close()
```

The example creates and closes a session without running model inference.
Each model or device name must be unique within its registry.

## Implementing a model architecture

The Quail executor implements the Qwen3 and DiffusionGemma architectures.

Quail loads the checkpoint through vLLM, then selects its forward pass
using `ModelSpec.arch`. Supporting another architecture requires both a
compatible model loader and a forward pass that works with Quail's executor.

1. Confirm that vLLM can load the checkpoint. Quail's
   [loader](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/model.py)
   also expects the loaded model to expose an `lm_head` output layer.
2. Define a `ModelSpec` with the model dimensions, KV shapes, weight
   format, and prompt format. The executor uses these values to allocate
   memory and prepare model inputs.
3. Implement a subclass of `ModelPipeline` in
   `quail/backends/quail/executor/models/`. Its constructor receives
   `(model, arena, *, spec)`: the loaded model, KV memory allocator,
   and specification. Its `forward_chunk()` method returns hidden states
   after the model's final normalization, for `chunk.final_indices`.
4. Configure the pipeline's attention support and KV requirements with
   `tree_attention` and `needs_pages`. If `gemm_warmup` is enabled,
   implement `linears()` and provide an `engine` with the `quant()` and
   `gemm()` methods used to prepare kernels. Models with extra answer
   positions also need the canvas settings described in the interface.
5. Add the class to `PIPELINES` in that directory's `__init__.py` and
   set `ModelSpec.arch` to the corresponding key.

The executor allocates and releases KV pages. The forward pass computes
outputs using the supplied pages and the selected attention path.
Before reusing a kernel, check its operation, input shapes, and number
formats against the model. For example, Qwen3's activation kernel computes
`SiLU(gate) * up`. For a model that uses GELU, use that model's GELU
implementation in the forward pass.

Check the forward pass on a GPU against the model's reference
implementation using identical input tokens and positions. Check both
fresh inputs and inputs that reuse saved KV.

See the
[`ModelPipeline` interface](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/models/base.py)
and the
[Qwen3 implementation](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/models/qwen3.py)
for the execution requirements.
