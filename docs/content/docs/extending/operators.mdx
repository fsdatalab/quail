---
title: Custom operators
---

To add an operator, define its logical representation and physical
plan. Add a runtime for each new physical node. For Python functions
between existing operators, use [`apply`](/docs/user-guide/python-api#apply).

## Logical expressions

Model calls are expressions within logical operators. `AI.CLASSIFY`,
for example, is a `ModelCall` with `kind="label"`. In `SELECT`, the
call is wrapped in an `Alias`. In a label filter, `LabelIn` tests the call.

Add a logical node when the operation requires new inputs or an output
schema. Logical nodes implement `children()`, `expressions()`, validation,
and immutable rewrite methods. The protocol is described in
[logical plans](/docs/architecture/logical-plans).

SQL and Python syntax must produce equivalent logical representations.

## Physical nodes

A physical node declares typed input and output ports, a `type_name`,
a runtime lookup key, and an execution location. Serialization uses
`attributes()` and `from_attributes()`.

The runtime implements `execute(node, inputs, context)` and returns a
`NodeResult` with the declared output ports. Register the node and runtime
on an [extension registry](/docs/extending):

```python
registry.register_node(MyNode, runtime=MyRuntime())
```

`register_node()` supplies a `NodeCodec` by default. Supply a custom codec
if the node needs another encoding. The
[`FirstDocuments` example](https://github.com/fsdatalab/quail/blob/main/tests/test_physical.py)
includes a node, runtime, planner, and registration that run without a GPU.

## Planning

A physical planner produces `PhysicalCandidate` values containing a
graph, a plan, and an estimated execution time. The candidate with the
lowest estimate is selected. Unsupported configurations must be rejected
during planning.

Tokenized prompt preparation and physical graph construction belong
in `quail.planner`.
Work counts and execution time estimates belong in `quail.cost`.
Classification uses
[`planner/classify.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/classify.py)
and [`cost/classify.py`](https://github.com/fsdatalab/quail/blob/main/quail/cost/classify.py).

## Pipelines

An operator runtime can execute independently or in a pipeline.
To support pipelines, define which adjacent operators can run together
and which document state they can reuse.

[`execution/pipelines.py`](https://github.com/fsdatalab/quail/blob/main/quail/execution/pipelines.py)
groups physical nodes.
[`executor/pipeline.py`](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/pipeline.py)
executes the groups using `executor/operators/`.
For classification, decoder rounds run inside one physical node.

## Optimizer rules

Register a logical rule to rewrite the logical tree, or a physical
rule to rewrite the selected graph. Return `None` when no rewrite is
needed.

Logical rules run in registration order until a pass makes no change,
with a maximum of four passes. Physical rules run once in registration
order. The built-in physical rules are `prefix_sharing`, followed by
`tree_attention`.

Quail may first plan with estimated document lengths while
tokenization continues. After the tokens are available, it runs the
physical rules again. A rule must handle repeated application without
duplicating its changes.

The rule protocols are in
[`logical_optimizer.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/logical_optimizer.py)
and [`physical_optimizer.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/physical_optimizer.py).
See [physical plans](/docs/architecture/physical-plans#classification-nodes)
and [execution](/docs/architecture/execution#classification-execution)
for the existing classification implementation.
