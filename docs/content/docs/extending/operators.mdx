---
title: Custom operators
---

Quail includes `AI.IF`, `AI.SCORE`, and `AI.CLASSIFY`. To add another
operation, define what it means in the logical plan, choose physical
nodes for its execution, and register a runtime for any new node type.

If you only need Python logic to filter documents or select candidate
pairs, use [`apply`](/docs/user-guide/python-api#apply). It already has
a logical node, a physical node, and execution support.

## Start with the logical expression

Model calls are expressions within logical operators. For example,
`AI.CLASSIFY` is a `ModelCall` with `kind="label"`. The front ends put
it in a projection to return a label, or inside `LabelIn` to filter
on that label. It does not require a separate logical classification
node.

Decide whether your operation needs a new expression or a new node.
An expression represents a computed value. A node represents a query
operation with inputs and an output schema. Logical nodes implement
`children`, `expressions`, validation, and immutable rewrite methods.
See [logical plans](/docs/architecture/logical-plans) for the protocol.

Update the SQL compiler and Python builder together when adding
public syntax. They should produce equivalent logical plans for the
same operation.

## Define physical inputs and outputs

A physical node describes one executable operation. Its typed ports
state which values it consumes and produces. An `AiClassify`, for
example, consumes document ids or earlier score tables and produces
a label table. A one-document classifier also produces the ids of
documents that received a label.

For a new node type, define:

- Its input and output ports, including their value types and schemas.
- A unique `type_name` and a `runtime_key` for runtime lookup.
- An execution location, either the coordinator or a GPU executor.
- `attributes()` and `from_attributes()` for serialization.

The runtime implements `execute(node, inputs, context)` and returns
a `NodeResult`. Its output dictionary must match the node's declared
ports. Register the node and runtime together:

```python
registry.register_node(MyNode, runtime=MyRuntime())
```

See the [extension overview](/docs/extending) for creating a registry
and passing it to a session.

`register_node` supplies a `NodeCodec` by default. Supply a custom codec
when the node needs a different encoding. The
[`FirstDocuments` example in `tests/test_physical.py`](https://github.com/fsdatalab/quail/blob/main/tests/test_physical.py)
shows a complete node, runtime, planner, and registration that run
without a GPU.

## Plan and estimate the operation

The backend planner or an extension planner constructs physical
candidates from the logical request. A `PhysicalCandidate` contains
a graph, a plan, and its estimated execution time. Quail selects the
candidate with the lowest estimate.

Keep prompt preparation and graph construction in the planner.
Keep calculations of tokens, attention work, and execution time in
`quail.cost`. For classification, those responsibilities are in
[`planner/classify.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/classify.py)
and [`cost/classify.py`](https://github.com/fsdatalab/quail/blob/main/quail/cost/classify.py).

Reject an unsupported configuration during planning. Pair
classification is one example. The Quail backend rejects a plan
when the pair classifier cannot run in its AI join pipeline.

## Add pipeline support when needed

A runtime that executes a node independently is the starting point.
If the operation should also execute with adjacent operators, define
when they can share a pipeline and which input state is reusable.

The current pipeline builder is
[`execution/pipelines.py`](https://github.com/fsdatalab/quail/blob/main/quail/execution/pipelines.py).
Model pipeline execution is in
[`executor/pipeline.py`](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/pipeline.py),
and operator implementations are in `executor/operators/`.
Classification decoder rounds remain inside the classification
executor. The physical graph still contains one node per classification.

## Optimizer rules

Register a logical rule to rewrite the logical tree, or a physical
rule to rewrite the selected graph. Return `None` when no rewrite is
needed.

Logical rules run in registration order until a pass makes no change,
with a maximum of four passes. Physical rules run once in registration
order. The built-in physical rules are `prefix_sharing`, followed by
`tree_attention`.

Quail may first plan with estimated document lengths while
tokenization continues. After the tokens are available, it runs the
physical rules again. A rule must handle repeated application without
duplicating its changes.

The rule protocols are in
[`logical_optimizer.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/logical_optimizer.py)
and [`physical_optimizer.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/physical_optimizer.py).
See [classification](/docs/architecture/classification) for the existing
operator's plan and execution structure.
