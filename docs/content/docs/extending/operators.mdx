title: Custom operators
---

Quail supports `AI.IF` (Snowflake: `AI_FILTER`), which returns
TRUE or FALSE, `AI.SCORE`, which returns a numeric score, and
`AI.CLASSIFY`, which returns a label. Adding a new operator requires
changes at three levels: a logical representation, a physical node,
and planning logic.

We use `AI.CLASSIFY` as a running example. `AI.CLASSIFY` categorizes
each document into one of N labels instead of returning TRUE/FALSE.
The planner chooses among letter scoring, tree scoring, and greedy
decoding. See [classification scoring](/docs/architecture/planning#choosing-classification-scoring).

## Logical node

A logical node defines what the operator means in the query plan.
Classification uses a `ModelCall` expression within existing nodes.
For a bound `prompt`, the call holds the allowed labels:

```python
from quail.logical import ModelCall

call = ModelCall(prompt, kind="label", labels=("refund", "praise"))
```

An `Alias` in `Project` names the output column. `LabelIn` in a
`SemanticFilter` tests the label against an accepted list. SQL and
Python syntax produce the same logical expressions.

For a new logical node, implement the inputs, expressions, output schema,
validation, and immutable rewrite methods described in the
[node protocol](/docs/architecture/logical-plans#the-node-protocol).

See
[`SemanticFilter`](https://github.com/fsdatalab/quail/blob/main/quail/logical/nodes.py)
for how the existing filter node is built.

## Physical node

A physical node specifies how the operator runs. `AiClassify` holds a
`ClassifySpec` with the tokenized prompt, labels, and scoring rule.
Given a `spec` built by the planner:

```python
from quail.physical import AiClassify

node = AiClassify(
    node_id="classify:topic", backend_name="quail",
    model="qwen3-4b-fp8", spec=spec)
```

`AiClassify` uses the `AiScore` runtime. A later `Filter` tests its
labels. See [classification nodes](/docs/architecture/physical-plans#classification-nodes)
for the physical graph.

Each physical node also needs:

- A **codec** to serialize the node across the process boundary.
  `register_node()` supplies a `NodeCodec` by default.
- A **runtime** that implements `execute(node, inputs, context)` and
  returns the Arrow output tables.

See
[`AiFilter`](https://github.com/fsdatalab/quail/blob/main/quail/physical/nodes.py)
for how the existing filter physical node is built, and
[`tests/test_physical.py`](https://github.com/fsdatalab/quail/blob/main/tests/test_physical.py)
for a complete working example of a custom node with its codec,
runtime, and planner.

## Planning

Adding a new operator to the planner means teaching the existing
Quail backend how to plan and cost the new node. Concretely:

1. **Work counting.** Add a function that counts fresh tokens,
   attention pairs, KV written, and KV read for the new operator.
   Pass `window=model.sliding_window` to `scan`, `ask`, or `stream`
   so you also count pairs and KV reads for sliding-window layers.
   Classification counts depend on the chosen scoring rule. Letter
   scoring reads category codes, tree scoring compares complete label
   sequences, and greedy decoding adds one token at a time. See
   [`quail/cost/classify.py`](https://github.com/fsdatalab/quail/blob/main/quail/cost/classify.py)
   for classification work counts and
   [`quail/cost/work.py`](https://github.com/fsdatalab/quail/blob/main/quail/cost/work.py).
2. **Cost estimation.** Pass the work counts through the
   [roofline model](/docs/architecture/planning#the-roofline-speed-of-light-model)
   to get estimated seconds. See
   [`quail/cost/sol.py`](https://github.com/fsdatalab/quail/blob/main/quail/cost/sol.py).
3. **Graph construction.** Include the new physical node in the graph
   the planner builds. The planner in
   [`quail/planner/decide.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/decide.py)
   constructs the full physical graph (scans, filters, joins,
   barriers, projection) and returns a `PhysicalCandidate` with the
   graph and estimated time. The new node would be placed in the
   graph alongside the existing node types. Classification prompt
   preparation and graph construction are in
   [`quail/planner/classify.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/classify.py).

## Pipelines

An operator runtime can execute independently or in a pipeline.
To support pipelines, define which adjacent operators can run together
and which document state they can reuse.

[`execution/pipelines.py`](https://github.com/fsdatalab/quail/blob/main/quail/execution/pipelines.py)
groups physical nodes.
[`executor/pipeline.py`](https://github.com/fsdatalab/quail/blob/main/quail/backends/quail/executor/pipeline.py)
executes the groups using `executor/operators/`.
For classification, decoder rounds run inside one physical node.

## Optional: logical and physical rules

**Logical rules** rewrite the logical plan before physical planning.
For example, a rule can merge adjacent filters on the same table.

**Physical rules** rewrite the physical graph after the planner
selects one. For example, `prefix_sharing` enables reuse of KV
for shared document prefixes.

Rules run in this order:

- Logical rules run in registration order, with built-in rules first.
  Quail repeats the sequence until a pass leaves the plan unchanged
  or it has run four passes (`MAX_PASSES`).
- Physical rules run once per pass: `prefix_sharing`, then
  `tree_attention`, then extension rules in registration order.
- If the plan was built while tokenization was running, Quail runs
  the physical rules again once the tokens are available. Return
  `None` when your rule has no change to make. A repeated pass should
  not duplicate a change already present in the plan.

Repeated rule application is an established optimizer design.
[DataFusion](https://datafusion.apache.org/library-user-guide/query-optimizer.html)
also supports repeated logical optimization passes.
[Spark's rule executor](https://github.com/apache/spark/blob/master/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/rules/RuleExecutor.scala)
organizes rules into batches that run once or repeat until the plan
stops changing or a configured limit is reached.

See
[`quail/planner/logical_optimizer.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/logical_optimizer.py)
and
[`quail/planner/physical_optimizer.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/physical_optimizer.py)
for the rule protocols.

## Registration

Register your node, runtime, planner, and rules on the session's
`ExtensionRegistry`:

```python
registry = quail.ExtensionRegistry.with_built_ins()
registry.register_node(MyNode, runtime=MyRuntime())
registry.register_physical_planner(MyPlanner())
registry.register_logical_rule(MyLogicalRule())
```

See the [Overview](/docs/extending) for how to create and pass a
registry.
