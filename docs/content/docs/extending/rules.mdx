---
title: Custom Rules
---

An optimizer rule changes a plan while preserving the query's result.
Quail's rules are written in Rust:

- Logical rules are DataFusion `OptimizerRule`s that run over the
  whole plan, Quail's `AiNode`s included: DataFusion's default rules
  and Quail's. They are listed by name in `LOGICAL_RULES` and
  `logical_rule` in
  [`crates/quail-datafusion/src/rules.rs`](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/rules.rs).
  `claim_model_regions` always runs after them.
- Physical rules rewrite executable graphs and their settings, in
  [`crates/quail-planner/src/physical_rules.rs`](https://github.com/fsdatalab/quail/blob/main/crates/quail-planner/src/physical_rules.rs).

A session's registry lists the rules the planner applies, by name, and
their order.

## Add a rule

1. Write the rule in Rust. A logical rule implements DataFusion's
   `OptimizerRule` and returns the rewritten plan, as `PushDownFilter`
   does. A physical rule returns a replacement graph, or none to keep
   the graph, and may add settings the executor reads.
2. Add its name to the match in `logical_rule` or `apply_rule`. A
   logical rule that moves operators around an `AiNode` follows the
   node's `UserDefinedLogicalNodeCore` methods, which say which filters
   and limits may move below it.
3. Register the name.

Give each rule a unique name, shown in `explain()`. A logical rule's
name is its `OptimizerRule::name()`, such as `push_down_distinct`. A
physical rule uses `should_...` for yes/no decisions and `choose_...`
to select an implementation.

For example, imagine a session that should run every built-in rule and
then a rule `should_skip_empty_tables` added to `physical_rules.rs`:

```python
import quail
from quail.extensions import PhysicalRule

registry = quail.ExtensionRegistry.with_built_ins()
registry.register_physical_rule(PhysicalRule("should_skip_empty_tables"))
session = quail.Session(config, registry=registry)
```

Registering an object that is not a `LogicalRule` or a `PhysicalRule`
raises `TypeError`.

A logical rule is turned off by leaving its name out of the registry.
For example, imagine a test that checks a query returns the same rows
with and without `push_down_limit_into_ai_nodes`, which makes a LIMIT
the fetch of the `AiNode` below it:

```python
from quail.builtins import LOGICAL_RULES, built_in_registry

rules = [name for name in LOGICAL_RULES if name != "push_down_limit_into_ai_nodes"]
session = quail.Session(config, registry=built_in_registry(logical_rules=rules))
```

## Fetch rules

An `AiNode`'s fetch keeps the first rows that pass its filter, of all
rows or of each key, and lets the executor stop asking the model. A
rule that sets a fetch follows two conditions:

- The node's tests are its own filter first. A fetch counts rows after
  the filter, and `absorb_into_ai_nodes` absorbs nothing into a node
  with a fetch.
- Only operators that keep one row per row are between the LIMIT or
  DISTINCT and the node, and the node has no `HINT`.

`push_down_limit_into_ai_nodes` and `push_down_distinct`, in
[`limit.rs`](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/limit.rs)
and
[`distinct.rs`](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/distinct.rs),
are the built-in examples.

## Rewrites by number

Each rewrite of an AI operator has a number. The operator is
`AI(R; g, p, h, P, n)`, as
[Logical plans](/docs/architecture/logical-plans) defines it. The table
names the rule that makes each rewrite and when it applies.

| Number | Rewrite | Rule | Condition |
| --- | --- | --- | --- |
| R1 | `σ_q(AI(R)) ⇒ AI(σ_q(R))` | Quail's region claim, then DataFusion's `push_down_filter` | `q` reads only columns of `R`, and the node has no fetch. Above a per-key fetch, only a test of the key columns moves. |
| R2 | `σ_q(AI(R; p)) ⇒ AI(R; p ∧ q)` | `absorb_into_ai_nodes` | `q` tests the node's answer, and the node has no fetch. |
| R8 | `Limit_k(π(R)) ⇒ π(Limit_k(R))` | DataFusion's `push_down_limit`; `push_down_limit_into_ai_nodes` also reads through projections | The projection keeps one row per row. Over an `AiNode`, the LIMIT becomes the node's fetch (R9). |
| R9 | `Limit_k(AI(R; n)) ⇒ AI(R; n = min(k, n))` | `push_down_limit_into_ai_nodes` | Only projections and aliases are between them, the node has no `HINT` and no per-key fetch, and `k > 0`. |
| R10 | `Limit_{k,m}(AI(R; n)) ⇒ Limit_{k,m}(AI(R; n = min(k + m, n)))` | `push_down_limit_into_ai_nodes` | As R9, for a LIMIT with an OFFSET of `m`. |
| R12 | `δ(π_K(AI(R))) ⇒ δ(π_K(AI(R; n = 1 per K)))` | `push_down_distinct` | `K` is input columns or a classification's label, and the node has no fetch. |

R1 needs no rule of its own. Quail moves each plain filter term to its
table while it finds the model regions, before DataFusion's optimizer
runs, so the term is below the `AiNode` once the node exists. Within
the optimizer, an `AiNode`'s `prevent_predicate_push_down_columns`
lets `push_down_filter` move such a term below the node.

## Rule order

Rules run in registration order within each step:

1. DataFusion applies the logical rules to the whole plan, then
   `claim_model_regions` claims each model region, and Quail reads the
   region's operators from the result.
2. Build an executable graph for each placement of the column
   operators: the plan as placed, and each plan with a classification,
   extraction, or map moved above a join.
3. Apply the physical rules to each graph.
4. Select the candidate with the lowest estimated time.

If initial planning used estimated token lengths, the search runs again
when exact tokens are available. See [Optimizer](/docs/architecture/optimizer)
for the built-in rule order.

A request backend, such as stock vLLM, is planned in Rust too: its
`request_settings` say how it submits each operator, Rust lowers each
placement to one request node, and the first placement it does not
refuse is selected. The physical rules do not run on its plans.

## Test a rule

Write a Rust unit test next to the rule for its rewrite, and a Python
test that plans a query through a session and checks the plan or the
rows it returns. See the
[search tests](https://github.com/fsdatalab/quail/blob/main/tests/planner/test_search.py).
