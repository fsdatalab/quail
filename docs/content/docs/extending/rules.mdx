---
title: Custom Rules
---

An optimizer rule changes a plan while preserving the query's meaning.
For Quail's existing rules, see the [optimizer](/docs/architecture/optimizer).

## Choose the category

- A **universal rule** applies whenever its conditions hold, without
  comparing costs. Set `cost_based = False`.
- A **cost-based rule** proposes alternatives or chooses an implementation
  using estimated cost. Set `cost_based = True`.

Each rule also declares its target. Set `target = "logical"` to rewrite
query trees, or `target = "physical"` to rewrite executable graphs.
The target tells the planner which representation the rule accepts.
Both categories use the same `OptimizerRule` interface.

## Implement the rule

Define a class with `name`, `target`, `cost_based`, and `rewrite()`.
The name identifies the rule in the registry and plan explanations.
Use a name that differs from every registered rule, across both categories.
Return new nodes instead of changing existing nodes in place.
Return `None` when no change is needed.

For example, imagine a `reviews` table with `id`, `body`, and `author`
columns. A query returns `id` and uses `body` in a model filter.
Projection pushdown tells the scan to retain `id` values for the result.
Quail still tokenizes `body` for the filter. It does not need `author`.

```python
from quail.planner.rules.rewrites import push_down_projection


class ProjectionPushdown:
    name = "projection_pushdown"
    target = "logical"
    cost_based = False

    def rewrite(self, root, context):
        rewritten = push_down_projection(root)
        return None if rewritten is root else rewritten
```

The helper updates the scans and returns the plan's root. It returns the
original root when no change is needed. See the
[complete implementation](https://github.com/fsdatalab/quail/blob/main/quail/planner/rules/universal.py).

For a query tree target, `rewrite(root, context)` returns a new root.
For a cost-based tree rewrite, the planner retains the original,
deduplicates equal roots, and lowers and refines every alternative before
comparing costs. The rewrite proposes a placement; it does not call the
planner recursively to price it. Check `context.backend` when a placement
requires a particular engine's support, as `LiftMaps` does.

For an executable graph target, `rewrite(graph, context)` returns a new
`PhysicalGraph`. A cost-based graph rule compares the implementations it
supports and returns its choice. The planner applies the change before
comparing whole candidates. The current search is staged and does not
enumerate all combinations of implementations and placements.

The *planning context* provides the configuration and input statistics
available to a rule. See
[`LogicalPlanningContext`](https://github.com/fsdatalab/quail/blob/main/quail/planner/optimizer/logical.py)
and
[`PlanningContext`](https://github.com/fsdatalab/quail/blob/main/quail/planner/optimizer/physical.py)
for their fields.

## Register the rule

Create an [extension registry](/docs/extending#registration) with
`ExtensionRegistry.with_built_ins()`. Register an instance with the method
for its category:

| Category | Registration method |
| --- | --- |
| Universal | `registry.register_universal_rule(rule)` |
| Cost-based | `registry.register_cost_based_rule(rule)` |

Pass the registry to the session. `ProjectionPushdown` is already
registered in Quail's default registry. The example shows its interface;
you do not need to register it again.

`registry.universal_rules` and `registry.cost_based_rules` expose each
category. `registry.rules` contains both in one registration order.
The registry checks the target and category when a rule is registered.

### Execution order

- Universal tree rewrites simplify the query before search. A *pass*
  applies all matching rules once. Quail repeats passes until nothing
  changes, with a maximum of four passes.
- Cost-based tree rewrites expand the known alternatives until no new
  plan appears, with a maximum of four passes. The original stays first.
- Both categories of graph rules run once on each candidate in their
  shared registration order. Registration order preserves dependencies
  across categories. Quail compares candidate costs after graph refinement.
- Exact token sequences trigger the search again when initial planning
  used estimated document lengths.
- Rule settings belong to one candidate. The context memo is shared for
  reusable statistics; memo keys must include all inputs that affect a value.

`explain(verbose=True)` lists both categories and the graph refinement
order. The pricing helper
`quail.planner.pricing.estimated_seconds(plan, context, registry)` uses the
same search and registered rules.

## Check the rule

Call `rewrite()` directly to test your rule without model inference.
Check that:

- The intended nodes and fields change.
- The original plan remains unchanged.
- The revised plan preserves the query's meaning.
- A second call returns `None` if no further change is needed.
- Cost-based tree alternatives are compared after graph refinement.

See the [tree rewrite tests](https://github.com/fsdatalab/quail/blob/main/tests/frontend/test_logical_extensions.py)
and [search tests](https://github.com/fsdatalab/quail/blob/main/tests/planner/test_search.py)
for examples.
