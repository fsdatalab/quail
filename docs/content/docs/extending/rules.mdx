title: Custom Rules
---

An optimizer rule changes a plan while preserving the query's result.
Quail's rules are written in Rust:

- Logical rules are DataFusion `OptimizerRule`s that run over the
  whole plan, Quail's `AiNode`s included: DataFusion's default rules
  and Quail's. They are listed by name in `LOGICAL_RULES` and
  `logical_rule` in
  [`crates/quail-datafusion/src/rules.rs`](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/rules.rs).
  `claim_model_regions` always runs after them.
- Physical rules rewrite executable graphs and their settings, in
  [`crates/quail-planner/src/physical_rules.rs`](https://github.com/fsdatalab/quail/blob/main/crates/quail-planner/src/physical_rules.rs).

A session's registry lists the rules the planner applies, by name, and
their order.

## Add a rule

1. Write the rule in Rust. A logical rule implements DataFusion's
   `OptimizerRule` and returns the rewritten plan, as `PushDownFilter`
   does. A physical rule returns a replacement graph, or none to keep
   the graph, and may add settings the executor reads.
2. Add its name to the match in `logical_rule` or `apply_rule`. A
   logical rule that moves operators around an `AiNode` follows the
   node's `UserDefinedLogicalNodeCore` methods, which say which filters
   and limits may move below it.
3. Register the name.

Give each rule a unique name, shown in `explain()`. A logical rule's
name is its `OptimizerRule::name()`, such as `push_down_distinct`. A
physical rule uses `should_...` for yes/no decisions and `choose_...`
to select an implementation.

For example, imagine a session that should run every built-in rule and
then a rule `should_skip_empty_tables` added to `physical_rules.rs`:

```python
import quail
from quail.extensions import PhysicalRule

registry = quail.ExtensionRegistry.with_built_ins()
registry.register_physical_rule(PhysicalRule("should_skip_empty_tables"))
session = quail.Session(config, registry=registry)
```

Registering an object that is not a `LogicalRule` or a `PhysicalRule`
raises `TypeError`.

A logical rule is turned off by leaving its name out of the registry.
For example, imagine a test that checks a query returns the same rows
with and without `push_down_limit_into_ai_nodes`, which makes a LIMIT
the fetch of the `AiNode` below it:

```python
from quail.builtins import LOGICAL_RULES, built_in_registry

rules = [name for name in LOGICAL_RULES if name != "push_down_limit_into_ai_nodes"]
session = quail.Session(config, registry=built_in_registry(logical_rules=rules))
```

## Fetch rules

An `AiNode`'s fetch keeps the first rows that pass its filter, of all
rows or of each key, and lets the executor stop asking the model. A
rule that sets a fetch follows two conditions:

- The node's tests are its own filter first. A fetch counts rows after
  the filter, and `absorb_into_ai_nodes` absorbs nothing into a node
  with a fetch.
- Only operators that keep one row per row are between the LIMIT or
  DISTINCT and the node, and the node has no `HINT`.

`push_down_limit_into_ai_nodes` and `push_down_distinct`, in
[`limit.rs`](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/limit.rs)
and
[`distinct.rs`](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/distinct.rs),
are the built-in examples.

## Rewrites by number

Each rewrite of an AI operator has a number. The operator is
`AI(R; g, p, h, P, n)`, as
[Logical plans](/docs/architecture/logical-plans) defines it. The table
names the rule that makes each rewrite and when it applies.

| Number | Rewrite | Rule | Condition |
| --- | --- | --- | --- |
| R1 | `σ_q(AI(R)) ⇒ AI(σ_q(R))` | Quail's region claim, then DataFusion's `push_down_filter` | `q` reads only columns of `R`, and the node has no fetch. Above a per-key fetch, only a test of the key columns moves. |
| R2 | `σ_q(AI(R; p)) ⇒ AI(R; p ∧ q)` | `absorb_into_ai_nodes` | `q` tests the node's answer, and the node has no fetch. |
| R3 | `σ_q(AI(R; h)) ⇒ σ_q(AI(R; h ∧ q))` | `push_down_hint_tests` | The filter is directly above a classification, extraction, map, or SAE features node of rows with no fetch; `q` is a term of the filter that reads a column the node adds and otherwise only the node's input, with no AI call. The filter stays. |
| R4 | `σ_{a LIKE x}(AI_{extract(d)→a}(R)) ⇒ σ_{a LIKE x}(AI_{extract(d)→a}(σ_{d ILIKE '%s%'}(R)))` | `push_down_substring_prechecks` | The node is an extraction of rows with no fetch; its filter has a term `a.f LIKE x` or `ILIKE x`, not negated, with a literal pattern; `s` is the longest word of the longest literal run of `x`. The test of the answer stays. |
| R5 | `π_Q(AI(R; P)) ⇒ π_Q(AI(R; P = Q[P]))` | `push_down_projection_into_ai_nodes` | `Q` is a projection directly above a node of rows; the node keeps its answer, and drops each other added column `Q` does not read, such as an extraction's spans under a FROM subquery. DataFusion's `optimize_projections` already prunes the input columns the node reads. |
| R6 | `π_{B, (CASE WHEN c THEN a END)→z}(AI_{f→a}(R)) ⇒ π_{B, a→z}(AI_{f→a}(R; g = g ∧ c))` | `push_down_case_guards` | The node is a classification, map, or SAE features of rows with no filter, `HINT`, or fetch; the projection is directly above it; every item that reads an added column is `CASE WHEN c THEN <column> END` with the same `c`; `c` reads only columns of the one table the call reads. |
| R7 | `AI_{f→b}(R; p = a ∨ b) ⇒ AI_{f→b}(R; g = (a IS NOT TRUE), p = a ∨ b)` | `push_down_or_guards` | The node is an AI.IF of rows with no guard, `HINT`, or fetch, and returns none of the columns it adds; a term of its filter is an OR with the answer `b` as one term and no other term reads `b`; the other terms `a` read only columns of the one table the call reads. |
| R8 | `Limit_k(π(R)) ⇒ π(Limit_k(R))` | DataFusion's `push_down_limit`; `push_down_limit_into_ai_nodes` also reads through projections | The projection keeps one row per row. Over an `AiNode`, the LIMIT becomes the node's fetch (R9). |
| R9 | `Limit_k(AI(R; n)) ⇒ AI(R; n = min(k, n))` | `push_down_limit_into_ai_nodes` | Only projections and aliases are between them, the node has no `HINT` and no per-key fetch, and `k > 0`. |
| R10 | `Limit_{k,m}(AI(R; n)) ⇒ Limit_{k,m}(AI(R; n = min(k + m, n)))` | `push_down_limit_into_ai_nodes` | As R9, for a LIMIT with an OFFSET of `m`. |
| R11 | `Limit_k(R ⊎ S) ⇒ Limit_k(Limit_k(R) ⊎ Limit_k(S))` | DataFusion's `push_down_limit`, then `push_down_limit_into_ai_nodes` | `⊎` is UNION ALL. Each branch's LIMIT becomes its `AiNode`'s fetch as R9 allows. |
| R12 | `δ(π_K(AI(R))) ⇒ δ(π_K(AI(R; n = 1 per K)))` | `push_down_distinct` | `K` is input columns or a classification's label, and the node has no fetch. |
| R13 | `S ⋉_{J=K} AI(R) ⇒ S ⋉_{J=K} AI(R; n = 1 per K)` | `push_down_semi_join_fetch` | `J = K` is the whole join condition, `K` are input columns of the node, each name once; only projections and aliases are between the join and the node; the node, and every `AiNode` below it, is an AI.IF over the same one table, with no join, fetch, `HINT`, or guard. |
| R14 | `π_K(σ_{c ≥ k}(γ_{K; count(*)→c}(AI(R)))) ⇒ π_K(σ_{c ≥ k}(γ_{K; count(*)→c}(AI(R; n = k per K))))` | `push_down_count_threshold` | The HAVING is `COUNT(*) >= k`, `> k - 1`, or written the other way round, with `k` a positive integer; the GROUP BY keys `K` are columns; `count(*)` is the only aggregate and only the HAVING reads it; the node is under the GROUP BY as for R13. |
| R17 | `AI_{f→b}(AI_{f→a}(R)) ⇒ π_{*, a→b}(AI_{f→a}(R))` | `merge_repeated_ai_calls` | Same call and guard, only filters and other `AiNode`s of the same rows between them, no fetch on the upper node, each test of the upper node's answer already a test of the lower node's, and the lower node returns each column the upper one returns. The lowering already gives calls written the same way in one SELECT list and WHERE one node. |

R3 gives the node a hint test, which it may drop rows by; the filter
above still decides which rows the query returns. R2 absorbs the same
terms into the node's exact filter, and runs first, so in the default
order R3 finds a term only when `absorb_into_ai_nodes` is turned off.
Its practical role is small: the executor already stops a map's or
extraction's answer by the region's exact tests of that answer alone
(`should_stop_answers_early`), and reads a hint test the same way. See
[Evaluation on partial answers](/docs/architecture/execution#evaluation-on-partial-answers).

R4 relies on `AI.EXTRACT` copying each answer from its document, so an
answer is NULL or a substring of `d`. A decoded answer may differ from
the document in case and whitespace, which `locate_span` forgives, so
the precheck ignores case and reads one word of the pattern's literal
text. `push_down_filter` then moves the precheck to the table, where
DataFusion runs it before the model region.

R5 changes what the node returns, not what the model is asked: the
executor still locates each extracted answer's span. A SELECT list that
reads one field of an extraction, such as `x.e.w`, still asks every
question of the extraction; a classification asked for probabilities
under a FROM subquery still computes them. Neither is a column of the
node's `P` today.

For R6, the executor evaluates the guard over the rows a column
operator reads, asks the model about the rows where it is TRUE, and
gives every other row a NULL answer. A guarded operator runs in a
pipeline of its own, and stock vLLM refuses a plan with a guard. An
extraction keeps its `CASE`: its answer is a struct of one answer per
question, and an unasked row would read as a struct of NULL answers
rather than NULL.

R7 starts from the lowering. `WHERE r.flagged OR AI.IF(...)` is one
`AiNode` whose filter is `r.flagged OR b`, with the answer `b` in the
call's place, and which returns none of its added columns; that is
`σ_{a ∨ b}(AI_{f→b}(R))` once the OR is the node's filter. The rule
guards the node with `r.flagged IS NOT TRUE`. The physical AI filter
then carries the guard and the alternative `a`: the executor asks the
model about the rows where the guard is TRUE, keeps those it answers
TRUE, and passes each row where `a` is TRUE without asking. Without the
rule, the filter asks every row and still passes the rows where `a` is
TRUE. A guarded or ORed AI filter runs in a pipeline of its own, stock
vLLM refuses it, and so does a region with a LIMIT or a DISTINCT stop
key over it, since the executor counts survivors among the rows it
asks. An OR of two AI.IF calls, or of an AI.IF over two tables, is
still refused.

R13 covers an uncorrelated `IN` subquery, such as `WHERE p.number IN
(SELECT r.product FROM reviews r WHERE AI.IF(...))`: Quail lowers the
subquery's AI calls as a part of its own, and DataFusion's
`decorrelate_predicate_subquery` runs the `IN` as a semi-join above the
subquery's model region. The executor stops a key's documents once one
passes the table's AI filters, as for R12, and only in a region that
asks one table's AI.IF filters and joins nothing; the rule's conditions
are that region's. A correlated `EXISTS` with an AI call on the
subquery's table alone is still refused: its semi-join is inside the
region, which Quail does not bind.

R14 uses the same stop as R13 with `n = k`: the executor skips a key's
remaining documents once `k` of them pass the table's AI filters. With
more than one document of a key in flight, a few more than `k` may
pass; the count threshold keeps the same keys either way. Explain shows
`stop per key: <key> (the rest skipped once k survive)`.

R1 needs no rule of its own. Quail moves each plain filter term to its
table while it finds the model regions, before DataFusion's optimizer
runs, so the term is below the `AiNode` once the node exists. Within
the optimizer, an `AiNode`'s `prevent_predicate_push_down_columns`
lets `push_down_filter` move such a term below the node.

## Rule order

Rules run in registration order within each step:

1. DataFusion applies the logical rules to the whole plan, then
   `claim_model_regions` claims each model region, and Quail reads the
   region's operators from the result.
2. Build an executable graph for each placement of the column
   operators: the plan as placed, and each plan with a classification,
   extraction, or map moved above a join.
3. Apply the physical rules to each graph.
4. Select the candidate with the lowest estimated time.

If initial planning used estimated token lengths, the search runs again
when exact tokens are available. See [Optimizer](/docs/architecture/optimizer)
for the built-in rule order.

A request backend, such as stock vLLM, is planned in Rust too: its
`request_settings` say how it submits each operator, Rust lowers each
placement to one request node, and the first placement it does not
refuse is selected. The physical rules do not run on its plans.

## Test a rule

Write a Rust unit test next to the rule for its rewrite, and a Python
test that plans a query through a session and checks the plan or the
rows it returns. See the
[search tests](https://github.com/fsdatalab/quail/blob/main/tests/planner/test_search.py).
