---
title: Custom Rules
---

An optimizer rule changes a plan while preserving the query's result.
Subclass `LogicalRule` for query trees or `PhysicalRule` for executable graphs.
Both receive the same `PlanningContext`.

## Logical rules

Import `LogicalRule` from `quail.planner.optimizer.rules` and implement
`rewrites(root, context)`. Return a nonempty list of equivalent query tree
roots. The list replaces the input candidate:

| Return | Meaning |
| --- | --- |
| `[root]` | Keep the input unchanged. |
| `[rewritten]` | Replace the input. |
| `[root, rewritten]` | Keep both for cost comparison. |

Include the input root explicitly to keep it. Do not modify input nodes.
Each later rule runs on every returned candidate. The planner removes duplicate
trees and compares costs after physical rules run. On a cost tie, it keeps the
first candidate.

For example, imagine a query that extracts a date from each document and
joins those documents with questions. Extraction can run before or after
the join. This built-in rule proposes the second placement:

```python
from quail.planner.optimizer.rules import LogicalRule
from quail.planner.rules.tree_transforms import lift_maps


class ShouldLiftMaps(LogicalRule):
    name = "should_lift_maps"

    def rewrites(self, root, context):
        rewritten = lift_maps(root)
        return [root] if rewritten is None else [root, rewritten]
```

The planner applies KV retention, prefix sharing, and the other physical
rules to each placement before choosing one.

## Physical rules

Import `PhysicalRule` from `quail.planner.optimizer.rules` and implement
`rewrite(graph, context)`. Return a replacement `PhysicalGraph`, or `None`
to keep the graph. You can also update `context.settings` for this candidate.
Do not modify the input nodes.

A physical rule can compare implementation costs internally. For example,
`should_share_prefixes` enables sharing when saved computation costs more
than the extra KV writes. `should_retain_kv` sets up retention for compatible
later operators without comparing on versus off.

See the [physical rules](https://github.com/fsdatalab/quail/blob/main/quail/planner/rules/physical.py)
for implementations.

## Register a rule

Give each rule a unique `name`, shown in `explain()`. Use `should_...` for
yes/no decisions and `choose_...` to select an implementation.

Create a registry with `ExtensionRegistry.with_built_ins()` and register
your rule with the method matching its base class:

| Base class | Registration |
| --- | --- |
| `LogicalRule` | `registry.register_logical_rule(rule)` |
| `PhysicalRule` | `registry.register_physical_rule(rule)` |

Pass the registry to the session. Quail already registers `ShouldLiftMaps`;
do not register it again. Rules run in registration order within each step:

1. Apply logical `rewrites()` to every candidate in registration order. Remove
   duplicate trees. Repeat until the roots stop changing, up to four passes.
2. Build an executable graph for each tree.
3. Apply physical `rewrite()` methods to each graph in registration order.
4. Select the candidate with the lowest estimated time.

If initial planning used estimated token lengths, repeat the search when
exact tokens are available. See [Optimizer](/docs/architecture/optimizer)
for the built-in rule order.

## Planning context

`PlanningContext` provides the model, device, tokenizer, catalog, token
counts, and estimated fractions of rows kept by filters and joins.
`context.logical_plan` is the current candidate's query tree.

Each executable candidate has separate `settings`. Rules can reuse computed
values through `memo`. Memo keys must include all inputs that affect the value.
See [`optimizer/context.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/optimizer/context.py)
for the fields.

## Test a rule

Call its methods without model inference. Check that the intended fields
change, the input stays unchanged, and the result is equivalent. For an
alternative, check which plan wins after physical rules run.

See the [rule tests](https://github.com/fsdatalab/quail/blob/main/tests/frontend/test_logical_extensions.py)
and [search tests](https://github.com/fsdatalab/quail/blob/main/tests/planner/test_search.py).
