title: Custom Rules
---

An optimizer rule changes a plan while preserving the query's result.
See [Optimizer](/docs/architecture/optimizer) for the built-in rules.

## Define a rule

Each rule has a name, a category, a target, and a `rewrite()` method.

| Field | Meaning |
| --- | --- |
| `name` | Unique name shown in `explain()`. Use `should_...` for yes/no decisions and `choose_...` to select an implementation. |
| `cost_based` | `False` for a universal rule. `True` for a rule that compares alternatives by cost. |
| `target` | `"logical"` for the query tree. `"physical"` for the executable graph. |

`rewrite(plan, context)` receives the tree root or graph named by `target`.
Return a new root or graph when you change it. Return `None` otherwise.
Do not modify the original nodes.

For example, imagine a query that returns review IDs and filters on review
text. The projection rule tells the scan to load IDs for the result and
omit unused columns. The text is still tokenized for the filter.

```python
from quail.planner.rules.tree_transforms import push_down_projection


class ShouldPushDownProjection:
    name = "should_push_down_projection"
    target = "logical"
    cost_based = False

    def rewrite(self, root, context):
        rewritten = push_down_projection(root)
        return None if rewritten is root else rewritten
```

Quail already includes this rule. Use the example as a template for your rule.

## Cost-based rules

For a cost-based tree rule, return an alternative query tree. The planner keeps the
original too, builds both executable plans, and compares their costs after
applying execution settings such as prefix sharing.

For a graph rewrite, compare the supported implementations and return the
chosen graph. The planner includes its cost when comparing complete plans.

## Planning context

All rules receive the same `PlanningContext` type. It provides:

- The model, device, tokenizer, and session catalog.
- Document token counts and estimated fractions of rows kept by filters and joins.
- The logical plan for the current candidate.
- `settings`, where graph rules add execution settings for that candidate.
- `memo`, where rules can reuse computed values within one search.

Each candidate has separate settings. Memo keys must include all inputs
that affect the saved value. See the fields in
[`optimizer/context.py`](https://github.com/fsdatalab/quail/blob/main/quail/planner/optimizer/context.py).

## Register a rule

Create a registry with `ExtensionRegistry.with_built_ins()` and register
your rule:

| Category | Method |
| --- | --- |
| Universal | `registry.register_universal_rule(rule)` |
| Cost-based | `registry.register_cost_based_rule(rule)` |

Pass the registry to the session. Rules share one registration order across
both categories. `registry.rules` lists that order.

The planner:

1. Applies universal tree rewrites until nothing changes, up to four passes.
2. Collects cost-based tree alternatives, keeping the original and removing
   duplicates, up to four passes.
3. Builds executable candidates and applies graph rules in registration order.
4. Selects the candidate with the lowest estimated time.

If initial planning used estimated token lengths, the planner repeats the
search when exact tokens are available.

## Test a rule

Call `rewrite()` without model inference. Check that the intended fields
change, the original plan stays unchanged, and the result is equivalent.
For a cost-based rule, check which plan wins after execution settings are
applied.

See the [rule tests](https://github.com/fsdatalab/quail/blob/main/tests/frontend/test_logical_extensions.py)
and [search tests](https://github.com/fsdatalab/quail/blob/main/tests/planner/test_search.py).
