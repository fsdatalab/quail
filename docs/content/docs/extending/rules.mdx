---
title: Custom Rules
---

Quail implements its planning rules in Rust and registers them by name.

- Logical optimizer rules implement DataFusion's `OptimizerRule` and
  rewrite its logical plan, including `AiNode`s.
- Physical rules rewrite a model region's physical plan or set values
  the executor reads.

## Add a rule

1. Implement the rewrite in Rust. A logical rule returns a rewritten
   `LogicalPlan`. A physical rule returns a replacement graph, or `None`
   when it only changes settings or makes no change.
2. Add the name to `logical_rule` in
   [rules.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/rules.rs)
   or `apply_rule` in
   [physical_rules.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-planner/src/physical_rules.rs).
3. Register a `LogicalRule(name)` with `register_logical_rule()`, or a
   `PhysicalRule(name)` with `register_physical_rule()`. Pass the registry
   to the session.

Use a unique name. Logical rules use `OptimizerRule::name()`.
Physical rules use `should_...` for yes/no decisions or `choose_...` for
implementation choices. Registering a name does not implement the rule.

To turn off a built-in rule, omit its name from the registry.
E.g., create a session without limit pushdown into `AiNode`s:

```python
import quail
from quail.builtins import LOGICAL_RULES, built_in_registry

rules = [name for name in LOGICAL_RULES if name != "push_down_limit_into_ai_nodes"]
registry = built_in_registry(logical_rules=rules)
config = quail.EngineConfig(model="qwen3-4b-fp8", device="h100-sxm")
with quail.Session(config=config, registry=registry) as session:
    pass
```

## Fetch rules

An `AiNode`'s fetch limits rows **after** its exact filter, globally or
per key. Setting it too early changes query results.

- Absorb answer tests before setting a fetch. `absorb_into_ai_nodes`
  does not move tests into a node that already has one.
- Do not move a later filter below a fetch unless it keeps or rejects
  whole per-key groups.
- Check intervening operators and `HINT` before pushing a limit into a node.

See [limit.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/limit.rs)
and [distinct.rs](https://github.com/fsdatalab/quail/blob/main/crates/quail-datafusion/src/distinct.rs)
for the built-in checks.

## Rewrites by number

The table summarizes R1–R17. Conditions here identify the main safety
constraints; the rule implementation defines every accepted plan shape.

| Number | Rule | Change and conditions |
| --- | --- | --- |
| R1 | DataFusion `push_down_filter` | Move an input-only filter below an `AiNode` without a fetch. Above a per-key fetch, move only filters of key columns. |
| R2 | `absorb_into_ai_nodes` | Add an answer test to the node's exact filter when the node has no fetch. |
| R3 | `push_down_hint_tests` | Copy a directly preceding answer test into a column-producing node's hint test. Require no fetch; keep the original filter. |
| R4 | `push_down_substring_prechecks` | Before extraction, test the document for literal text required by an answer's `LIKE` or `ILIKE` pattern. Require no fetch and a non-negated literal pattern; keep the answer test. |
| R5 | `push_down_projection_into_ai_nodes` | Remove unused added columns and extraction questions. Keep all extraction fields when any use reads the whole struct. |
| R6 | `push_down_case_guards` | Ask only where a `CASE WHEN` condition is TRUE. Every use of an added column must have the same condition over the call's table. Require no filter, `HINT`, or fetch. |
| R7 | `push_down_or_guards` | Skip an `AI.IF` when other eligible `OR` terms already pass. Require no existing guard, `HINT`, or fetch. Preserve the OR's row selection. |
| R8 | DataFusion `push_down_limit` | Move a limit through a projection that preserves row count. At an `AiNode`, apply R9 instead. |
| R9 | `push_down_limit_into_ai_nodes` | Set a global fetch from a positive limit, through projections and aliases. Require no `HINT` or per-key fetch; keep the smaller existing limit. |
| R10 | `push_down_limit_into_ai_nodes` | Fetch `LIMIT + OFFSET` rows under R9's conditions. Keep the outer limit and offset. |
| R11 | DataFusion `push_down_limit` | Push limits into `UNION ALL` branches. R9 can then set each branch's AI fetch. Keep the outer limit. |
| R12 | `push_down_distinct` | Fetch one passing row per selected input key or classification label. Require no fetch or `HINT`; keep `DISTINCT`. |
| R13 | `push_down_semi_join_fetch` | Fetch one passing row per semi-join equality key. Require only unguarded `AI.IF` nodes over one table, without joins, fetches, or `HINT`. |
| R14 | `push_down_count_threshold` | Fetch `k` passing rows per group for `HAVING COUNT(*) >= k`. Require positive `k`, column keys, no other aggregate or use of the count, and R13's AI restrictions. |
| R15 | DataFusion dynamic filter | Let a top-k sort reject rows that cannot enter its result. Require no region fetch or stop keys, and enough known values or answer bounds to decide rejection. |
| R16 | DataFusion dynamic filter | Let a hash join reject rows that cannot match its completed build side. Use the same region restrictions as R15. |
| R17 | `merge_repeated_ai_calls` | Reuse an identical earlier call with the same guard across eligible filters or projections. Require no upper fetch and preserve every answer column and test. |

R3 normally has no remaining test after R2. Both exact tests and hint
tests can [stop partial answers](/docs/architecture/execution#evaluation-on-partial-answers).

R4 tests the longest word of the pattern's longest literal run, ignoring
case. This avoids requiring whitespace to match the document exactly.
R5 is safe because extraction asks each field's question separately.
R6 keeps the outer `CASE` for extraction so an unasked row returns a
NULL struct, not a struct of NULL fields.

R13 and R14 can return extra passing rows already in progress when a
key reaches its threshold. The outer semi-join or count test still
returns the same keys.

R15 and R16 act during execution rather than logical optimization.
They reject a row only when its known columns and answer bounds prove
it cannot pass. See [Runtime filters](/docs/architecture/physical-plans#runtime-filters).

## Rule order

DataFusion runs logical rules in registration order. `claim_model_regions`
always runs last. Quail then builds candidate physical plans and applies
physical rules to each candidate before comparing estimated GPU time.

See [Optimizer](/docs/architecture/optimizer) for the built-in order.

## Test a rule

Add a Rust unit test beside the rule to check its rewrite. Add a Python
test through a session to check the returned rows. Include a case where
the rule must not apply. See the
[planner tests](https://github.com/fsdatalab/quail/blob/main/tests/planner/test_search.py).
