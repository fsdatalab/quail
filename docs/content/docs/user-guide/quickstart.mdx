This quickstart runs QUAIL-B's IMDB-1 query over 100 published movie
reviews. The query keeps reviews that mention at least one positive aspect
of the movie.

Model execution requires a CUDA GPU. You can use a local GPU or submit the
same code to a Modal H100.

## 1. Install

Quail requires Python 3.12 and currently installs from this repository.

```bash
git clone https://github.com/fsdatalab/quail-exploration.git
cd quail-exploration
uv sync
```

## 2. Run the example

<Tabs items={['Local GPU', 'Modal H100']}>
<Tab value="Local GPU">

```bash
uv run python demos/quickstart.py
```

</Tab>
<Tab value="Modal H100">

Set up the Modal client once:

```bash
uv run modal setup
```

Then submit the example and keep its full log:

```bash
mkdir -p results
uv run modal run demos/quickstart_modal.py \
  2>&1 | tee results/quickstart.log
```

The command prints a Modal function call id before waiting for the result.
Keep that id in the log so you can retrieve the call after a disconnect.

</Tab>
</Tabs>

The example prints the matching review ids and an execution report. On a
first run, model startup is reported separately from query time.

## 3. Read the query

[`demos/quickstart.py`](https://github.com/fsdatalab/quail-exploration/blob/main/demos/quickstart.py)
does four things:

```python
import quail
import quail_b as benchmark
from quail.bench.quailb import build_query

reviews = benchmark.load_table("reviews", limit=100)
spec = benchmark.get_query("IMDB-1")

with quail.Session() as session:
    session.register(
        "reviews",
        quail.DocumentProvider.from_table(reviews, id_col="id"),
    )
    query = build_query(session, spec)
    result = query.run()
    rows = result.collect()
    report = result.report
```

1. QUAIL-B downloads the public IMDB table and selects 100 reviews.
2. `Session.register()` gives the Arrow table the SQL name `reviews`.
3. `build_query()` reads IMDB-1's saved Substrait plan into Quail.
4. `run()` executes the filter. `collect()` returns an Arrow table.

The equivalent SQL has this shape:

```sql
SELECT r.id
FROM reviews r
WHERE AI_FILTER(PROMPT(
  'Does the review in DOCUMENT {0} mention a positive aspect of the movie?',
  r.body
))
```

The benchmark uses a longer, fixed prompt for scoring. Both versions ask one
true-or-false question about each review.

## 4. Inspect the result

`Query.run()` returns a `QueryResult`:

```python
rows = result.collect()     # pyarrow.Table
count = result.count()      # number of matching rows
metrics = result.report     # query time, token counts, and stage metrics
```

Start with these report fields:

| Field | Meaning |
| --- | --- |
| `wall_s` | Query time in seconds, excluding model startup. |
| `boot_s` | Model startup time. |
| `fresh_tokens` | Input tokens computed in model forward passes. |
| `stages` | Rows or pairs evaluated and kept at each filter or join. |
| `node_metrics` | Metrics for each physical plan node. |

See [Results and explain](/docs/user-guide/results) for every result method
and report field.

## 5. Inspect the plan without a GPU run

Call `explain()` before `run()`:

```python
print(query.explain())
```

The output has two parts:

- The logical plan shows the query's filters, joins, scans, and projection.
- The physical plan shows the chosen backend, token budgets, expected row
  counts, KV reuse, and estimated model time.

Planning tokenizes a sample of each document column, but it does not execute
the model.
