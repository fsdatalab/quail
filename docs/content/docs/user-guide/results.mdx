## Preview the plan

Call `explain()` to see the query plan without running it:

```python
query = session.sql("...", dialect="snowflake")
print(query.explain())
```

Quail runs the query planner and produces the full execution plan,
but does not load the model or run any GPU work.

The output has two parts.

**Logical plan** shows the query structure. Read it bottom-up: scans
are at the leaves, the projection is at the root. Each predicate
appears under the operator that evaluates it.

```text
Project: r.id, a.aspect
  SemanticJoin (full)
    PROMPT('...', r.body, a.aspect) (selectivity=15%)
    Join
      cross
      SemanticFilter
        PROMPT('...', r.body) (selectivity=60%)
        Scan reviews as r [body, id]
      Scan aspects as a [aspect]
```

**Physical plan** shows what the execution engine will do, including
the model, token budgets, estimated row counts, and estimated time
per node.

```text
backend=quail, model=qwen3-4b-fp8, workers=1
KV=bf16, chunk budget=110,376 tokens

Project: r.id, a.aspect
  AiJoin: anchor=r (estimated_seconds=0.003)
    AiFilter: r (estimated_rows=4.8, estimated_seconds=0.004)
      Scan reviews as r (estimated_rows=8)
    Scan aspects as a (estimated_rows=12)
```

`explain(verbose=True)` adds node ids, port connections, KV retention
decisions, and planner remarks.

## Measure the plan

`explain(analyze=True)` works like `EXPLAIN ANALYZE` in DataFusion or
PostgreSQL: it runs the query, then prints the same plan with each
node's measured rows, time, and tokens next to the planner's
estimates, followed by the totals of the run.

```python
print(query.explain(analyze=True))
```

```text
physical: (backend=quail, model=qwen3-4b-fp8, workers=1)
  KV=bf16, chunk budget=110,376 tokens

  Limit: 1 (actual_rows=1, estimated_rows=1, wall_s=0.000)
    Project: r.id (actual_rows=2, estimated_rows=1.5, wall_s=0.000)
      AiFilter: r (actual_rows=2, estimated_rows=1.5, wall_s=0.412, estimated_seconds=0.380, fresh_tokens=60)
        KV rewind=on
        1. PROMPT('...', r.review) (selectivity=50%, observed=66.67%, evaluated=6 documents, question_tokens=10)
        2. PROMPT('...', r.review) (selectivity=50%, observed=50%, evaluated=4 documents, question_tokens=10)
        Scan reviews as r (actual_rows=6, estimated_rows=6, wall_s=0.000)
          tokens=12, mean_doc_tokens=2

measured:
  query time=0.412 s (model startup excluded)
  throughput=14.6 documents/second (6 input documents)
  fresh_tokens=60
  GPU cost=$0.0005/query (1 GPU x $3.9492/hour, startup excluded)
  model startup=41.200 s (cold)
```

Each predicate line shows the selectivity you provided (or the
planner's default) next to the fraction that actually passed and how
many documents or pairs the model evaluated. A large gap between
`selectivity` and `observed` is the usual reason a plan's order or
its estimated time was off.

`explain(analyze=True, verbose=True)` adds every measured field of
each node, including KV hits and misses and GPU seconds.

The query runs once for the measurement. To keep the rows as well,
run it yourself and ask the result for the measured tree:

```python
result = query.run()
rows = result.collect()
print(result.explain())
```

## Refusals

If the planner cannot execute the query, `explain()` prints the
reason instead of a plan, and `run()` raises `quail.RefusalError`.

For example, if a document is too long to fit in one forward pass:

```text
Refused: a document in 'r' needs 131,072 tokens with its prompt,
but the forward pass budget is 110,376 tokens
```

Other common refusals:

- `the model needs 4 GPUs of memory, but Quail loads one complete copy per GPU`
- `per-batch apply() requires one GPU; use apply_table() or set gpus=1`
- `one join pair anchored on 'r' needs 150,000 tokens, but the forward pass budget is 110,376 tokens`

## Running a query

`run()` executes the query on the GPU and returns a `QueryResult`.
`query.collect()` is a shortcut that calls `run().collect()`.

```python
result = query.run()
```

### QueryResult

```python
class QueryResult:
    schema: pa.Schema              # output column schema
    report: dict                   # execution metrics
    plan: PhysicalPlan             # the executed physical plan

    def collect(limit=None) -> pa.Table: ...
    def to_rows(limit=None) -> list[tuple]: ...
    def count() -> int: ...        # len(result) also works
    def execute_stream() -> pa.RecordBatchReader: ...
```

If you are on Modal, collect the rows before returning from the
function.

### Execution report

`result.report` is a dict with query time, token counts, and
per-stage metrics. See [Metrics](/docs/user-guide/metrics) for
every field.
