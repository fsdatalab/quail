---
title: Quail Server
---

Quail Server is an optional HTTP server that runs on the machine with
the GPU. You start it once, and clients send SQL to it by passing
`endpoint` when they create a `Session`. The server compiles the
query, plans it, loads the model, and runs the work. Because that
work lives in the server process, the query continues after your
client exits, and another process can read the same record later.
Several clients share the model the server has already loaded.

A `Session` without `endpoint` still runs in your own process, which
is the path the rest of this guide describes.

## Start the server

Install the `server` extra on the GPU machine. On a machine with one
supported GPU, `quail-server` needs no further options: it accepts
every built-in model, chooses the device from the GPU, stores its
files under `~/.quail/server`, and listens on `127.0.0.1:8642`.

```bash
pip install "quail-engine[server]"
quail-server
```

Each query names the model it wants in `EngineConfig`. The
server reads GPU 0 and maps the CUDA device name onto a Quail device.
A name containing `H100 80GB HBM3` is `h100-sxm`, and a name
containing `RTX PRO 6000 Blackwell` is
`rtx-pro-6000-blackwell-server`. When the process starts, it prints
the device, the models it will accept, the data directory, and the
`endpoint` string to pass to `Session`.

The first query that names a model loads that model's weights and
compiles its kernels. Later queries that name the same model reuse
what is already on the GPU. A query that names a different model
loads that model in place of the first, because one model's weights
and KV fill the GPU.

If CUDA reports no GPU, or a GPU this server does not recognize, the
process prints those two device names and exits. Pass `--device`
with one of them when you want to name the device yourself.

### From another machine

The default address, `127.0.0.1`, accepts connections only from the
machine the server is running on. To accept connections from other
machines, listen on every interface and set a token. The port is
then reachable on the network, and every request under `/v1` has to
present that token.

```bash
QUAIL_SERVER_TOKEN=<token> quail-server --host 0.0.0.0
```

Pass `endpoint="http://<host>:8642"` and set the same
`QUAIL_SERVER_TOKEN` in the client's environment. The client sends
it as a bearer token on each request.

### Options

| Option | Default | Meaning |
| --- | --- | --- |
| `--data-dir` | `~/.quail/server` | Directory for the SQLite file, uploads, and results. Keep it on a disk that survives restarts. |
| `--model` | every built-in model | A model this server accepts. Repeat the option to list more than one. |
| `--device` | this machine's GPU | The device name every query must use. |
| `--gpus` | `1` | A GPU count this server accepts. Repeat the option for more than one count. |
| `--backend` | `quail` | An accepted backend. Repeat the option for more than one. |
| `--host` | `127.0.0.1` | Address to listen on. Use `0.0.0.0` to accept other machines. |
| `--port` | `8642` | Port to listen on. |
| `--default-timeout` | `1000` | Execution limit in seconds when a submission sets none. About 17 minutes. |
| `--max-timeout` | `14400` | Largest limit a submission may set, in seconds. 4 hours. |
| `--max-upload-gib` | `8` | Largest input snapshot accepted, in GiB. |
| `--token` | `QUAIL_SERVER_TOKEN` | Bearer token required on `/v1`. When the variable is unset, no token is required. |

The server keeps one SQLite file, and only that process writes it.
Uploads and result files sit beside the database. Stop the process
and start it again with the same `--data-dir`, and those files are
still there. A query that was `queued` runs after the restart. A
query that was `planning` or `running` is marked `interrupted`;
submit it again if you still want the result.

### What the machine needs

The server needs a CUDA GPU that Quail has specs for: an H100 SXM or
an RTX PRO 6000 Blackwell Server. Each GPU holds one complete copy of
a model. The configurations are on
[Supported models and GPUs](/docs/user-guide/models). Weights download
into the usual Hugging Face cache, and compiled kernels into the
usual kernel cache. DiffusionGemma is gated, so the environment also
needs `HF_TOKEN`, or the weight download fails.

## Connect from Python

Pass `endpoint` to `Session`. Registering tables and running SQL use
the same calls as a local session. This example waits until the
saved result is ready and then reads it.

```python
import quail

config = quail.EngineConfig(model="qwen3-4b-fp8", device="h100-sxm")
with quail.Session(config=config, endpoint="http://127.0.0.1:8642") as session:
    session.register("reviews", quail.DocumentProvider.from_parquet(
        "reviews.parquet", id_col="id"))
    result = session.sql(SQL, dialect="bq").run()
    table = result.collect()
```

`sql()` returns a [`RemoteQuery`](#remotequery). The client talks
HTTP with the Python standard library and reads the
batches with pyarrow. The `server` extra is only required on the
machine that runs `quail-server`. `Session` has no argument for the
token. When the server requires one, set `QUAIL_SERVER_TOKEN` where
the client runs, or construct `quail.server.client.ServerClient` and
pass `token` to it.

## Tables on a remote session

`register` has to hand the server a description it can read after
your process has exited. A provider that cannot be described that
way raises `TypeError` at `register()`, and the table is left
unregistered.

| Provider | What the server receives |
| --- | --- |
| `from_table`, `from_parquet`, `from_ipc`, `from_dataset` | One Arrow IPC file. The file name is the SHA-256 of its bytes. |
| `from_hf` | A Hugging Face dataset, pinned to a commit. If you omit `revision`, the client looks up the current head at `register()` and pins that. |

Before an upload, the client asks whether the server already holds
that hash, so the same table is transferred once no matter how many
queries use it. Once a query has been accepted, its inputs stay on
the server. Closing the session removes the staging files on the
client and leaves the server's copy where it is.

## Submit without waiting

`run()` and `collect()` block until the rows are ready. Call
`submit()` when the query should keep going without the client. It
returns a `QueryRun` as soon as the server has saved the record, and
the query continues if you disconnect. From any later process,
`session.get_run(query_id)` returns a handle to that same run.

```python
with quail.Session(config=config, endpoint=endpoint) as session:
    session.register("reviews", provider)
    run = session.sql(SQL, dialect="bq").submit(
        query_id="nightly-2026-09-21", timeout_s=1000)
```

```python
with quail.Session(config=config, endpoint=endpoint) as session:
    run = session.get_run("nightly-2026-09-21")
    for status in run.watch():
        print(status.state, status.progress)
    result = run.result()
```

The loop in the example is `QueryRun.watch`, documented with the
[other methods](#queryrun). The record it yields is a
[`QueryStatus`](#querystatus).

`cancel()` removes a queued query immediately. On a query that is
already running, it kills the process that has the model loaded, and
the record ends `cancelled`. The next query loads the model again.

The `query_id` you pass names the run, and it is also how you retry
a submission safely. If the response to `submit()` is lost, submit
the same id with the same query and the server returns the run it
already saved. The same id with a different query, engine config,
inputs, or timeout is rejected with HTTP 409,
`QueryIdConflictError`. Leave `query_id` out and the client picks a
random one. An id is 1 to 128 characters. The first character is a
letter or a digit, and the rest may be letters, digits, `.`, `_`,
`:`, or `-`.

`session.session_id` identifies this client session. The server
stores it on every record that session submits, and
`GET /v1/queries?session_id=<id>` lists those records.

A record moves through `queued`, `planning`, and `running`, and then
ends in `succeeded`, `failed`, `interrupted`, or `cancelled`. Once
it is in one of those four ending states, the record stays as it
is. The server marks a record `succeeded` only after it has opened
the saved result, the report, and the answer tables again and
checked that the result file has the row count the run reported.

Each submission has a time limit. Pass `timeout_s`, or leave it
unset to use the server's `--default-timeout`. The clock starts when
execution starts, after the query has left the queue. A query that
runs past the limit ends `failed` with error type `TimeoutError`,
and the model process is killed the same way as on cancel. A limit
above `--max-timeout` is rejected when you submit.

## RemoteQuery

`session.sql` on a server session returns a `RemoteQuery`. It holds
the statement text. The server compiles and plans that text when the
query runs. A local session returns a
[`Query`](/docs/user-guide/results#query) instead. After you submit,
the plan text is on the record at `QueryStatus.plan["text"]`.

#### Attributes

| Attribute | Description |
| --- | --- |
| `session` | The `Session` that created this query. |
| `sql` | The statement text. |
| `dialect` | `bq` or `snowflake`. |
| `order` | Predicate order passed to `sql`, or `None`. |

#### Methods

##### submit

`RemoteQuery.submit(query_id=None, timeout_s=None)`

Send the query to the server and return once the record is saved. The
query keeps running if the client disconnects. Submitting the same
`query_id` with the same statement, engine config, inputs, and timeout
returns the existing run. The same id with a different submission is
HTTP 409, `QueryIdConflictError`.

**Parameters**

| Name | Description |
| --- | --- |
| `query_id` | Name of the run. Omit it and the client picks a random id. An id is 1 to 128 characters: a letter or digit, then letters, digits, `.`, `_`, `:`, or `-`. |
| `timeout_s` | Execution limit in seconds, starting when the query leaves the queue. Omit it to use the server's `--default-timeout`. A value above `--max-timeout` is rejected. |

**Returns**

`QueryRun`.

##### run

`RemoteQuery.run(timeout_s=None)`

Submit the query, wait until the saved result is ready, and return it.
A record that ended `failed`, `interrupted`, or `cancelled` raises
`QueryFailedError`. The exception carries the saved status.

**Parameters**

| Name | Description |
| --- | --- |
| `timeout_s` | Passed through to `submit`. |

**Returns**

[`QueryResult`](/docs/user-guide/results#queryresult).

##### collect

`RemoteQuery.collect(limit=None, batch_rows=65536)`

Submit the query, wait, and return one Arrow table.

**Parameters**

| Name | Description |
| --- | --- |
| `limit` | Stop after this many rows. |
| `batch_rows` | Accepted so the call matches a local `Query`. The server chooses the batch size, and this argument is ignored. |

**Returns**

`pyarrow.Table`.

##### execute_stream

`RemoteQuery.execute_stream(batch_rows=65536, limit=None)`

Submit the query, wait, and stream the rows.

**Parameters**

| Name | Description |
| --- | --- |
| `batch_rows` | Accepted so the call matches a local `Query`. The server chooses the batch size, and this argument is ignored. |
| `limit` | Stop after this many rows. |

**Returns**

`pyarrow.RecordBatchReader`.

## QueryRun

A handle to one record the server has accepted. `submit` returns one.
`session.get_run(query_id)` returns a handle to a record that is
already there.

#### Attributes

| Attribute | Description |
| --- | --- |
| `id` | The query id. |

#### Methods

##### status

`QueryRun.status()`

Read the current saved record.

**Returns**

`QueryStatus`.

##### watch

`QueryRun.watch(poll_s=30)`

Yield the current record, then each newer revision, until the query
is finished. The default poll is 30 seconds, so a progress update
that was replaced before the next poll is skipped. A lost connection
raises `ServerError`. Calling `watch` again continues from the record
as it stands then.

**Parameters**

| Name | Description |
| --- | --- |
| `poll_s` | Seconds to hold each long-poll open. The server stops the hold at 60 seconds. |

**Returns**

An iterator of `QueryStatus`.

##### result

`QueryRun.result(poll_s=30)`

Wait until the record is finished and return the saved rows. A record
that ended `failed`, `interrupted`, or `cancelled` raises
`QueryFailedError`, and the exception carries the saved status.

**Parameters**

| Name | Description |
| --- | --- |
| `poll_s` | Seconds between polls while waiting. The default is 30. |

**Returns**

[`QueryResult`](/docs/user-guide/results#queryresult), built from the
saved Arrow files and the report.

##### stream_result

`QueryRun.stream_result(poll_s=30)`

Wait until the record is finished, then stream the rows. The failure
behavior matches `result`.

**Parameters**

| Name | Description |
| --- | --- |
| `poll_s` | Seconds between polls while waiting. The default is 30. |

**Returns**

`pyarrow.RecordBatchReader`. The server chooses the batch size.

##### cancel

`QueryRun.cancel()`

Ask the server to stop this query. A queued query ends immediately.
A query that is already running has its model process killed, and the
record ends `cancelled`. The next query loads the model again.

**Returns**

`QueryStatus`. The snapshot after the cancel request.

##### answers

`QueryRun.answers(after=0, limit=1000)`

Return answer entries saved so far, starting at entry `after`. The
entry shapes are in [Answers while the query runs](#answers-while-the-query-runs).

**Parameters**

| Name | Description |
| --- | --- |
| `after` | First entry index to return. |
| `limit` | Maximum entries in this page. The default is 1,000 and the server stops at 10,000. |

**Returns**

A dict with `answers` (the entries), `next` (the index to pass as
`after` on the next call), and `done` (whether more entries can still
arrive).

##### stream_answers

`QueryRun.stream_answers(poll_s=30)`

Yield each saved answer entry in order. The iterator returns when the
query is finished and every saved entry has been yielded.

**Parameters**

| Name | Description |
| --- | --- |
| `poll_s` | Seconds between polls. The default is 30. |

**Returns**

An iterator of answer dicts.

## QueryStatus

One saved snapshot of a query record. `status`, `watch`, and
`GET /v1/queries/{id}` return this object. Every write replaces the
snapshot and increases `revision`. A record in `succeeded`, `failed`,
`interrupted`, or `cancelled` stays as it is. The server writes
`succeeded` only after it has opened the saved result, the report,
and the answer tables again and checked the result's row count.

#### Attributes

| Attribute | Description |
| --- | --- |
| `id` | The query id. |
| `state` | `queued`, `planning`, `running`, `succeeded`, `failed`, `interrupted`, or `cancelled`. |
| `revision` | Integer that increases on every write. |
| `created_at` | Unix seconds when the record was saved. |
| `updated_at` | Unix seconds of the latest write. |
| `started_at` | Unix seconds when the record left `queued`, or `None` while it is still queued. |
| `timeout_s` | Execution limit in seconds. |
| `session_id` | The client session that submitted the record, or `None`. |
| `cancel_requested` | True after a cancel request has been recorded. |
| `spec` | The SQL submission. Keys are below. |
| `config` | The engine config. Keys are below. |
| `inputs` | Registered table name to the stored input description. Shapes are below. |
| `progress` | The latest engine count, or `None` before the first one. Keys are below. |
| `plan` | The plan, or `None` until planning has finished. Keys are below. |
| `error` | The error, or `None` unless the record ended `failed`, `interrupted`, or `cancelled`. Keys are below. |
| `result` | The result manifest, or `None` until the record is `succeeded`. Keys are below. |
| `done` | True when `state` is an ending state. |

##### spec

| Key | Description |
| --- | --- |
| `sql` | The statement text. |
| `dialect` | `bq` or `snowflake`. |
| `order` | Predicate order, or null. |

##### config

| Key | Description |
| --- | --- |
| `model` | Model name from `EngineConfig`. |
| `device` | Device name from `EngineConfig`. |
| `gpus` | GPU count. |
| `backend` | Backend name. The default submission sends `quail`. |

##### inputs

Each value is one registered table.

A snapshot has `kind` `"snapshot"`, `content_id` (the SHA-256 of the
Arrow file), `id_col`, and `columns`.

A Hugging Face dataset has `kind` `"hf"`, `dataset`, `config`,
`split`, `revision`, and `id_col`.

##### progress

| Key | Description |
| --- | --- |
| `label` | What the engine is counting. |
| `done` | How many units have finished. |
| `total` | How many units were expected, or null when the total is open. |
| `unit` | The unit, such as `documents`, `scores`, or `anchors`. |
| `recorded_at` | Unix seconds of this count. |
| `answers_saved` | How many answer entries are stored. |

##### plan

| Key | Description |
| --- | --- |
| `text` | The plan printout. |
| `estimated_seconds` | The planner's time estimate. |
| `backend` | Backend that will run the plan. |
| `workers` | Worker count. |
| `envelope` | The same plan encoded for the executor. |

##### error

| Key | Description |
| --- | --- |
| `type` | Exception name, such as `TimeoutError`, `Cancelled`, or `Interrupted`. |
| `message` | The error text. |
| `traceback` | Present when the executor raised. |

##### result

| Key | Description |
| --- | --- |
| `rows` | Row count of the output file. |
| `columns` | Output column names. |
| `files.result` | Relative path of the Arrow file of output rows. |
| `files.report` | Relative path of the execution report. |
| `files.answers.filters` | Filter answer tables. Each entry has `alias`, `position`, and `file`. |
| `files.answers.joins` | Join answer tables. Each entry has `position` and `file`. |

## Answers while the query runs

The engine reports answers as it produces them, and the server saves
each report, so a client can show rows filling in before the final
result exists.

A filter report is one chunk of finished documents. Each document is
a row index, the last stage that was asked, and whether the document
passed. A join report arrives when an anchor document is finished.
`matches` lists the partner rows that answered true, and `asked` is
how many pairs were evaluated. `AI.SCORE` reports one batch of
scores, with `rows` and `scores` in the same order. An `evict` entry
is one document prefix dropped from KV: the alias, the row index,
and the length in tokens.

```python
for entry in run.stream_answers():
    if entry["kind"] == "filter":
        survivors = [row for row, _stage, passed in entry["documents"] if passed]
    elif entry["kind"] == "join":
        print(entry["anchor"], entry["document"],
              len(entry["matches"]), "of", entry["asked"])
    elif entry["kind"] == "score":
        ...
    elif entry["kind"] == "evict":
        print(entry["alias"], entry["document"], entry["tokens"])
```

`stream_answers()` yields those entries in order and returns when the
query is finished and every saved entry has been yielded.
`answers(after=N)` returns the entries saved so far, starting at
entry `N`, together with `next` (the entry to ask for next) and
`done` (whether more entries can still arrive). The count stored on
the record is `status().progress["answers_saved"]`. Entries carry
row indexes, which line up with the saved answer tables. The
document text is in those tables and in the final result.

## Reading the plan

The server compiles and plans the query as part of running it, so
the plan is ready once the record has left `planning`. Read it from
`run.status().plan["text"]` after you submit. Write the query in
SQL. The server runs the plan it chose. Planning the query in this
process, before it runs, is what a local
[`Query`](/docs/user-guide/results#query) does. The Python builder
is part of that same local session.

## In the browser

Open `http://<host>:8642/queries/<query_id>` for a page that shows
the state, the progress, the plan, any error, the SQL, the inputs,
and a preview of the first 20 result rows. The page follows the
record with server-sent events, so it updates while the query runs.
`http://<host>:8642/` lists recent queries.

The page calls the same `/v1` routes as the Python client, so it
needs the token when the server was started with one. Open the page
once with `#token=<token>` on the end of the URL. The page saves the
token in that browser's local storage and then removes it from the
address bar. If no token is saved and a request comes back
unauthorized, the page asks for one. Links to the result and the
report are fetched with the token and then saved, because following
a plain link does not send the header.

## HTTP API

Clients, including the status page, talk to the server over these
routes. When the server was started with a token, every `/v1` route
expects `Authorization: Bearer <token>`. The browser loads the two
HTML pages without that header, and the page attaches the token to
the API calls it makes.

| Route | Purpose |
| --- | --- |
| `GET /v1/capabilities` | Models, device, GPU counts, backends, and the timeout and upload limits |
| `HEAD /v1/inputs/{content_id}` | `200` when this snapshot is already stored, `404` when it is not |
| `PUT /v1/inputs/{content_id}` | Upload one Arrow IPC file. `content_id` is the lowercase SHA-256 hex digest of the bytes |
| `POST /v1/queries` | Submit a query. Returns the saved record with HTTP 201 |
| `GET /v1/queries?limit=&session_id=` | Recent records, newest first. `limit` defaults to 50 and stops at 500 |
| `GET /v1/queries/{id}?after=N&wait=S` | The record, holding the request open for up to `S` seconds until the revision passes `N`. `S` stops at 60 |
| `GET /v1/queries/{id}/events` | Server-sent events, one per revision |
| `POST /v1/queries/{id}/cancel` | Cancel the query |
| `GET /v1/queries/{id}/result` | The result rows as an Arrow stream. The row count is the `x-quail-rows` header |
| `GET /v1/queries/{id}/files/{name}` | One file named in the record's result manifest, as stored on disk |
| `GET /v1/queries/{id}/rows?limit=` | The first rows as JSON, for the status page. `limit` defaults to 20 and stops at 1000 |
| `GET /v1/queries/{id}/answers?after=N&limit=` | Answer entries from entry `N` on. `limit` defaults to 1000 and stops at 10000 |
| `GET /queries/{id}` | The status page for one query |
| `GET /` | The list of recent queries |

A submission body has `sql`, `dialect`, `order`, `config`, `inputs`,
`query_id`, `session_id`, and `timeout_s`. `dialect` is `bq` or
`snowflake`, the same values as `session.sql`.

## On Modal

You can also host the server on Modal. `quail.server.modal_app`
deploys it as one web endpoint on the existing `quail-engine` app,
backed by one H100. Hosting it there is optional. The `quail-server`
command above runs on any machine with a supported GPU.

```bash
modal secret create quail-server-token QUAIL_SERVER_TOKEN=<token>
modal deploy -m quail.server.modal_app
```

`modal deploy` prints the endpoint URL. Pass that URL as `endpoint`.
The URL is public, so create the token before you deploy. The secret
is named `quail-server-token` and holds `QUAIL_SERVER_TOKEN`. Clients
set the same variable. The deployment accepts the same built-in
models as a server you start yourself: `qwen3-4b-fp8`,
`qwen3-32b-fp8`, `diffusion-gemma-26b-a4b-fp8`,
`qwen3-reranker-0.6b-bf16`, and `qwen3-reranker-4b-bf16`.

Results and uploaded inputs are written to the `quail-results` Volume
under `/results/quail-server/`. The live SQLite file stays on the
container's local disk, at `/tmp/quail-server/quail.sqlite3`. A Modal
Volume has no file locking, and an in-place write can rewrite a
whole file, so SQLite runs on the local disk. A checkpoint thread
copies the database onto the Volume with SQLite's online backup,
which includes the write-ahead log, and then calls
`volume.commit()`.

The server makes that copy and commits it before it returns a new
query id, so an id you have received is on the Volume. A change of
state is copied within one second. A write that only moved a
progress counter is copied at most every 30 seconds.

When a new container starts, it copies the database back from the
Volume before it serves requests. `max_containers=1` keeps a single
writer. An idle container stops after 15 minutes, and the next
request starts a new one. The first query on that container loads
the model again.
