---
title: Quail Server
---

Quail Server is the HTTP server for remote queries. Point a `Session`
at it with `endpoint`. The client sends SQL. The server compiles the
query, runs it, and stores the record and the result. The query
continues after the client disconnects.

Omit `endpoint` to run the query in the client process. That path
does not start Quail Server.

## Start the server

On a machine with one supported GPU:

```bash
pip install "quail-engine[server]"
quail-server
```

With no options, `quail-server`:

- serves every built-in model. Each query still names its model.
- selects the device from GPU 0. A CUDA name containing
  `H100 80GB HBM3` is `h100-sxm`. A name containing
  `RTX PRO 6000 Blackwell` is `rtx-pro-6000-blackwell-server`.
- stores the SQLite file, uploads, and results in `~/.quail/server`.
- listens on `127.0.0.1:8642`.

It prints the device, the models, the data directory, and the
`endpoint` string to pass to `Session`. The first query loads its
model. A later query that asks for the same model reuses it.

If there is no CUDA GPU, or the GPU is not one of those two, the
process exits. Pass `--device` with `h100-sxm` or
`rtx-pro-6000-blackwell-server`.

### Accept connections from other machines

```bash
QUAIL_SERVER_TOKEN=<token> quail-server --host 0.0.0.0
```

Set `QUAIL_SERVER_TOKEN` to the same value in the client environment.
Clients pass `endpoint="http://<host>:8642"`.

### Options

| Option | Default | Meaning |
| --- | --- | --- |
| `--data-dir` | `~/.quail/server` | SQLite file, uploads, and results |
| `--model` | every built-in model | A model this server accepts. Repeat for more than one |
| `--device` | this machine's GPU | Device name every query must use |
| `--gpus` | `1` | A GPU count this server accepts. Repeat for more than one |
| `--backend` | `quail` | An accepted backend. Repeat for more than one |
| `--host` | `127.0.0.1` | Bind address. `0.0.0.0` accepts other machines |
| `--port` | `8642` | Port |
| `--default-timeout` | `1000` | Execution limit, in seconds, when a submission sets none |
| `--max-timeout` | `14400` | Largest limit a submission may set, in seconds |
| `--max-upload-gib` | `8` | Largest input snapshot, in GiB |
| `--token` | `QUAIL_SERVER_TOKEN` | Bearer token required on `/v1`. No token when unset |

Restart the server on the same `--data-dir`. Saved results are still
there, and a `queued` query runs. A query that was `planning` or
`running` is marked `interrupted`.

### What you need

- An H100 SXM or an RTX PRO 6000 Blackwell Server.
- One GPU for each copy of a model. Quail does not shard one model's
  weights across GPUs.
- `HF_TOKEN` for a gated model, such as DiffusionGemma.

## Connect

```python
import quail

config = quail.EngineConfig(model="qwen3-4b-fp8", device="h100-sxm")
with quail.Session(config=config, endpoint="http://127.0.0.1:8642") as session:
    session.register("reviews", quail.DocumentProvider.from_parquet(
        "reviews.parquet", id_col="id"))
    result = session.sql(SQL, dialect="bq").run()
    table = result.collect()
```

- `run()` submits the query, waits, and returns a `QueryResult`.
- `collect()` does the same and returns one Arrow table.
- `execute_stream()` waits, then streams the rows as Arrow record
  batches. The server picks the batch size, so `batch_rows` is
  ignored. `limit` applies.
- The client does not need the `server` extra.
- `Session` has no token argument. Set `QUAIL_SERVER_TOKEN`, or
  construct `quail.server.client.ServerClient(endpoint, token=...)`.

## Tables

`register` describes each table so the server can read it. Anything
else raises `TypeError` at `register()`.

| Provider | What is sent |
| --- | --- |
| `from_table`, `from_parquet`, `from_ipc`, `from_dataset` | One Arrow IPC file, named by the SHA-256 of its bytes |
| `from_hf` | A Hugging Face dataset pinned to a commit. With no `revision`, the current head is pinned at `register()` |

The client skips the upload when the server already has that hash.
Closing the session deletes only the client's local staging files.

## Submit

`submit()` returns once the record is saved. You can disconnect and
reattach later, from this process or another one.

```python
with quail.Session(config=config, endpoint=endpoint) as session:
    session.register("reviews", provider)
    run = session.sql(SQL, dialect="bq").submit(
        query_id="nightly-2026-09-21", timeout_s=1000)
```

```python
with quail.Session(config=config, endpoint=endpoint) as session:
    run = session.get_run("nightly-2026-09-21")
    for status in run.watch():
        print(status.state, status.progress)
    result = run.result()
```

`session.get_run(id)` does not submit the query again.

- `status()` returns the saved record: `state`, `revision`,
  `progress`, `plan`, `error`, `result`, and the submission.
- `watch()` yields the current record, then each newer `revision`,
  until the query is done. The default poll is 30 seconds.
- `result()` waits and returns the `QueryResult`. It raises
  `QueryFailedError` when the record is `failed`, `interrupted`, or
  `cancelled`.
- `stream_result()` waits, then streams the rows as Arrow record
  batches.
- `cancel()` cancels a `queued` query immediately. On a running query
  it kills the process that holds the model, and the record becomes
  `cancelled`. The next query loads the model again.

`query_id` is the name of the run. Submit the same id with the same
query and the server returns the existing run. The same id with a
different query, config, inputs, or timeout is HTTP 409,
`QueryIdConflictError`. Omit `query_id` and the client generates one.
An id is 1 to 128 characters: a letter or digit, then letters,
digits, `.`, `_`, `:`, or `-`.

`session.session_id` is stored on every record from that session.
`GET /v1/queries?session_id=<id>` lists them.

The states are `queued`, `planning`, `running`, `succeeded`,
`failed`, `interrupted`, and `cancelled`. A record in one of the last
four does not change. The server sets `succeeded` only after it has
reread the result, the report, and the answer tables.

`timeout_s` is the execution limit, counted from when the query
starts running. When you omit it, the server uses `--default-timeout`.
A query that exceeds the limit is `failed` with error type
`TimeoutError`, and the model process is killed. A limit above
`--max-timeout` is rejected.

## Answers while the query runs

The server stores answer entries as the engine produces them.

```python
for entry in run.stream_answers():
    if entry["kind"] == "filter":
        survivors = [row for row, _stage, passed in entry["documents"] if passed]
    elif entry["kind"] == "join":
        print(entry["anchor"], entry["document"],
              len(entry["matches"]), "of", entry["asked"])
    elif entry["kind"] == "score":
        ...  # entry["rows"] and entry["scores"]
    elif entry["kind"] == "evict":
        print(entry["alias"], entry["document"], entry["tokens"])
```

- `filter`: one chunk of documents, each `[row, last stage, passed]`.
- `join`: one finished anchor. `matches` lists the partner rows that
  answered true, out of `asked` pairs.
- `score`: one batch of reranker scores.
- `evict`: one document prefix dropped from KV, in tokens.
- `answers(after=N)` returns the entries from `N` on, plus `next` and
  `done`. `status().progress["answers_saved"]` is the count on the
  record.

Entries carry row indexes, not document text.

## Unsupported

- `explain()` and `plan()` before the query runs. After you submit,
  the plan text is `run.status().plan["text"]`.
- `session.docs`. Write the query in SQL.
- `run(plan=...)`. The server runs the plan it chose.

## Browser

Open `http://<host>:8642/queries/<query_id>` for the state, progress,
plan, error, SQL, inputs, and the first 20 result rows. The page
updates from server-sent events. `http://<host>:8642/` lists recent
queries.

When the server has a token, open the page once as
`.../queries/<query_id>#token=<token>`. The page stores the token in
local storage and removes it from the address bar. Result links are
fetched with that token, because a normal link cannot send the
header.

## HTTP API

`/v1` routes require `Authorization: Bearer <token>` when a token is
set. The HTML pages do not.

| Route | Purpose |
| --- | --- |
| `GET /v1/capabilities` | Models, device, GPU counts, backends, limits |
| `HEAD /v1/inputs/{content_id}` | `200` if this snapshot is already stored, otherwise `404` |
| `PUT /v1/inputs/{content_id}` | Upload one Arrow IPC file. `content_id` is its SHA-256 hex digest |
| `POST /v1/queries` | Submit. Returns the saved record, HTTP 201 |
| `GET /v1/queries?limit=&session_id=` | Recent records, newest first |
| `GET /v1/queries/{id}?after=N&wait=S` | The record, waiting up to `S` seconds for a newer revision |
| `GET /v1/queries/{id}/events` | Server-sent events, one per revision |
| `POST /v1/queries/{id}/cancel` | Cancel |
| `GET /v1/queries/{id}/result` | Result rows as an Arrow stream. Row count is `x-quail-rows` |
| `GET /v1/queries/{id}/files/{name}` | One file named in the result manifest |
| `GET /v1/queries/{id}/rows?limit=` | The first rows as JSON |
| `GET /v1/queries/{id}/answers?after=N&limit=` | Answer entries from `N` on |
| `GET /queries/{id}` | Status page |
| `GET /` | Recent queries |

`POST /v1/queries` takes `sql`, `dialect`, `order`, `config`,
`inputs`, `query_id`, `session_id`, and `timeout_s`.

## On Modal

Modal is one way to host the server. `quail-server` on your own
machine does not use it.

```bash
modal secret create quail-server-token QUAIL_SERVER_TOKEN=<token>
modal deploy -m quail.server.modal_app
```

`modal deploy` prints the URL. Pass it as `endpoint`. The URL is
public, so the token is required. The deployment is one H100
container on the `quail-engine` app, and it accepts the built-in
models.

- Results and uploads are written to the `quail-results` Volume at
  `/results/quail-server/`.
- The live SQLite file is `/tmp/quail-server/quail.sqlite3` on the
  container disk. A Volume has no file locking, so SQLite does not
  run on the Volume. A checkpoint copies the database to
  `/results/quail-server/quail.sqlite3` and calls `volume.commit()`.
- That copy is committed before the server returns a new query id.
  A state change is copied within 1 second. A progress update is
  copied at most every 30 seconds.
- A new container restores the database before it serves requests.
  `max_containers=1`.
- An idle container stops after 15 minutes. The next request starts
  a container, and the first query loads the model.
