# Filter profiling results

Date: 2026-08-18. One H100 on Modal. Qwen3 4B fp8. All data files are
in `results/`. Plots are generated by `reports/make_plots.py`.

## What we found

We profiled a 3,000-document, 5-filter run (1.15M fresh tokens, 21
chunks) with `torch.profiler`. The profiled run took 29.0 s wall time,
but the GPU was busy for only 14.6 s. The GPU was idle for half the
run.

Two things caused the slowdown:

- The Python loop between chunks (packing, admission, result
  collection) left the GPU with nothing to do between forward passes.
  The idle time was 14.5 s.
- The KV scatter (writing each document's KV into the arena's pages)
  used 432,756 separate `index_copy_` calls, one per document per
  layer per chunk. Each call was tiny, and the GPU launch overhead
  per call was larger than the actual byte movement.

## GPU time breakdown

The profile was captured before the batched KV-write fix described
below. The KV scatter cost in these numbers reflects the old
per-document-per-layer `index_copy_` path. After the fix, the KV
scatter segment would be much smaller.

The plot `plots/profile_categories.png` shows where the 14.6 s of GPU
busy time went. Here is the same data as a table:

| Category | GPU time (s) | Share |
|---|---|---|
| GEMM (DeepGEMM fp8 linear projections) | 5.96 | 41% |
| KV scatter (`index_copy_`) | 1.86 | 13% |
| Fused Triton kernels (silu/norm/quant) | 1.61 | 11% |
| Attention (flash_attn + paged cross) | 0.89 | 6% |
| fp8 quantization | 0.83 | 6% |
| Copies and other | 3.45 | 24% |

The ideal GEMM time at peak hardware rates is 4.18 s, so the measured
GEMMs ran at about 70% of peak. The gap comes from drain chunks
(the last few chunks have fewer tokens and use smaller, less efficient
GEMM configurations).

One note on absolute numbers: the profiler slows everything down
(29.0 s profiled compared with about 11 s unprofiled for 3,000 docs),
because it records every kernel launch. The relative shares are still
meaningful.

## The KV scatter problem

Before this profile, we estimated the KV scatter cost at 0.3 s, based
on the raw byte volume at memory bandwidth. The actual cost was much
higher because of how the copies were issued.

The path was: `pack_chunk` recorded one write per document, and then
`attention()` ran each write as a separate `index_copy_` call on every
one of the 36 layers. With about 570 writes per chunk, that was about
20,600 kernel launches per chunk. Each launch copied a few hundred
rows into non-contiguous arena pages.

The raw bytes were small (about 520 GB total at 2 TB/s is 0.3 s), but
the per-launch overhead of 432,756 tiny calls added up to 1.86 s of
GPU time, and the CPU-side dispatch cost showed up as gaps between
kernels.

## The fix

We batched the writes. `pack_chunk` now builds one index tensor per
chunk with all the destination rows concatenated, and `attention()`
does one gather and one scatter per K and V pool per layer. The total
launches per chunk dropped from about 20,600 to 144. The bytes moved
are the same.

Code changes: `quail/executor/loop.py` (the `kv_src`/`kv_dst` tensors
in `pack_chunk`) and `quail/executor/attention.py`. The per-document
`KVArena.write` method was removed.

## Results after the fix

We re-ran the probe and filter gates on the same hardware.

- Probe: zero disagreements on every check. The batching changed
  launch order, not arithmetic.
- Filter (10,000 documents, 5 filters, 2 reps):
  - Before the fix: 39.4 s wall, 37.6 s GPU, 97,300 tokens/s
  - After the fix: 35.8 s wall, 33.4 s GPU, 107,200 tokens/s
  - GPU time per token fell from 9.9 to 8.7 microseconds
- The 4.2 s of saved GPU time is more than the 1.86 s of copy
  kernel time, which confirms that the CPU-side launch gaps were the
  larger half of the cost.
- Survivors, answers, and wrong counts are unchanged (1,807 survivors,
  23,113 answered, 6,294 wrong against planted labels).

## Comparison with stock vLLM

The plot `plots/vs_stock.png` shows the before/after comparison on
both milestone workloads.

| Workload | Stock vLLM (tuned) | Quail (after fix) | Speedup |
|---|---|---|---|
| 5-filter chain, 10k docs | 38.7 to 39.0 s | 35.8 s | 1.08x |
| 72k-pair join | 90.3 to 92.7 s | 31.1 s | 2.9x |

The stock filter baseline used separate requests per (document,
stage), pipelined submission, document-cap admission, and a token
budget of 374,891 (the bf16-KV equivalent of our budget). The stock
join baseline used one request per pair, anchor-major order, and
prefix caching.

On two GPUs, the dispatch gate holds: filter 1.99x, join 2.02x
(`dispatch_gate.json`).

## What is still on the table

- The remaining wall-minus-GPU gap is about 2.4 s per 10k run (35.8 s
  wall against 33.4 s GPU). The gap is answer readback and Python
  scheduling between chunks.
- GEMMs at 70% of peak. The drain chunks (few tokens, small GEMM
  shapes) are the main cause. Merging drain work into fewer chunks
  could help, or we accept the tail cost of continuous admission.
