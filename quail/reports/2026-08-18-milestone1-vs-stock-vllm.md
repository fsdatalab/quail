# Milestone 1: Quail compared with stock vLLM

Date: 2026-08-18. One H100 on Modal (two for the scaling check).
Qwen3 4B fp8 weights, bf16 KV on both sides. All data files are in
`results/`. Plots are generated by `reports/make_plots.py`.

Related reports:
- `2026-08-18-filter-profiling.md` covers the KV-write fix that
  produced the current filter numbers.
- `2026-08-19-quailb-sf0.1.md` covers the full benchmark suite
  (rerun after the KV-write fix). The pre-fix numbers are in
  `2026-08-18-quailb-sf0.1.md`.

## How we set up the comparison

Both sides use the same model, the same engine step size (25,305
tokens), and the same KV data type (bf16). Prefix caching is on for
stock vLLM.

For filters, the stock client uses the committed document-cap
admission strategy: a budget of 374,891 tokens (the bf16 equivalent
of our arena budget), expressed as a cap on live documents. Quail
runs its arena admission at the same budget.

For joins, the stock client submits one request per (anchor, partner)
pair in anchor-major order, so the prefix cache gets the best
possible hit pattern. Quail packs multiple pairs into one forward
pass and shares the anchor's KV pages across all of them.

## Results

The plot `plots/vs_stock.png` shows the comparison on both workloads.

| Workload | Stock vLLM | Quail | Speedup |
|---|---|---|---|
| 5-filter chain, 10k docs | 38.7 to 39.0 s | 35.8 s | 1.08x |
| 72k-pair join | 69.8 to 70.6 s | 31.1 s | 2.3x |

## Filter chain details

The workload is 10,000 synthetic documents (mean 320 tokens each),
five filter stages where survivors advance to the next stage, on one
H100.

| | Stock vLLM | Quail |
|---|---|---|
| Wall time (2 reps) | 38.98 / 38.72 s | 35.76 / 35.85 s |
| Fresh tokens | 3.92M / 3.94M | 3.83M |
| Tokens per second | about 101,000 | about 107,000 |
| Requests or answers | 23,388 / 23,381 | 23,113 |
| Survivors | 1,875 / 1,873 | 1,807 |

What these numbers mean:

- The fresh token counts are close (within 3%). Stock vLLM's prefix
  cache keeps most document KV between filter stages on this workload
  because the pool is large enough. Quail's advantage here is not
  that it computes fewer tokens. Quail guarantees residency through
  admission arithmetic instead of relying on cache eviction, and it
  runs a simpler execution path (no per-request scheduling, one
  packed forward pass per chunk).
- The margin is 8%. On filters at this corpus size, when the stock
  pool is not under pressure, 8% is the honest size of the win.
- Survivors differ by 3.5% (1,807 compared with 1,873). Both engines
  run the same weights. The differing answers come from numerical
  near-ties that flip with accumulation order. Wrong-answer rates
  against the planted labels are similar: 27.2% for Quail, 26.6% for
  stock. Neither side is more correct.

## Join details

The workload is 60 anchor documents (reports, about 3,000 tokens
each) joined against 1,200 candidates each, for 72,000 pairs total,
on one H100.

Stock vLLM submits one request per pair in anchor-major order with
prefix caching. Quail packs multiple pairs into one chunk and shares
the anchor's KV pages across all pairs in that chunk.

| | Stock vLLM | Quail |
|---|---|---|
| Wall time | 70.6 / 69.8 s | 31.1 s |
| Fresh tokens computed | 1.01M | 2.64M |
| Pairs answered | 72,000 | 72,000 |

The interesting number is the fresh token column. Stock vLLM computed
2.6x fewer fresh tokens because prefix caching avoids recomputing
each anchor. But stock still took 2.3x longer. The reason is that
every pair is still its own request: the engine re-reads the anchor's
cached KV through attention for each pair, and pays per-request
scheduling overhead at every step. Quail makes the anchor's pages a
shared operand, so 32 pair-suffixes attend to one anchor's KV inside
a single packed chunk.

The stock baseline uses max_num_seqs=4096, the same cap as the filter
baseline, so the scheduler can fill steps properly. An earlier run
used max_num_seqs=366 (derived from the KV budget divided by the full
pair length, ignoring prefix-cache sharing) and measured 90-93 s; the
fix to 4096 cut 22 s. Raising max_num_batched_tokens from 25,305 to
100,000 did not help further (75-77 s), confirming that the remaining
overhead is per-request scheduling inside vLLM, not step
underutilization.

The committed exploration measured 4.1x on the BioDEX shape (longer
anchors, so more re-read cost per pair). The 2.3x here is on a
synthetic shape with shorter anchors.

## Two-GPU scaling

Quail ran both workloads on two GPUs: filter 1.99x faster, join
2.02x faster compared with one GPU (`dispatch_gate.json`). We did
not build a multi-GPU stock baseline, so no multi-GPU comparison is
claimed.

## What this report does not cover

- No warm-pass comparison. Quail's KV store measured 11.7 s warm
  compared with 31.3 s cold at 5,000 documents, but we have not
  built the equivalent stock warm scenario (a long-lived stock engine
  whose prefix cache survives between queries). No cross-query claim
  is made.
- No quality comparison beyond the planted-label check above. Both
  sides run the same model and prompt.
