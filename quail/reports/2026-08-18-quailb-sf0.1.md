# QUAIL-B benchmark results at SF=0.1 (before the KV-write fix)

Date: 2026-08-18. One H100 on Modal. Qwen3 4B fp8. All data files are
in `results/`. Plots are generated by `reports/make_plots.py`.

These numbers were collected before the batched KV-write fix. The
2026-08-19 rerun is in `2026-08-19-quailb-sf0.1.md`. The filter
queries (B1 to B4, B12, B13) were 14% faster on that rerun. The join
queries moved by about 2%.

## What QUAIL-B is

QUAIL-B is a benchmark of 14 queries over five document sets built
from real text (IMDB reviews, BioDEX patient reports, ABT-BUY product
descriptions, and derived sets). Each document has planted yes/no flag
lines with known ground truth, so we can measure both speed and
correctness.

The benchmark runs two passes in one session. The cold pass flushes
and disables the KV store (each document's KV is computed from
scratch). The warm pass enables the KV store (documents whose KV was
saved in a previous query can restore it instead of recomputing it).

SF (scale factor) controls document counts. At SF=0.1, the sets have
5,000 reviews (400 tokens each), 1,000 threads (1,200 tokens each),
200 reports (3,000 tokens each), 100 products (150 tokens each), and
2,560 medical terms (32 tokens each).

## Results

The plot `plots/quailb_cold_warm.png` shows each query's wall time
on both passes. The data is in `quailb_sf0.1.json`.

Cold pass total: 1,806 s. Warm pass total: 1,718 s. The warm pass
was 5% faster.

## Why the warm pass was only 5% faster

The warm pass was honest, and the data explains where warm KV helped
and where it couldn't.

- **Join queries don't use the store yet.** B5, B8, B10, B11, and B14
  account for 1,320 s of the cold pass's 1,635 s of query time (81%).
  The KV store currently saves and restores only filter-scanned
  documents. Join anchors are not stored. B14 (a rerun of B5 with a
  new question) gained nothing from the warm pass: 279.3 s compared
  with 280.9 s cold. Adding join anchor storage to the KV store is
  the biggest remaining warm-pass improvement.
- **The store held only 342 of 5,000 reviews.** The reviews corpus is
  3.2M tokens. At 144 KB of KV per token, the full set needs about
  470 GB of host memory. The store has 64 GB. The planner keeps only
  documents whose KV is long enough that restoring it is faster than
  recomputing it, which selected the 342 longest reviews (432,525
  tokens, about 63 GB). The three queries that re-scanned reviews
  with new questions each restored those 342 documents: B3w went from
  35.4 to 31.8 s, B3c went from 42.5 to 31.0 s, and B13 went from
  35.6 to 31.8 s.
- **The worker container restarted and lost the store.** Warm B2 shows
  31.6 s of boot time. The container died between warm B1 and warm
  B2. B1 had just saved 63 GB of KV to the store (device-to-host
  copies, which is also why warm B1 was 5.8 s slower than cold B1).
  B2 found an empty store, restored nothing, and saved the same 342
  documents again. The likely cause is host memory pressure from the
  64 GB pinned store plus model-loading leftovers. Without the
  restart, B2 would have restored its 342 documents and saved 4 to
  11 s.

## Selectivity check

The benchmark plants flag values with known rates, and each query
reports both the provided selectivity (what the planner was told) and
the observed selectivity (what the model actually returned). The model
was stricter than the planted labels on most filters.

For example, B3's first filter was planted at selectivity 0.9 (90% of
documents should pass), but the model only passed 40%. The 0.2 filter,
when asked first in B3c, observed 0.07 instead of 0.2.

Any cost model that uses provided selectivities to predict costs will
overestimate the number of surviving documents. The predictions are
still directionally useful (the low-selectivity filter still kills
more documents than the high-selectivity one), but the absolute
numbers drift.

## Cost order lost to written order on the cold pass

B3w (written order) and B3c (cost order, strictest filter first) run
the same five filters on the same 5,000 reviews, but B3c was 7 s
slower on the cold pass (42.5 s compared with 35.4 s). B3c evaluated
fewer document-stages (5,754 compared with 7,575), so the cost model
picked a better filter order. But the time got worse.

Both queries read all 5,000 documents in full at stage 0 (document
token costs dominate; later stages add only question tokens under
KV rewind). The stage counts don't explain a 7 s gap, so something
in chunk packing or admission behaves differently when stage 0 kills
93% of documents in B3c compared with 60% in B3w.

On the warm pass the order flipped the expected way (B3c 31.0 s, B3w
31.8 s), because restored documents skip the stage-0 compute that
caused the cold-pass gap.

We haven't traced the two cold runs to find the cause. Worth
investigating before relying on cost-order claims at larger scale.

## Follow-ups

- Wire join anchors into the KV store. Join queries are 81% of the
  suite and get no warm benefit today.
- Fix the container restart during the warm pass. Likely host memory
  pressure. Lower `cpu_memory_gb` or raise the container memory
  limit.
- Rerun the suite with the batched KV-write fix to get updated
  filter-heavy numbers. Done: see `2026-08-19-quailb-sf0.1.md`.
  The B3c cold gap is gone after that fix.
